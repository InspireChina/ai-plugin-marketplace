# AI SOW Epic 级混合团队排期与人天设计

状态：待评审

日期：2026-08-23

目标插件版本：0.1.0-beta.1 后续版本

## 1. 背景与结论

现有人员模拟器以项目总开发人天、统一红军或蓝军模式、每组固定一名 TL/BA/QA 和一名全职 PM 为基础。该模型不能表达真实项目中常见的以下情况：

1. 外部分包组与内部组并存，并采用不同的交付模式；
2. Epic 在项目开始时定向分配给小组；
3. 内部组完成本组工作后可以支援其他 Epic，外部组默认不共享；
4. BA、TL 跨组服务，PM 跨项目服务；
5. 外部团队只按实际开发人天计算，不计敏捷仪式和等待人天；
6. 预览需要解释每一类人天的来源，而不是只给出总人数和总日历。

本设计选择“逐工作日、全局阶段门禁、Epic 初始归属、Dev 可选共享”的确定性调度模型。Excel 负责用公式回填 Epic 级工作量，模拟器负责团队配置、每日调度、日历生成和人天构成解释。

## 2. 已确认的业务规则

### 2.1 阶段与工作量

- 项目阶段固定为：开发 → SIT → UAT → 上线。
- 上线工作属于开发范围，但只能在全部 UAT 工作完成后执行，不参与 UAT。
- 人工测试不单独建立 Story；QA 在流程上承接 Dev 已完成的功能。
- 自动化、性能与容量、安全与隐私、兼容性与无障碍等需要编码的测试工作属于开发工作量。
- 普通 Story 只有一名主责 Dev 参加开卡和结卡，合计 0.5 小时/Story。
- TL 的少量设计工作不作为独立容量约束。

### 2.2 团队与模式

- 每组独立选择红军或蓝军，不再使用项目级统一模式。
- 每组 Dev 人数范围统一为 1～4 人。
- 红军工作量系数为 1.0。
- 蓝军表示“10 天的开发工作 6 天完成”，工作量系数为 0.6。
- 团队来源与交付模式是两个独立维度。内部或外部组都可以选择红军或蓝军。
- 外部组默认红军、默认不进入共享池，但两个默认值都允许手动覆盖。
- 内部组默认允许共享；本组当前阶段的自有工作完成后，Dev 可以支援其他未完成 Epic。
- 共享池只转移 Dev 交付能力。TL、BA 本身是项目级共享角色；QA 不作为共享开发容量。

### 2.3 角色投入

- QA 仍按每组一人、100% 项目投入计算。
- BA 和 TL 在每组分别配置投入率，范围为 0%～100%。
- 一个 BA 或 TL 可以跨组。例如三个组的投入率为 50%、50%、100%，对应 2.0 FTE，最低需要两人。
- PM 配置项目投入率。例如兼任两个同等项目时，本项目投入率为 50%。
- BA、TL、PM 的部分投入用比例填充方块展示；完整方块为 1 人天。
- 内部 Dev 不使用兼职投入率；内部 Dev 在项目工作日内全职投入，未用于开发或敏捷实践的时间归入等待/缓冲人天。
- 外部 Dev 不计敏捷、等待或缓冲人天，只计实际完成开发工作的时间。

## 3. 范围与分期

### 3.1 第一阶段：模拟器

- 用 Epic 级示例数据或独立手填回退数据完成调度模型和预览；
- 支持每组来源、模式、Dev 数、BA/TL 投入率、共享开关和 Epic 初始分配；
- 输出连续日历、分组结果、人天构成和算法说明；
- 保持已有项目总工作量手填区与团队参数区分离。

### 3.2 第二阶段：Excel

- 在权威工作簿中增加 Epic 级公式汇总；
- 将 Task/Story 估算通过公式聚合到 Epic；
- 向模拟器提供稳定的 Epic 级只读数据区域；
- 验证 Epic 汇总与项目总计完全一致。

### 3.3 本设计不处理

- 不记录具体 BA、TL 或 PM 姓名及个人排班；只计算 FTE、人天和最低人数；
- 不使用优化求解器寻找理论最优排期；
- 不改变 Task 基础人天和复杂度模型；
- 不把 QA 人工测试转换成开发 Story 或 Task；
- 不自动改变 Epic 的业务归属；共享支援只改变实际执行组。

## 4. 领域模型

### 4.1 Epic 工作量

每个 Epic 包含以下只读估算字段：

| 字段 | 含义 |
|---|---|
| `epicId` | 稳定且唯一的 Epic ID |
| `name` | Epic 名称 |
| `storyCount` | 普通 Story 数 |
| `developmentDays` | UAT 前开发人天 |
| `sitDays` | SIT 开发人天 |
| `uatDays` | UAT 开发人天 |
| `goLiveDays` | UAT 后上线开发人天 |
| `initialGroupId` | 初始负责组 |

工作量按 Epic 和阶段形成独立队列：

```text
EpicWork(epicId, phase, baselineDays, remainingDays, initialGroupId)
```

### 4.2 小组配置

| 字段 | 含义 |
|---|---|
| `groupId` | 稳定组 ID |
| `source` | `internal` 或 `external` |
| `mode` | `red` 或 `blue` |
| `devCount` | 1～4 |
| `shareAfterOwnWork` | 本阶段自有工作完成后是否支援其他 Epic |
| `baRate` | 0～1 |
| `tlRate` | 0～1 |

默认值：

| 来源 | 模式 | 完成后共享 |
|---|---|---|
| 内部 | 红军 | 开启 |
| 外部 | 红军 | 关闭 |

默认值不构成限制，使用者可以逐组覆盖。

### 4.3 项目配置

项目配置包含开始日期、规划方向、目标迭代数、PM 投入率和小组列表。规划方向继续支持：

- 团队驱动：使用手工填写的每组 Dev 数；
- 时间驱动：保持小组来源、模式、Epic 分配和共享设置不变，在每组 1～4 Dev 的范围内寻找满足目标迭代数的最小 Dev 配置。

## 5. Excel 公式回填契约

Excel 是 Epic 级工作量的权威来源。Epic 汇总必须使用公式引用 Story/Task 权威区域，不能复制静态值。

每个 Epic 至少回填：

```text
普通 Story 数
UAT 前开发人天
SIT 人天
UAT 人天
上线人天
Epic 总开发人天
```

聚合原则：

1. 通过稳定的 Epic、Feature、Story、Task ID 建立归属关系；
2. 普通 Story 数按 Epic 下符合口径的 Story 计数；
3. 各阶段人天从 Task 估算列按阶段分类汇总；
4. Epic 总开发人天等于四个阶段人天之和；
5. 所有 Epic 合计必须等于项目级对应总计；
6. 模拟器只读取公式结果，不在导入时重新解释 Task 估算规则；
7. 公式错误、空 Epic ID、重复 ID 或总计不一致时阻止正式排期。

手填回退区使用相同字段，但必须与 Excel 只读区视觉分离，并明确标记数据来源。

## 6. 调度模型

### 6.1 采用逐日调度的原因

迭代级总公式不能准确说明某组何时完成自有工作、何时开始共享支援、何时等待下一阶段，也无法为连续日历产生可信的逐日方块。优化求解器虽可寻找理论最短工期，但结果难以解释且超出当前需要。因此使用规则明确、结果可重复的逐工作日调度。

### 6.2 全局阶段门禁

项目只允许一个活动阶段：

```text
development → sit → uat → go-live
```

只有当前阶段全部 Epic 的剩余工作量归零，下一阶段才开始。上线阶段必须等待整个项目 UAT 完成，而不是某个 Epic 单独完成 UAT 后提前开始。

### 6.3 模式与实际开发时间

设执行组为 `g`，交付模式系数为：

```text
F(g) = 1.0  红军
F(g) = 0.6  蓝军
```

执行一段 Excel 基准工作量 `W` 所需的实际 Dev 人天为：

```text
ActualDevDays = W × F(g)
```

共享支援使用实际执行组的系数。蓝军支援原本分配给红军组的 Epic 时，该支援部分仍按 0.6 计算；Epic 的初始归属不改变。

### 6.4 内部组容量

内部 Dev 参加以下固定敏捷活动：

| 活动 | 每名 Dev |
|---|---:|
| 站会 | 0.5 小时/工作日 |
| Code Review | 1 小时/工作日 |
| IPM | 2 小时/迭代 |
| Retro | 1 小时/迭代 |
| ShowCase | 不占 Dev 工作时间 |

每个完整 10 工作日迭代共 18 小时，即 2.25 人天；净开发容量为 7.75 人天/Dev/迭代。

逐日计算时，每名 Dev 的固定敏捷小时为：

```text
迭代第 1 个工作日：3.5 小时
迭代第 10 个工作日：2.5 小时
其他工作日：1.5 小时
```

内部组当日可用于编码的实际容量为：

```text
InternalActualCapacity(g, day)
  = devCount(g) × (8 - agileHours(day)) / 8
```

普通 Story 的开卡和结卡合计 0.5 小时，只由一名主责 Dev 承担：

```text
StoryAgileDays = storyCount / 16
```

该动态敏捷人天归入 Epic 的初始内部负责组。外部负责组不计算该项。共享支援不重复增加 Story 数或开结卡人天。

在开发阶段，初始内部负责组先从当日实际容量中扣减尚未完成的 Story 开结卡队列，再用剩余容量执行 Epic 基准开发工作。该队列计入项目工期，但不会被红军或蓝军系数压缩。

### 6.5 外部组容量

外部组不计算固定或动态敏捷人天：

```text
ExternalActualCapacity(g, day) = devCount(g)
```

外部 Dev 人天只等于实际执行的编码时间。阶段等待、项目剩余时间和未使用容量均不进入外部人天。

### 6.6 每日分配顺序

每个工作日、每个活动阶段执行以下规则：

1. 小组优先处理初始分配给自己的未完成 Epic；
2. 一个组有多个自有 Epic 时，优先处理剩余基准工作量最大的 Epic；相同时按 Epic ID 排序；
3. 自有队列为空且 `shareAfterOwnWork=true` 时，进入共享池；
4. 共享容量优先支援按当前各组剩余容量估算后预计最晚完成的 Epic；相同时按剩余工作量和 Epic ID 排序；
5. `shareAfterOwnWork=false` 的组在本阶段停止开发，下一阶段存在自有工作时重新投入；
6. 每段执行记录实际组、初始归属组、Epic、阶段、基准工作量、实际人天及是否共享；
7. 当前阶段所有 Epic 归零后，下一工作日进入下一阶段；同一天未使用的阶段尾部容量不跨阶段使用；
8. 周末展示在日历中，但所有角色的人天为零。

该顺序保证同一输入产生同一结果，便于审计和测试。

## 7. 人天计算

设项目实际工作日为 `T`，组数为 `G`。

### 7.1 内部 Dev

内部 Dev 为全职项目人员：

```text
InternalDevStaffDays(g) = devCount(g) × T
```

拆分为：

```text
内部实际开发人天
+ 内部固定敏捷人天
+ 内部 Story 开结卡人天
+ 内部等待/缓冲人天
= InternalDevStaffDays
```

其中：

```text
InternalBuildDays(g)
  = Σ(该组实际执行的基准工作量片段 × F(g))

InternalFixedAgileDays(g)
  = devCount(g) × Σ每日固定敏捷小时 / 8

InternalStoryAgileDays(g)
  = Σ该组初始负责 Epic 的普通 Story 数 / 16

InternalBufferDays(g)
  = InternalDevStaffDays(g)
    - InternalBuildDays(g)
    - InternalFixedAgileDays(g)
    - InternalStoryAgileDays(g)
```

等待/缓冲必须大于等于零；出现负数表示调度或汇总错误。

### 7.2 外部 Dev

```text
ExternalDevDays(g)
  = Σ(该组实际执行的基准工作量片段 × F(g))
```

外部 Dev 不增加固定敏捷、Story 敏捷或等待/缓冲人天。外部共享开关手动开启后，其支援工作也进入上述实际开发人天。

### 7.3 BA、TL、QA、PM

每组分别配置 BA 和 TL 投入率：

```text
BA_FTE = Σ baRate(g)
TL_FTE = Σ tlRate(g)

BA人天 = T × BA_FTE
TL人天 = T × TL_FTE
QA人天 = T × G
PM人天 = T × pmRate
```

最低人数用于人员视图，不改变人天：

```text
BA最低人数 = CEILING(BA_FTE)
TL最低人数 = CEILING(TL_FTE)
```

例如三个组 BA 投入率为 50%、50%、100%，则 `BA_FTE=2.0`、最低两人，BA 人天为 `2T`。

### 7.4 项目总人天

```text
项目总人天
  = Σ内部 Dev 全职人天
  + Σ外部 Dev 实际开发人天
  + BA人天
  + TL人天
  + QA人天
  + PM人天
```

内部敏捷、内部等待和共享支援是总人天的构成项，不能在项目总人天之外再次相加。共享支援人天是实际开发人天的子集，不是额外投入。

## 8. 时间驱动规划

时间驱动模式输入目标迭代数 `I_target`。搜索过程：

1. 保持 Epic 分配、小组来源、红蓝军模式、共享开关、BA/TL 投入率和 PM 投入率不变；
2. 从 Dev 总数 `G` 到 `4G` 逐级搜索每组 1～4 Dev 的配置，并按当前预计瓶颈优先扩展；
3. 对每个配置运行同一个逐日调度器；
4. 保留 `工作日 ≤ I_target × 10` 的配置；
5. 优先选择 Dev 总数最少的配置；
6. Dev 数相同时，优先项目总人天较少、完成日期较早的配置；
7. 用已经找到的同 Dev 总数更优结果剪枝；超过安全搜索上限时返回明确错误，不给出未经验证的推荐；
8. 无可行配置时显示明确错误，不改变用户已经填写的参数。

## 9. 预览信息架构

### 9.1 输入区

1. **Excel Epic 工作量**：只读 Epic 表格；显示数据来源和项目总计校验；
2. **手填回退**：与 Excel 区域分开，只在没有正式工作簿数据时使用；
3. **项目参数**：开始日期、规划方向、目标迭代数、PM 投入率；
4. **小组配置**：来源、模式、Dev 数、共享开关、BA/TL 投入率；
5. **Epic 分配**：每个 Epic 选择一个初始负责组。

切换来源、模式、规划方向或共享开关不能改写 Epic 工作量。模式变化只重新计算排期和人天。Dev 输入统一限制为 1～4。

### 9.2 顶部结果

顶部显示：

- 项目完成日期；
- 实际工作日和迭代数；
- 总人天；
- 内部/外部 Dev 配置；
- BA、TL、QA、PM FTE 和最低人数；
- 是否存在无法调度的剩余工作。

### 9.3 人天构成表

构成表至少包含：

| 构成 | 必须显示的解释 |
|---|---|
| Excel 基准开发人天 | 四个阶段 Epic 工作量合计 |
| 红军实际开发人天 | 红军执行基准工作量 × 1.0 |
| 蓝军实际开发人天 | 蓝军执行基准工作量 × 0.6 |
| 内部固定敏捷人天 | 每日仪式小时按 Dev 汇总 |
| 内部 Story 敏捷人天 | 内部初始负责 Story 数 ÷ 16 |
| 内部等待/缓冲人天 | 内部全职 Dev 人天减开发和敏捷 |
| 外部 Dev 人天 | 外部实际执行的开发人天 |
| 共享支援人天 | 实际开发人天中的支援子集 |
| BA/TL/QA/PM 人天 | 投入率或人数 × 项目工作日 |
| 项目总人天 | 所有不重复投入项合计 |

每一行同时显示数值和算法说明。按组明细显示本组工作、共享支援、敏捷、等待和角色投入。

### 9.4 连续日历

日历继续使用一个连续表格：

- 列固定到自然日期，工作日和休息日使用不同背景；
- 阶段背景依次为开发、SIT、UAT、上线；
- 角色使用稳定颜色；
- 完整方块为 1 人天，部分填充表示相应投入比例；
- Dev 方块额外区分本组工作、共享支援和等待/缓冲；
- 外部 Dev 只在发生实际开发投入时显示；
- QA 为每组一条完整投入行；
- BA、TL 按组显示投入率；PM 按项目投入率显示；
- 悬停或选中显示角色、组、Epic、阶段、工作类型、人天和计算来源；
- 休息日展示但不计人天；
- 表格自身允许横向滚动，页面其他区域不得横向溢出。

## 10. 校验与错误处理

正式排期前必须验证：

1. Epic ID 唯一且每个 Epic 已分配初始组；
2. Epic 四阶段人天和 Story 数均为非负数；
3. Epic 汇总与项目总计差异不超过 0.01 人天；
4. 每组 Dev 数为 1～4；
5. BA、TL、PM 投入率为 0%～100%；
6. 至少有一个组可以处理每个非零阶段；
7. 调度过程中若剩余工作没有合格执行组，停止并显示 Epic、阶段和原因；
8. 时间驱动搜索无可行解时显示目标迭代数、当前上限和最早可完成结果；
9. 日历循环设置安全上限，达到上限视为模型错误，不能返回伪造完成日期。

错误不得静默修正 Epic 工作量、模式或投入率。输入无效时保留用户内容并在对应区域显示原因。

## 11. 组件边界

模拟器拆为四个可独立测试的逻辑单元：

1. `normalizeInput`：解析并验证 Excel/手填、项目和团队配置；
2. `scheduleByDay`：只负责阶段门禁、每日容量、Epic 归属和共享分配；
3. `summarizeEffort`：从执行记录计算开发、敏捷、等待、角色和总人天；
4. `renderPreview`：只负责控件、汇总表和连续日历，不重复计算业务公式。

Excel 公式回填与浏览器调度器通过明确的 Epic 数据契约连接，避免在界面代码中重新聚合 Task。

## 12. 测试策略

### 12.1 调度测试

- 单一内部红军组与现有公式一致；
- 单一内部蓝军组把编码工作压缩为 60%，敏捷时间不压缩；
- 单一外部红军组无敏捷、无等待，只计实际开发；
- 外部蓝军手动覆盖后无敏捷且工作量按 60% 计算；
- 内外部混合时，各组模式独立生效；
- 共享关闭组不会处理其他 Epic；
- 共享开启组完成自有工作后支援预计最晚完成的 Epic；
- 支援部分使用执行组模式，但不改变 Epic 初始归属；
- 阶段门禁阻止 SIT、UAT 和上线提前开始；
- 周末不产生容量或人天；
- 阶段尾部剩余日容量不跨阶段复用。

### 12.2 人天测试

- 内部 Dev 人天准确拆分为开发、固定敏捷、Story 敏捷和等待；
- 外部 Dev 总人天等于实际开发人天；
- BA/TL 投入率 50%+50%+100% 得到 2.0 FTE 和 `2T` 人天；
- PM 50% 得到 `0.5T` 人天；
- QA 得到 `G×T` 人天；
- 共享支援是开发子集，不被重复加入项目总人天；
- 所有构成项之和与项目总人天一致。

### 12.3 交互与视觉测试

- 切换来源、模式、共享开关或规划方向不修改 Epic 工作量；
- 每组 Dev 上限始终为 4；
- 每组模式、BA/TL 投入率和共享设置互相独立；
- 部分填充方块与汇总人天一致；
- 工作日、休息日、角色、阶段、本组工作、共享和等待均能同时辨识；
- 在 360px、736px 和 1024px 宽度下无页面级横向溢出；
- 连续日历可以独立横向滚动；
- 亮色和暗色主题下文字与颜色保持可读。

## 13. 实施顺序

1. 先把当前模拟器的计算与渲染分离；
2. 用测试驱动实现 Epic 数据模型和逐日调度器；
3. 加入混合团队、共享规则和人天汇总；
4. 更新输入区、人天构成表和连续日历；
5. 完成浏览器交互与响应式验证；
6. 再调整 Excel，增加 Epic 级公式回填和一致性校验；
7. 用真实工作簿数据替换模拟器的 Epic 示例/手填回退数据。

## 14. 验收标准

设计实现完成后必须满足：

1. 同一项目可同时存在红军、蓝军、内部组和外部组；
2. 各组 Dev 上限统一为 4；
3. Epic 初始分配、外部独占和内部共享均可解释、可覆盖、可追溯；
4. 外部 Dev 不产生敏捷或等待人天；
5. BA、TL、PM 投入率正确折算人天和部分方块；
6. QA 仍按每组一名计算；
7. 上线工作始终位于全部 UAT 完成之后；
8. 预览同时展示日期、阶段、角色、工作状态和人天构成；
9. 人天构成无重复计算，并能从执行记录复算；
10. Excel Epic 汇总与项目总计一致，否则不允许进入正式排期。
