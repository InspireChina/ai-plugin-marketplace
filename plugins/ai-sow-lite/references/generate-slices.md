# 联合生成、公共归属与合并

本参考在骨架、片内生成及合并时使用。输入用途、稀疏历史和实例匹配只由 [输入分析](input-analysis.md) 维护；机械编写见 [命令与编写](generate-authoring.md)。以下是 Agent 的专业判断方法，不是 Python 门禁或新的检查阶段。

## 目标与验收属于谁

按目标组织 Epic/Feature；一个 Story 交付一个可说明的成果。独立角色目标、交付成果或可独立验收边界才构成拆分理由，同一目标的成功、失败和权限边界通常仍在一个 Story 中。页面章节、AC 条数及 Excel 行高不构成拆分依据。

每条 AC 用“条件/触发 → 可判定结果”表达一个清楚的业务成果、验收场景或对外契约。先形成完整场景，再按验收意图组织；AC 不是逐字段、逐状态码或逐断言的测试清单。同一场景的相关输入条件、可见结果和边界可一起表达；不同验收意图再分条。复杂分支用 Given/When/Then，简单成果用短验证点，可用中文。写入当前 `AC.text` 前随本次编写核对：

- **可测试**：读者能据结果判定通过/失败，明确角色、对象、状态及必要测量条件。有据的指标保留数值和口径，“运行正常”“性能良好”不替代验收结果。
- **无歧义**：保留决定结论的范围、否定/排除、权限和时间边界。同一查询场景可同时说明筛选、返回内容和分页；同一性能验收可列出条件明确的页面/接口目标。能分别编写测试不构成拆条理由，不把互不相干的成果堆成分号包。 对重试、补发和恢复，区分前次已完成、未完成或结果未知；有依据的分支分别说明结果，不能把某一前态的结果套用到所有失败。凡列名、允许值、长度或格式本身决定验收，直接写出必要判据；章节编号、“按约定校验”不能替代判据，来源引用仍留 evidence_refs。
- **What**：业务 Story 验收用户/系统行为，技术 Story 验收调用方可验证的能力/契约，交付 Story 验收可检查的交付成果。必要的 API 契约、响应数据边界、性能结果仍是 What；内部事务、表结构、组件调用和缓存方法属于实现约束。 把“先处理/过滤再输出”改写成允许或禁止出现的实际结果；只有处理次序本身是外部承诺时才验收次序。
- **独立性**：结果属于当前 Story，不要求在此重复验收依赖方的全部机制。存在依赖不等于不能独立判定当前成果。

例如，材料已明确撤销后旧分享链接失效，AC 可写“链接已撤销时，访问原链接不能获得文件内容，并显示已失效提示”，而不是“查询链接表并清除缓存”。材料要求业务访问可审计时，消费 Story 验收该访问的审计结果，Task 表达接入工作；公共 Story 验收审计能力的对外契约，不把“调用公共组件”本身当完成条件。示例不为项目新增规则。

业务 Story 用业务语言说明成果，不给每个实现 Task 再配一套 AC。页面和接口服务同一业务行为时，输入校验和结果边界表达一次；API 路径、状态码或字段名只有本身属于该 Story 承诺的外部契约时才保留，不因存在 API Task 就复制接口规格。独立接口/公共能力为交付目标的技术 Story 才围绕其调用契约组织验收。来源的数据库字段、内部元数据或整份请求结构不自动成为 AC。

已有 AC 较多时，先判断是否混入独立目标或实现细节，再按成果整理和公共归属去重。保留真实义务及必要 Task，移出的实施约束留在原 HLD/主题/证据，不转塞 notes 或 classification_basis，也不仅为存放细节新建技术 Story。层级、AC 和 Task 不设数量门禁；多条 AC 可由同一工作满足。Excel 自包含指完整读取本次 AC 和 open 问题，不是复制输入全集。

正常路径、异常/边界、角色权限、状态后续/通知是本次编写的覆盖视角，只采用与当前成果相关且材料明确的要求。不能从通用清单补猜超时秒数、重试/锁定次数或下游通知。AC 和备注中的事实、方案、责任及验证前提都须有输入依据；标准只支持 Task 单位、包含边界和分类。来源只说沿用规范但未给具体内容时不补写规范；若其内容决定验收而仍未知，按既有出口澄清或留问题，不能用“符合规范”冒充充分 AC。后期局部缺依据时留未知并绑定对象/字段，不再搜索、补问或自行认定。

技术/NFR 按实际承载位置处理：业务触发且影响验收结论的关键约束写入适用 Story 的 AC；项目级约束保留在主题/依据。有依据且独立交付、可被消费的公共能力才单列建设，由唯一公共 Story 验收能力的对外行为与契约；业务消费 Story 验收本业务的实际效果。比如共享查询客户端负责超时/重试能力，订单查询 Story 验收自己的筛选结果和可观察的失败反馈；保留判定指标所需的负载、数据和计时边界，不因精简措辞改变承诺。材料明确在各页面内部实现约束且不交付独立程序库时，各页验收自身关键行为，不创造公共平台，也不漏约束。用于测量指标的看板并不等于满足该指标。

交付范围从输入中的迁移、演练、上线准备和外部依赖主动识别。资产建设与实际执行分别判断，只有分别形成当前标准中的独立成果时才分项计量。外部承担的生产执行、数据准备或验收等责任保留为前提/排除；依赖未确定先归入输入问题。SIT/UAT 适用性是模板口径，不自动增加测试自动化、执行、生产部署、PoC 或设计工作；缺基础方案不能改成 Spike/设计 Task 来出稿。

## 备注与问题的目标

Story 的 Excel 备注通常为空，只写必要的已确认范围/责任/外部前提说明，以及实际影响该 Story 的待确认事项和当前处理。已确认说明须同时满足：省略会误解本 Story 的交付边界，且 AC 尚未表达。Agent 将这部分写入 `Story.notes`；待确认事项单独保存，由投影器合并到备注，不重复抄入 `notes`。

已确认说明来自 PRD/HLD 的明确陈述或用户已确认答复；只保留对当前 Story 必要的结论，不复制整段来源或问答历史。往期 SOW 只提供历史范围证据，不能据此认定当前责任或确认复用；原型主要支持行为与 AC，观察和文档冲突时记录问题。分析、拆分或修改反馈中的未知由 Agent 写成具体问题和真实当前处理，不能把所需前提写成已经具备的条件。

待确认项须影响当前范围、验收、分类或责任判断。资源已明确由客户提供且足以界定本期工作时，保留必要外部责任，不仅因尚未实际交付就增加“何时提供账号/凭据”的催办问题，也不声称资源已经就绪。

例如，只有输入已明确责任时才可写“本 Story 交付迁移脚本及非生产自测，生产迁移由客户执行。”局部执行责任未知时记录待确认事项“生产迁移由谁执行？”，并按实际候选说明哪些工作尚未拆明、未估算。可观察的验收行为和结果写入 AC，不在备注重复；工作方式/复杂度判断原因归 Task。依赖保留结构字段，只有影响交付责任且确需解释的外部前提才写入 Story 备注。Task 的模型 `notes` 同样通常为空，仅保留该 Task 必要且有依据的补充说明。Task 列表和证据引用各归自己的结构字段；Excel 的安全别名原名由投影器保留，Agent 不预写机械说明或外部路径。

Task 的 Excel 备注还展示非新建工作方式、非 M 复杂度的判断原因。Agent 将实际采用的原因写入 `classification_basis.rationale`，用 `fields` 标明支撑的维度；说明采用哪个既有实例及本次变化，或本次规模/规则如何符合标准定档，用户指定口径则如实写明。不同维度原因宜分别记录，共同原因可合并；不要再次抄到模型 `notes`。投影器只选择适用维度的已有原因，合并完全相同的正文，未知不编造；新建、M 的原因不额外展示，默认 M 的未知仍通过原待确认项表达。

open 问题用具体 `question` 加 `current_handling`，准确绑定实际目标；投影备注以“待确认：”开始。Epic/Feature 问题落实际受影响的 Story 行，AC 问题标明哪条 AC。Task 问题只落 Task 行；若同一问题也影响 Story 范围或 AC，由 Agent 显式追加受影响 Story/AC 的 target，不自动上卷。resolved/superseded 问题留项目 JSON/MD 历史，不留在 Excel 备注。Clarify 采用答复时，将仍影响当前交付的结论更新到对应 AC、必要 `notes` 或 Task 分类依据；没有必要说明时备注恢复为空，不保留“已确认”流水。未拆明且无 Story 的实际 Epic/Feature 由投影器在 01 表追加范围行，仅填实际父项和问题，Story/AC/人天为空；不为显示缺口伪造 Story/Task。

## Task 的实际单位和分类

先说明本片实际交付的对象和成果，再按当前模板匹配类型。`inspect/standards` 空 selector 返回目录；按片把候选类型合批查询，读取单位、交付成果、模式、包含边界和规模门槛，正常分页可继续。已有有效标准读取优先复用；只有存在具体歧义才比较相邻类型，不为每个 Task 强制查一个 challenger 或重复读取整行。

每个 Task 按该标准的基础单元计量。两个已知独立查询目标即使类型相同，也不能仅因同类型合为一个单位；多个 AC 共同描述同一交付对象则不各建一份实现。先判断成果，再判断工作方式：

- 新建：本期新交付的对象；现有平台承载一个新业务对象不等于该对象接入复用。
- 调整：同一实例已有依据，本期发生实际变化，只估本次变化及必要回归；SOW 文本改稿不构成实施调整。
- 接入复用：已知实例确实适用于本期，只估项目侧适配；普通配置/调用若已被消费者标准包含，不另计接入工作。

模式仍须是所选当前标准允许的值。分类依据同时连接本期事实和实际标准行，解释成果/单位/模式及定档理由；不能只根据类型名称或“旧项目”选择模式。

## 未知的有限出口

| 实际缺口 | 当前处理与绑定 |
| --- | --- |
| 仅复杂度无法从本片已有材料和标准识别 | 立即填 M，问题精确绑定该 Task.complexity，说明未知量和当前口径；不为定档再搜索、回读、重试或追问 |
| 相关历史候选存在，实例适用性未明 | 按输入参考的新建口径，问题绑定受影响 Task.work_mode 并保留具体历史候选和匹配范围；同根因影响多个 Task 合并问题 |
| 其他局部字段缺值 | 按合同留 null 或空 AC，问题绑定真实对象字段；明确不适用与未知区分 |
| 已知多个独立标准实例 | 根据已知边界有限拆分，不因同类型合并计量 |
| 已知超出标准单元、无法拆明 | 保留 Epic/Feature/Story 对象级 open 问题，`unestimated_work=true`；当前 Task 不冒充覆盖剩余工作，不用 M 掩盖已知 X |
| 目标、基础方案或责任仍不足以界定本期 | 回到输入充分性出口，保存补料要求；不替用户选方案 |

明确已有 S/M/L 档位不被默认值覆盖。标准给出 X 时先看是否有依据拆成独立单位；Task 的合法复杂度只有 S/M/L，不能把 X 写进 Task。局部未知允许随初稿交付；未拆明义务须在摘要/问题中可见。

## 一次语义整合

从骨架覆盖和有关联的 Task 检查成果归属，不做全量 Task 两两评审。重点比较公共建设/消费者、集成/内部同步、迁移/内含核验、IaC/普通配置、测试资产/重复执行：同一成果不能因为类型名不同就重复；不同成果也不能因为来源相同就删除。迁移单元已含的核验与消费单元已含的接入按标准保留在同一工作内。

复核每个本期义务的候选或明确缺口，项目级约束与外部责任的去向，所有输入问题的解决依据或正式目标，跨片 Story 关系及 AC 所属。公共范围真正发生变化时只修直接依赖片。合并完成后模型是正式业务来源，slice_id 不进入业务层级；引用完整性由 full check 验证，语义充分性仍由 Agent 负责。

## 有界返修和恢复

首次覆盖按已登记的有限目标/游标推进，每个目标首次处理一次，不用返修上限截断正常分页或大项目。重新安排同一范围最多一个批次；不是不断拆片扩大目标。

同一候选最多一轮修正，全请求最多两个自动返修批次，先到任一上限即停。把片内/跨片/机械错误按根因合批定位后修改，复用有效前序。工具操作或 Excel 失败，同一操作/根因最多重试一次，且计入上述请求总额度；没有实际输入或环境修法就不重试。同一根因再次失败、到限或无进展时返回诊断并保留候选/current；错误不能改名为待确认以绕过检查。

每批开始确定有限对象和修法，完成后记录结果与消耗，不把每个 CLI 调用当成一轮。render 自身会记录它消耗的返修额度，调用后复读 checkpoint，不能在外层再次扣同一批。纯专业修正由 Agent 保存计数，不能声称工具拦截了全部思考或提问。

响应丢失或中断时先做至多一轮结果查询恢复；已生效直接返回原版本，未生效保留实际文件，持续繁忙或事实不明就退出。重复 generate 不重写首版或倒回 current；现版修改使用 Clarify。取消结束执行；不能通过新 UUID、换片或重启增加额度。恢复读取活动记录、checkpoint、当前指针和有效候选，继承已耗次数；仍未知则保留未知并停止。用户实际新增材料/目标可以定向续接并记录关联，未变输入不重扫，旧额度不自动归零。
