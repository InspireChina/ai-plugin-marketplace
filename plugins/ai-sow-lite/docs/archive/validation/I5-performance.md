# I5.1：减少机械编写，定位响应成本

本轮接续 `4d05060` 已提交的 I4.3。目标是减少实际 Clarify 的机械编写和模型往返，并让现有原生用量更容易定位；不改变专业边界、确认、模板或有限退出规则。历史阶段证据保持原版本归属。

## 诊断和最小改动

复读 I4.3 两份明确指定的合成会话，原指引/定向指引分别生成 43,278 / 45,935 UTF-8 字节的工具代码。确认至交付分别用了 12 / 10 个模型响应、217.604 / 212.435 秒。减少 inspect 次数后，临时工具代码没有变少；重复出现信封、子进程、文件引用、确认绑定和交付调用。字节只是编写负担线索，不是 token 换算。

新增 [authoring.py](../../../runtime/ai_sow_lite/authoring.py) 和 [调用参考](../../../references/python-client.md)：

- Client.call 包装现有 execute，一次调用一个既有 operation。Agent 显式选择顺序；连续机械步骤可合并在同一宿主工具调用里。
- Client.save 只在已登记请求的 authoring 子目录保存不可变草稿；构造 Client 不创建缺检查点目录，也不重置额度。
- source_ref 映射实际文本/XLSX 区域引用；bind_confirmation 复核检查与展示计划字节，另存绑定实际答复的确认副本。原有 core check 继续核验完整来源和确认。
- 失败抛出原响应，停止当前批次，保留已完成引用。没有重试调度、语义分类器、模型 SDK 或新的 CLI 操作。

## 响应用量的真实上限

当前 Codex Desktop 0.153.4 的一个明确合成来源共 207 行、1,122,945 字节。28 条 usage 有精确 response_id；26 对工具调用有 call_id，但记录未提供两者到活动的完整身份链。真实反例中 usage 在活动 A 结束、B 开始之后到达；因此不能按 usage 结束时刻把整个响应记入 B。

报告将无活动绑定的原生数值标为 `scope.kind=response`，使用原生 response_id，basis.event_ids 回链已保存事件，并显示 `USAGE_BOUNDARY_UNKNOWN`。归属仍为 unassigned；请求总量与每响应条目是不同观察范围，不能相加。带真实集合的已有共享观察仍只有一个桶，原始事件无需迁移或回填。

该调整补充可追溯性，不表示逐活动 token 已精确取得。G12 继续开放；缺宿主身份链时保留未知，观测不阻断业务。今后若来源提供边界和身份链，可以判断完整响应所属活动；响应内部多个语义动作的聚合 token 仍不能反向精确拆开。

## 验证方法

TDD 从公开消费者开始：先出现缺 authoring 模块的 7 个失败，再通过真实 ingest/check/storage；随后实际确认、篡改/跨请求/错误来源的 5 个失败，再通过最小确认实现。已有指南消费测试读取真实登记/区域/检查响应，执行缩短后的示例，确认原计划不变；文本和 XLSX 映射保持真实 read_id。用量的公开 collect→report 反例先验证旧分组无法定位 response，再验证新报告、去重和正文不泄露。

实际速度配对使用两个独立合成项目，同一有效基线、模板、反馈和默认模型。控制副本冻结 `4d05060`；实验副本仅增加调用助手和三个有关参考差异，其他运行时字节相同。演员只拿用户原文、项目文件和运行 Skill；不提供预期编辑、Task ID 或评估答案。各自展示具体方案后才给真实执行确认。资源等待与确认段用时分开报告；模型缓存和服务调度不能固定，单次配对是探索性证据，不能当因果节省率或速度 SLA。

## 同基线实际结果

两侧均交付有效新版，分别复核47个输出/依赖引用，旧版摘要不变，最终业务文件等于实际展示候选。7个Task中只有迁移Task的notes/evidence_refs/classification_basis改变；复杂度仍为M，其余Task、Story/AC和依赖保持。唯一复杂度问题关闭，新增实际采用决定；总记录数仍未知。

| 方案：耗时 / 响应数 | 456.946秒 / 16 | 437.128秒 / 14 |

这是明确用户轮次的精确计数，不是轮次内input_analysis、design_discussion、export的精确分摊。输入累计包含重复供给的上下文，缓存输入已包含在其中；reasoning也包含在输出中，不能再次加总。原生轮次耗时含工具和宿主开销，不冒充纯模型耗时。

本次确认执行的工具代码从22,937降到9,485字节；方案轮次反而从30,784增到31,723字节。控制/助手的已记录operation数为19/23，工具累计7.193/7.108秒，Office各一次3.683/3.597秒。本配对中确认轮次的代码字节、响应数与用时同时减少，业务操作和Office次数未减少；各因素对耗时差值的贡献尚未测定。方案阶段仍约7分钟，分析JSON的编写与类型返修是下一处明确成本；本轮不宣称整体快速出稿目标已达成。

失败全部保留：控制侧先遇反馈来源路径错误，确认侧又遇/var与/private/var路径别名绑定错误，两次沿原请求有限返修；交付后可选元数据汇总还失败一次，未改有效版本。助手侧分析把三个字符串字段填成数组，一次同内容类型返修后通过；确认执行无返修。不同实际失误与不可控缓存/调度均影响结果，不能把单例差值当普遍因果收益。

按首次实际request标记，控制/助手的首个有用反馈为351.461/339.372秒，可用文件为671.767/695.503秒；后者含126.166/269.626秒真实评估及串行资源等待，因此不能直接用于比较处理速度。标记晚于Skill加载，覆盖partial，不回填开场时刻。

## 真实用量采集与审查

结束后仅对这两个已知会话做有界采集，分别导入26/19个唯一响应，六项原生计数逐项核对累计；known_tokens为1,877,894/1,311,420。新报告以response_id回链全部响应，归属仍为unassigned并显示边界缺失。两侧143/164个业务文件在采集前后摘要相同；CLOCK_UNALIGNED保持。第一遍读取1,185,115/1,186,576字节，采集耗时80.265/61.308毫秒；不是Agent业务执行时间。EOF复读分别28.006/28.079毫秒，101/106个事件及报告摘要/指标完全不变，本次EOF复读未重复导入或加总已观察用量。普通Skill仍未自动提供原生来源，精确活动成本仍缺。

独立审查发现通用起步示例在首次ingest前查询current会抛IO_FAILED；先以真实消费者复现Red，改为只构造Client并按入口登记后Green。新增测试及原有关测试33项通过，唯一P2已定点复核关闭。该修正针对新项目说明；保留本次既有项目实验副本原字节，不事后改写试验输入。原生用量公开消费者的Red/Green及既有共享桶兼容共132项通过，组合定向回归190项通过。

性能声明另经独立核对，数字和版本归属一致；将单例“主要原因”的归因收窄为并列观察，将EOF“计费”措辞收窄为本地用量未重复加总。最终完整Lite回归 **715 passed、12 skipped，623.35秒**，包含真实Office与独立复制Generate→Clarify消费者。该轮复用已验证交付基线，未替换真实Office断言；跳过仍是既有平台/条件限制。根测试52通过，仓库验证器和163场景清单检查通过；按仓库要求运行旧插件Skills回归388通过、4跳过，旧插件独立复制setup/generate成功。git diff --check通过。原模板SHA-256保持不变。

本阶段已完成薄调用助手和响应成本追踪；没有宣称整体速度达标，也没有关闭G12。后续性能优化应先针对实际分析JSON编写/类型返修，再以同语义结果验证，而非扩大流程控制或通过减少确认与校验缩短时间。脱敏计数和版本摘要见 [I5.1观察数据](I5.1-performance-observations.json)，自主取舍见 [AD29—AD30](implementation-decisions.md#i51-机械编写成本与响应成本定位)。
