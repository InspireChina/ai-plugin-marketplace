## 范围与执行方式

把安装消费者验证和新 AC 的 Excel 验证合成一次小案例，不重跑 Greenfield → Brownfield 整案。执行前冻结已有 [PRD](../../../tests/fixtures/generate/cases/three-scope/inputs/prd.md)、[HLD](../../../tests/fixtures/generate/cases/three-scope/inputs/hld.md)、输入答复脚本及“迁移数量仍未知，本次采用 M”的修改意见。没有预填模型、期望 Story 数或通过结论。

宿主原有 `ai-plugin-marketplace` 指向远端快照，该快照尚无 Lite；用同名本地来源注册时被正常拒绝。为保留用户原注册和旧插件，创建仅用于本轮的本地 marketplace 别名 `ai-sow-lite-release-check`，通过原生 `plugin marketplace add` / `plugin add` 安装。别名仅改变目录身份，插件内 304 个已提交文件与被测提交逐字节一致。

使用桌面应用随附的 Codex CLI `0.153.4` 执行真实 `exec` / `resume`，沿用 `gpt-6-astra` / `xhigh`。调用者只给插件名称、项目材料和实际答复，没有提供 Skill 路径；generate、clarify 均自动发现并读取安装缓存中的相应入口。首次入口在安装目录完成 Python 3.12.13 与锁定依赖自举，解释器及基础环境均位于本插件内。执行后重新核对 304 个源文件未变。

generate 在一个新会话中分析两份材料，合批询问一次迁移与发布责任；收到冻结脚本对应的实际答复后，完成四片及一次合并，生成 5 Story、7 Task。clarify 使用另一个新会话，只共享项目文件，先展示具体方案；主任务核对后才发送执行确认，没有预先注入批准或修改最终产物。

## I9-F01 · 隐式规范未取得适用内容或版本，却没有待确认

优先级 P1。实际 AC 使用了“约定的两个精确匹配筛选条件、四个展示条件”“既定 14 个字段的一对一映射”“使用现有发布规范”。冻结输入只说明已有定义、规范与规模，没有给出完整适用内容或规范版本；本次输入答复也只确认责任。

相应 AC 位于 `01-需求故事!D5`、`D6`、`D8`、`D9`，备注没有体现这些缺口，`J5/J6/J8/J9` 仍为“通过”。系统只保留了迁移复杂度问题。尤其发布规范名称、版本及实际 Go/No-Go 适用依据不明确，违反 [当前 AC 规则](../../../references/generate-slices.md#目标与验收属于谁) 中“影响验收的规范名称、版本或适用内容不明须留待确认”的要求。

这不要求把完整规范抄进 AC，也不要求为出首稿反复补齐资料。最小修复方向是让专业分析识别此类隐式引用：依据已明确时使用实际名称、版本和必要适用范围；缺失时沿已有局部待确认机制绑定受影响 Story/AC，使其行显示待确认。不能编造版本或把结构通过解释为业务条件已完整。

本次保留首次生成及修改后的原结果，不补写输入、不换样本、不重生成整案来覆盖发现。后续只需围绕该类缺口做定向修复与验证；无需改数据模型、模板、Task 计量或增加整体评审循环。clarify 的本次精确修改不承担修复这个无关问题。
