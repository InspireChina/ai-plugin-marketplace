# 09 · 文件共享与两个 Skill 的独立性

[返回总览](README.md)

## 1. 共享业务状态，不共享一条运行流程

新会话中的 clarify 应仅依靠项目文件和本次反馈理解当前 SOW。它不需要知道 generate 调用了哪些 Action、哪位 worker 完成了第几阶段，也不需要加载 generate 的聊天记录。

共享的核心是：输入及版本、as-is/to-be/gap 与匹配范围的可定位分析依据、当前交付模型、待确认项、已应用决定、模板版本和当前 Excel。两入口的过程草案与埋点各自记录；共享工具负责相同格式和可靠文件操作，不负责通用业务编排。

本章定义内部文件的职责。最小字段和未知编码见 [D02](detailed/D02-shared-data-and-evidence.md)，接口和一致生效协议见 [D07](detailed/D07-tools-storage-and-recovery.md)，Excel 投影及工作簿内问题/长内容定位见 [D06](detailed/D06-excel-projection-and-delivery.md)；这些合同仍待实现验证。当前基础工作簿只承载手工可见内容；不将内部 ID、来源、版本或生成状态塞进隐藏列，也不要求手工用户维护内部文件。

下面是候选逻辑布局，用于说明边界，尚不是已实现或定版的磁盘 Schema：

```text
.ai-sow-lite/
  project.json
  inputs/
    index.json
    originals/
    readings/
  template/
  analysis/
    index.json
    topics/
    observations/
  versions/
    <version-id>/
      model.json
      pending-items.json
      decisions.json
      projection.json
      sow.xlsx
      summary.md
      manifest.json
  current.json
  work/
    generate/<request-id>/
    clarify/<request-id>/
  telemetry/
```

项目运行数据与插件源码分离。模板和输入更新保留可识别版本；不得覆盖旧证据后让历史结果指向新的含义。布局不要求每次复制所有原件，具体存储与清理方式由实际规模验证。

## 2. 每类文件的责任

| 文件或逻辑内容 | 共享用途 | 关键约束 |
|---|---|---|
| project | 项目身份、新老项目类型、格式版本、默认语言等少量元信息 | 不存庞大聊天或运行状态机 |
| inputs / originals | 原始材料与来源、版本、格式、材料类型、使用用途、资源关联和读取覆盖 | 原件不被 agent 改写；新增材料可登记但不自动改变有效 SOW；未读或解析失败不等于内容不存在 |
| inputs / readings | 必要读取记录、所选区域与类型化摘录，绑定原件及读取器/选项 | 可丢缓存与交付所引用的依据分开；后者不能清理后只保留哈希 |
| analysis | 主题索引、必要事实与观察、分析判断、范围依据、证据定位与限制 | 结论绑定输入和相关决定版本；事实、判断及候选/已应用依据可区分；不要求全文结构化 |
| analysis / observations | 实际原型观察的版本、前置、动作/结果、限制和必要附件 | 按 D03 保留最少可回查证据，多主题共用；不默认保存完整浏览器日志 |
| template | 来自插件内复制资产的 Task 标准、参数和公式版本 | 有效结果指向其实际使用版本 |
| model | 层级、来源 AC、Task 六项专业内容、关系与证据引用、字段留空原因 | 稳定对象身份和关系可校验 |
| pending-items | 当前问题、现行处理、影响与应用关系 | 生成工作簿内完整待确认表与备注内部链接，同版 pending-items.md 保留兼容归档 |
| decisions | 已应用事实与决定、来源及适用范围 | 讨论草案不提前写成生效决定 |
| sow / summary / pending-items.md / details.md | 可独立阅读的 Excel，以及同版摘要和 Markdown 归档 | 与模型及待确认项属于同一版本 |
| projection | 对象 ID 与同版 Excel 的行、表、实际显示名映射 | 工具派生，用于反馈定位和关联核验，不承载第二份业务模型或计算权威 |
| manifest / current | 完整版本的身份及当前选择 | 只有完整且通过必要检查的版本可以成为 current |
| work | generate 的骨架、覆盖索引和各片候选；clarify 的讨论方案、修改候选与确认记录；各自的恢复信息 | 不作为当前业务事实；允许放弃和恢复 |
| telemetry | 实际执行开销及观测缺口 | 不参与决定业务是否足够或用户是否同意 |

Manifest 只需能核对本版本内容和完整性，例如文件标识或摘要及检查范围，不扩展成每阶段审批凭证。具体原子保存方式取决于宿主；实现前要证明中断和重复请求不会激活半成品。

Generate 在自己的 work 区保存轻量骨架、覆盖索引和各片候选。索引关联本次覆盖目标、已形成的业务对象、尚未完成范围、公共工作归属及适用的输入/规则依据，足够支持下一片读取、合并和中断恢复；不保存每个微动作的状态链。

范围索引覆盖业务、技术和交付需求，保存必要的公共能力与使用方、迁移/上线依赖、本期与外部责任、单一计量归属。新会话 clarify 应能沿这些关系定位技术 Story、业务接入 Story 或交付 Story，不依赖旧聊天。具体关系字段由 D02/D04/D05 用样例确定，不因此建立第二套技术需求库、实施对象实体或多父 Task。

一片保存成功只表示局部候选可复用，不代表已对外交付。合并及必要检查完成后，完整模型与 Excel 才进入有效版本。Clarify 读取合并后的业务对象，不需要理解 generate 的分片顺序，也不依赖其过程草案；生成片标识不成为新的业务层级或永久修改边界。

Analysis 可以在两入口之间复用，但只有适用的结论进入当前工作包。Clarify 新产生的依据先保存在草案；应用后再让新版本引用它，不能覆盖旧依据使旧版本语义漂移。

同一输入版本、相同解析方式得到的有效结构可供多个用途复用；按用途形成的分析结论各自保留适用范围。补充材料、解析方式或用途变化时，只重新处理受影响信息，允许定向复读原件。复用不能覆盖读取缺口，也不能把新增用途默认为已完成分析。历史按 D02 的可选粒度条目保存于主题，不强制重建完整旧 SOW；复用待确认允许当前字段有新建值。请求 work 按 D04B 保存批次及已用次数，恢复不重置。字段、来源定位、解析缓存和语义结论的失效规则由 D02/D03 联合设计，D07 负责相应文件操作；这里不预定完整 IR Schema、缓存键或新增存储服务。

模型字段允许“有依据的值”“缺依据的空值”和“明确不适用”三种语义；首稿采用 D02 的合法值、null + 精确问题目标，以及集成类型 null + 不适用标记。业务未知的空值关联待确认项，非集成 Task 的集成类型空白记录不适用。模板公式产生的人天是派生结果，不由 agent 在模型中手填另一套数值。

UAT 适用性同样是模板派生结果：类型标准与 Task 归属足以计算，模型不增加人工维护的 Story/Task UAT 字段，也不把它作为 clarify 的独立修改项。分类依据缺失时，问题关联工作类型；补足分类后模板自动更新 UAT。

已有 draft 按可选输入登记，保留原始层级和来源；不直接作为 current，也不要求导入后先成为完整模型。业务语义见 [10](10-draft-inputs.md)。

## 3. 读写边界

| 内容 | generate | clarify 讨论 | clarify 应用 |
|---|---|---|---|
| 原始输入与模板版本 | 读取、登记首次使用版本 | 读取、登记新增输入草案 | 引用方案决定采用的版本 |
| 分析索引与依据 | 建立候选并随初版保存适用引用 | 复用相关信息、保存候选补充 | 激活本片需要的新依据 |
| 当前模型 / 已应用决定 / 待确认项 | 成功时建立初版 | 只读，答案和方案写入 work | 按确认方案提交相关变化 |
| 当前 Excel | 成功时生成 | 读取；试算或预览明确标为草案 | 生成并检查一致的新版本 |
| 当前版本选择 | 初版全部有效后设置 | 不修改 | 全片成功后一次切换 |
| 日志与过程草案 | 本入口记录 | 本入口记录 | 接续同一请求或明确恢复关系 |

成功版本可以通过“先写完整候选版本，再切换 current”保持一致；这是一次结果保存，不是用户需要触发的发布或定稿步骤。项目由同一人串行使用，不设计并行改稿或自动合并；版本检查和短锁只防误覆盖与重复调用。

## 4. 方案确认需要关联什么

保存确认所对应的方案身份、基线与相关依赖、用户确认消息或简洁可追溯记录，以及写集合、回查边界和重要处理条件。记录用户真正确认的内容，不要求保存所有闲聊。

[D05](detailed/D05-clarify-and-change-scope.md) 细化具体候选、部分答复和已展示子集的确认；D02/D07 保留拆合原对象的确切版本，用于历史问题和旧行号定位。当前 open 问题指向当前对象，允许保留的历史引用必须实际可解析；不因对象退出就自动将问题记成已回答。

应用前核对相关内容是否仍适用。确认后若仅调整不改变方案含义的表述，无需重新询问；若改变范围、责任、估算前提或超出切片，必须回到方案讨论。收到旧问题答案时先核对问题版本和语义，不能只匹配 ID 就套用。

未确认方案、已确认待执行、执行失败和已生效结果需要能区分，但不必为每个微动作建立持久化状态。唯一的有效交付从 current 找到；work 文件存在不等于已经应用。

## 5. 跨会话、版本与缺失文件

| 情况 | 处理 |
|---|---|
| 用户在新会话运行 clarify | 读取 current、索引和相关对象，再按需补读证据；不要求粘贴旧聊天 |
| 只有自制 Excel draft，没有配套模型 | 作为 generate 的可选辅助输入，仍要求对应必需材料；不虚构已有有效基线 |
| 用户带来手改 Excel | 先明确它是否表达具体新意见；按补充输入读取相关内容，clarify 仍以共享模型为基线，不自动双向同步 |
| 问题只回答一部分 | 草案分别保留答案；本次确认范围只处理对应对象，未答项继续保留 |
| 没有任何待确认项，用户提出新建议 | 根据模型与来源定位，正常讨论调整方案 |
| 模型或模板版本不兼容 | 明确诊断或执行已支持的升级路径；不静默改解释 |
| current 存在但工件缺失 | 核对可恢复来源；必要时恢复同版文件，不以文件名存在冒充成功 |
| 上次已提交但用户没收到响应 | 核实请求与结果关系后返回原结果，不重复修改 |
| 仅澄清说明或关闭问题、业务内容不变 | 一致更新问题/决定及 Excel 视图；不重做无关业务分析 |

Draft 解析格式、共享文件兼容性及历史保留期限是需要验证的边界，见 [07](07-gaps-and-decisions.md)。任意手改 Excel 的无损往返同步不作为当前产品目标。基本前提是两 Skill 文件互通，不把丢失配套文件强行解释为可以无损恢复全部专业依据。
