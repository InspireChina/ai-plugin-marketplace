## 1. 数据边界与消费者

持久化的是下一片、下一次会话或可靠交付真正需要的结果，不保存 agent 的全部推理和聊天。Python 使用 D00 的 jsonschema 路径实现结构与引用检查；语义判断仍由 agent 完成。

| 数据 | 消费者 | 为什么必须留存 |
|---|---|---|
| 原件版本、用途和定位 | 输入分析、定向补读、clarify | 找回原话并识别过期依据 |
| 少量依据与主题覆盖 | 后续切片、clarify | 保留关键事实、限制及本期/外部责任，不重复读大材料 |
| 层级、AC、Task、依赖 | Excel、clarify、引用检查 | 投影结果，定位修改，检查公共建设/消费方和交付依赖 |
| 字段分类依据 | clarify、专业自查 | 解释为什么选该类型/方式/档位；不存推理长文或人天副本 |
| 待确认项及已应用决定 | 独立待确认说明、Excel 备注定位、跨会话问答 | 知道空在哪里、为什么空、什么答案已采用 |
| 版本清单及投影映射 | 保存工具、恢复、自然语言定位 | 核对同版文件；把“Excel 第几行”定位回稳定对象 |

不引入独立实施对象、全量需求 IR、Task 多父归属、必填 AC—Task 边或第二套技术需求库。业务、技术、交付是分析必须覆盖的视角，不增加用户要填的分类列。

## 2. 交付模型

`model.json` 顶层为 `schema_version`、`epics`、`features`、`stories`、`tasks`、`dependencies`、`lineage`。各数组保存当前有效对象；无记录的数组为空。对象 ID 在项目内唯一，数组位置不是身份；字段名保持英文，业务文本默认中文。

| 对象 | 必需字段 | 约束和使用方 |
|---|---|---|
| Epic | `id`、`title`、`evidence_refs` | 范围骨架与 Excel“需求”；标题可由 agent 概括，有范围依据 |
| Feature | `id`、`epic_id`、`title`、`evidence_refs` | 唯一 Epic 父项；Excel“子需求” |
| Story | `id`、`feature_id`、`title`、`acs`、`notes`、`evidence_refs` | 唯一 Feature；专业字段仅标题、AC、备注，其他均为内部身份/依据 |
| AC，内嵌 Story | `id`、`text`、`evidence_refs` | 可独立定位修改；有来源的验收条件，不能用模板完成标准代写项目 AC |
| Task | `id`、`story_id`、`name`、`work_type_name`、`work_mode`、`complexity`、`integration_type`、`notes`、`not_applicable_fields`、`evidence_refs`、`classification_basis` | 一个 Story 父项；六项专业内容投影模板；没有人天、倍率、数量乘数或 SIT/UAT 输入字段 |
| Dependency | `id`、`from_story_id`、`to_story_id`、`kind`、`notes`、`evidence_refs` | `from` 使用/依赖 `to`；`kind` 首版为 `uses` 或 `delivery_precondition`，不是执行顺序 |
| Lineage，按需 | `from_version_id`、`from_ids`、`to_ids`、`reason`、`evidence_refs` | 实质替换、拆分、合并或删除的义务去向；from_version_id 定位旧对象的确切版本。删除允许 to_ids=[]，须说明退出本期依据 |

`notes` 可以是空字符串；不因普通备注为空创建问题。名称、标题、父引用和 ID 不能靠 null 绕过结构检查。`acs=[]` 只在该 Story 验收依据暂缺且存在对应待确认项时允许；部分 AC 已知时保留已知条目，对缺失的验收意图创建指向 Story `acs` 的问题，不造占位假 AC。

没有独立 AC—Task 表；检查在 Story/切片层面确认工作足以覆盖验收意图，以及是否有设计、PoC、迁移等其他来源支持的工作。真实需要追查局部覆盖时可以写入简洁备注/分析，不强制扩大固定字段。

### 2.1 Task 分类依据

`classification_basis` 为小数组，每项含 `fields`、`evidence_refs`、`standard_id`、`rationale`。允许几个字段共用一条依据；理由只记录“本次变化与标准边界怎样对应”。`standard_id` 定位本版本模板中的标准行，不复制标准数值或公式。模板身份由版本 manifest 绑定。 工作类型尚未匹配时，默认 M、已知模式或不适用等仍可有依据，相关条目的 standard_id 允许为 null；不能编造标准 ID 来通过检查。work_type_name 一旦确定，分类依据须定位同版对应标准行。未匹配类型本身继续保持 null 与字段问题，按 D06 原样填值，金额由模板处理。

新建口径适用于两种情况：相关历史无候选；有具体业务关联的候选但实例或本期适用性未定。后一种保留新建值并附复用待确认，不能当成已确认不可用。分类依据引用目标、历史候选/范围、已知差异及采用该口径的理由；新项目无历史时引用项目类型和空基线登记，不造历史条目。真实未读/损坏或本期方案基础不足不能通过默认口径掩盖。

有效非空分类以及明确不适用的分类都须有依据。复杂度无法从现有材料判断时采用用户授权的默认 M，分类依据明确写“按默认 M 出稿，尚缺哪些定档事实”，并关联 open 问题；这是估算口径，不伪称资料证明了 M。无须为这一缺口回读原件、搜索规模或追加一轮提问。其他没有结论的字段不写猜测理由，其缺口由待确认项解释。工具验证类型名称和标准 ID 对应、枚举及模板允许的方式，不能单凭理由文本存在就断言专业判断正确。

示例：EX01 的 T-06 分类依据引用 H-D1/A1 和 DATA-MIGRATION，解释单一资料域迁移与内含核验。用户补条数后，新增复杂度字段依据；没有新增定量估算字段。

### 2.2 空值采用两处明确规则，不包装每一个值

| 语义 | 编码 | 检查与 Excel 行为 |
|---|---|---|
| 有依据的值，包括无候选时的新建 | 字段为合法字符串，附对应来源/匹配依据 | 正常投影 |
| 有复用候选，当前按新建出稿 | `work_mode=新建`，分类依据解释当前口径，同版 open 问题指向该字段和相关工作 | 新建口径可由模板计算，备注/问题明确候选及未确认；不是缺值，也不是复用已批准 |
| 无法判断复杂度，默认 M 出稿 | `complexity=M`，分类依据说明采用默认口径，同版 open 问题指向 complexity | 按 M 计算并提示待用户确认，不留空、不反复找定档证据 |
| 缺依据且没有授权默认值 | work_type_name、work_mode 或 integration_type 为 `null`，同版 open 问题明确指向对象/字段 | Excel 留空并关联问题；complexity 不走此分支，未知按默认 M |
| 明确不适用 | `integration_type=null`，`not_applicable_fields` 包含 `integration_type` | Excel 留空，不制造问题；须符合工作边界 |
| 非法或漏写 | 错误枚举、无解释的分类 null、缺父项等 | 拒绝候选，不能冒充局部未知 |

首版只有集成类型支持“不适用”；其他三项分类不能用“不适用”回避判断。集成工作缺内部/外部责任依据时是未知，不是不适用。无须为每个字段增加 `value/status/confidence` 三层对象。

`work_mode` 使用模板原词 `新建`、`调整`、`接入复用`；`complexity` 仅 S/M/L，生成候选无法定档就采用 M 并附问题。已有明确档位或已知触发 X/拆分的证据不能被默认 M 覆盖；X 按有限局部边界拆分或记录标准缺口，不当成一个人天档位。`integration_type` 为 `内部集成`、`外部集成` 或上述 null。模板规则与枚举冲突时诊断模板/合同兼容性，不能静默规范化改词。

### 2.3 共享关系的最小表达

EX01 用 S-01/S-02 → S-03 表示公共消费，S-01/S-05 → S-04 表示交付前提。T-05 的备注明确公共实现和独立验证归属，T-01/T-03 明确只承担页面及消费适配。

仅历史已有或外部提供的能力不为了承载依赖而创建虚假 Story；通过 Task/Story 的相关依据与备注保留关联。只有本期公共变化也形成 Story 时，才用上述模型内依赖。

代码检查关系端点存在、方向合法、重复记录和悬空引用；agent 判断是否实际漏依赖、重复建设或遗漏交付责任。关系不是程序自动重跑的传播规则：修改一个提供方只触发读取消费者索引，是否写入取决于本次具体变化。图中有业务相互依赖也不等于工作流死锁。

## 3. 身份、名称与修改

| 变化 | 身份处理 | 必需同步 |
|---|---|---|
| 改标题/描述，含义不变 | 保留 ID | Excel 名称关联与投影位置；问题仍按 ID 定位 |
| 补值、改档位、纠正局部 AC，义务仍相同 | 保留 ID | 字段依据、问题、受影响派生结果 |
| 同名不同对象 | 不合并，不以名称做内部外键 | 导出时生成可辨名称；反馈时显示归属上下文 |
| 拆成几个独立交付或合并为新的交付 | 新 ID，记录 lineage | 原 AC、来源、问题和依赖都有明确去向 |
| 删除/退出本期 | 当前数组删除，历史版本保留，lineage 说明退出 | 无孤儿引用；不能靠“关闭问题”删除未解决义务 |

ID 不编码 Excel 行号、生成片号或固定业务类别。Example 使用短 ID 便于阅读；新生产对象使用本地 Python 标准库生成的 UUID4，agent 写候选时可一次生成本片所需 ID，后续保留已有身份。工具检查唯一性和引用，不按标题重新算 ID，不新增中央 ID 分配服务或逐对象领号步骤。

[D05](D05-clarify-and-change-scope.md) / [EX05](examples/EX05-clarify-changes.md) 细化拆合：父项变化但义务未变的 Task/AC 可保留自身 ID；实质变化才新建。lineage 的 from_ids 必须在 from_version_id 中存在，该版本须为已应用的前序版本；新去向在该次候选中合法，后续再次退出须有明确后续去向。继承旧 lineage 保留原版本定位，拒绝循环或无法解析的去向，避免扫描全部历史。版本 manifest 保留这些历史引用的可达依赖，不能只留下无法读取的 ID/哈希。

`projection.json` 随 Excel 自动产生，保存对象 ID → Sheet/Table/输入行/实际显示名，以及投影器版本。它用于“第 8 行”的反馈定位和同版复核，不是第二份业务模型，不保存估算权威。[D06](D06-excel-projection-and-delivery.md) 第 3/7 节定义别名分配、版本绑定、逐字段位置、独立问题和长文本定位；所有实际显示名能唯一反查本版 Story。长标题/AC 的显示分段不修改原文或身份。用户手改后的位置不再自动可信，需按补充输入核对。

## 4. 原件、依据与轻量分析

### 4.1 原件登记

一个物理输入版本记录 `input_version_id`、`input_id`、`content_hash`、`relative_path`、`format`、`material_types`、`uses`，资源包增加 `resources` 清单和包摘要。`input_id` 表示逻辑材料，版本 ID 表示不可变内容。新增用途不改变原件字节，但形成新的用途分析记录。路径必须在项目输入区内，拒绝越界或隐含跨插件依赖。

一份文件含多个角色/用途区域时增加 `use_regions`，每项记录 `material_type`、`use`、`locators`；同一物理版本不复制成几份原件。区域无法确定时不得把角色标签算成已覆盖内容。单文件可以提供 PRD/HLD 两类清楚可分的内容，必需角色是否齐备及内容是否充分仍由 agent 判断，见 [D03](D03-input-analysis-and-exploration.md)。

`uses` 区分 as-is 基线、to-be 范围/架构/交互/辅助 draft，以及独立规则与模板。往期 SOW 构建 as-is，其余项目材料用于 to-be，用户明确答复按适用范围更正。一个 Excel 的历史和 draft 区域分别分析，不能整份都算 as-is 或都算本期需求；旧标准不得替代内置模板。非原型输入限定可读文本（默认 Markdown）和 `.xlsx`，不支持 PDF/DOCX、扫描件或自动转换，见 D03。

材料“已登记”“已读取”“某用途分析已覆盖”不是同义。读取结果保留可用区域、未读/失败区域及原因；PRD/HLD 没有输入就不能以一个用途字段假装已齐备。

### 4.2 依据记录

每条必要依据含 `id`、`kind`、`text`、`source_refs`、`basis_refs`、`limitations`。`kind` 为：

- `statement`：原文直接表达的事实/要求；文本可忠实归纳，不能改变限定条件。
- `observation`：实际浏览或读取观察到的现象；记录页面/资源版本和观察限制。模拟成功不等于生产能力存在。
- `judgment`：跨来源关联、范围归纳或专业判断；`basis_refs` 指向已知依据/已应用决定，不能标成原文直接陈述。

非判断记录至少有一个来源；判断至少有一个可追溯依据。未用字段为空数组或空字符串，不创建置信度分数。`source_refs` 含 `input_version_id`、`locator`、`excerpt_hash`；locator 由格式适配器定义，例如 Markdown 的标题路径+行范围、Excel 的 Sheet+区域、原型包内资源路径+可定位元素/观察附件。行号只是该版本的定位，不跨版本复用。

首轮定位种类、最小字段和摘录摘要算法由 D03 第 4.2 节定义：`text_lines`、`xlsx_range`、`observation`。读取附件必须绑定原件、适配器/选项及 read_id；动态观察绑定原型版本和不可变 observation_id，不用静态 HTML 哈希代替运行结果。观察及必要附件进入版本的依据清单；完整性校验不等于证明实际业务行为正确。

EX01 的依据 EV-H-D1 可写为：

```json
{
  "id": "EV-H-D1",
  "kind": "statement",
  "text": "单一资料域、14 字段一对一迁移，允许整体回滚；记录条数未提供。",
  "source_refs": [{
    "input_version_id": "H1",
    "locator": {"kind": "example_block", "block_id": "H-D1"},
    "excerpt_hash": "<由工具计算的摘录摘要>"
  }],
  "basis_refs": [],
  "limitations": "记录条数未知；本期责任还需结合 A1。"
}
```

`example_block` 和尖括号摘要仅用于本设计样例，不能在正式候选中当成已验证 locator/哈希。后续格式适配器只接受实际支持的定位类型。

### 4.3 主题索引与最小提取

主题记录保留 `topic_id`、标题、相关输入版本/用途、已覆盖与未覆盖区域、关键依据 ID、相关模型对象/外部责任说明、未解决限制。索引指向按主题保存的不可变分析版本；用于检索的 index 可以重建，不是当前业务真相。

每份不可变主题版本使用 `topic_version_id`；物理读取覆盖与用途分析覆盖分别记录，不展开为每句原文或每个单元格的状态机。覆盖可按章节/区域集合表达，三个需求视角也不要求与所有区域形成一张逐项交叉表。原型观察为技术依据工件，按需保留，不增加新的业务层级。

As-is/to-be/gap 的必要结论与匹配范围保存在上述主题和 `judgment` 中；历史的可复用最小内容按下节条目索引保存，不重建完整历史 SOW。匹配判断区分实例适用已明确、有相关候选、无相关候选和读取/基础未解决，记录目标、候选条目、相关历史范围及限制；类型相同不是实例适用依据。D07 的读取集合保留实际查询范围和不可变版本；后续串行请求增加历史材料时，只复核相关匹配结论，不维护并发冲突摘要。

只提取会被当前工作或后续修改使用的事实、冲突、结论和限制。EX01 需要查询行为、公共契约、迁移前提和交付责任四组主题；无需把 PRD 每个句子、API 对象或原型按钮都建成统一实体。说明文字可以保存在 Markdown，稳定引用落在小型 JSON 索引中。

### 4.4 轻量历史条目

按 D03 保存历史中明确表达且用于范围导航/匹配的条目，放在相应不可变主题版本的 `historical_items` 中，复用 analysis 索引，不新建全量资产管理系统。

| 字段 | 粒度与约束 |
|---|---|
| `id`、`label`、`description`、`evidence_refs` | 内部历史条目身份、原意标题/说明、可回查出处；描述可以为空，不能补造原文没有的承诺 |
| `level`、`parent_id`（可选） | 只保留确实能识别的 Epic/Feature/Story/Task 层级与父项；不明则不填，不要求四层齐全 |
| `type_hint`（可选） | 有依据的 API/页面/事件等类型提示，可空；不是必须匹配本期标准的 `standard_id` |
| `instance_facts`（可选） | 简短的已知系统、业务含义、契约或使用条件及相应依据引用；只记录原文已给信息，不建每类实例的必填规格表 |

已有 AC 可随来源回查；没有 AC 不创建空 AC 列表或问题。历史 Task 没有类型不触发本期标准缺值检查。条目只表达“历史写了什么”，本次是否能用仍由目标与历史的关联判断决定；一个 Story 描述足以指向候选时不必先造历史 Task。

初次保留范围导航；只对本期相关条目补充必要实例事实。多个历史来源可保留各自条目并在判断中关联，不按相似名称自动合并。层级、已知能力与说明允许不同深度，缺失历史细节不自动成为需要用户逐条补齐的问卷。

本期候选引用历史条目及对应主题版本，不将其作为本期模型的父对象。确认复用后仍只更新本期相关 Story/Task，不把历史条目复制到当前交付清单。被交付依据引用的条目/版本按 D07 留存。

### 4.5 复用与失效

| 变化 | 物理读取 | 语义分析 |
|---|---|---|
| 原件、适配器及读取选项均未变，增加另一用途 | 复用已读结构 | 只新增该用途所需分析；未读区域按需补读 |
| 同名文件内容变化 | 新输入版本，不覆盖旧件 | 对照变动区域及引用定位受影响主题；不能按文件名直接复用 |
| 读取器/必要选项改变 | 受影响格式或区域重新读取 | 比较新的结构/定位；旧定位无法验证的结论需要重绑或补读 |
| 用户回答补条数 | 原 PRD/HLD 无需重解析 | 新增回答证据，只更新迁移档位判断及相关问题 |
| 回答改变公共契约/本期责任 | 未变原件仍可复用 | 读取该契约、消费者及责任依赖，形成新的有限修改方案 |
| 新增或更正往期 SOW | 登记实际新版本，复用其他物理读取 | 检查相关 as-is/gap 和匹配范围，包括旧零匹配结论；clarify 只应用确认的对象/字段 |
| 摘要缺当前需要的细节 | 原件仍保留 | 定向读取原文并补主题；不全量重建 IR |

读取缓存键至少含内容摘要、适配器版本和影响读取结果的选项/资源包摘要；语义复用另核对用途及实际引用的依据/决定版本。缓存只是加速，缺失时可以补读；已交付版本引用的原件和必要依据不能当缓存清理。

## 5. 问题、答案与生效决定

`pending-items.json` 含 `schema_version` 和 `items`。每项字段见 EX01：`id`、`revision`、`question`、`targets`、`evidence_refs`、`current_handling`、`unestimated_work`、`status`、`resolution`。

`unestimated_work` 是布尔值，正常为 false；只表示“本期已有依据的某部分工作尚未形成可计量 Task”，不表示字段未确认或资料总体充分。为 true 的 open 问题必须指向 Story/Feature/Epic 的对象级目标（field=null），current_handling 说明尚未拆明的义务和保留范围。已知 Task 字段缺值由字段目标表达；默认 M、按新建出稿的复用问题、仅缺 AC 文本均为 false。机械检查不根据问句或备注中的关键词推断这个标记。

该标记服务范围覆盖说明和 clarify 定位：未拆明义务在独立待确认说明中可见；问题 resolved/superseded 后历史标记可保留。它不驱动任何金额、公式或估算完整性判断。含义改变、目标变化或 true/false 变化要提升 revision，并纳入 clarify 的写集合和确认。仍属大范围基础不足时按 D01 退出，不能靠 true 放行一个不可用 SOW。

无 Task 的非空 Story、仍有本期工作但尚无 Story 的 Feature/Epic，须有覆盖其缺口的此类 open 问题；空父项若实际无本期义务应移出当前模型并在分析中保留排除说明。已知 X/拆分条件不被默认 M 覆盖；有依据且有剩余轮次时有限拆分，仍无法形成合法 Task 则保留义务与工作缺口，不生成伪造档位的 Task。合法局部缺口能否带出仍由 agent 判断。

`targets` 使用稳定对象 ID + 字段名；问题影响整个对象时 field 可为 `null`，但分类空值必须有精确字段目标。一个问题可以覆盖多个字段；缺值问题可共同阻止字段定值，复用候选问题则允许目标字段已有新建值。已回答但未应用的答案仍在 work；current 的问题保持 open。

默认复杂度问题也使用同一结构，target 指向 `complexity`，`current_handling` 写明按 M 估算，问题可请用户确认 M 或提供调整意见/必要规模事实。同一 Task 的同一缺口只保留一项问题，共同缺口可合批并列明 targets。用户确认 M 后可保持字段不变、更新依据并关闭问题；指定 S/L 时记录为估算决定，不反向编造支持它的规模事实。Clarify 已有明确档位且本次没有改变其依据时保留原值，不借默认政策重置。

Generate 输入分析时尚无 Story/Task，问题先以来源和主题保存在 work，字段与处理见 D03 第 6.2 节；不预建假对象。实际生成后，把仍影响本期的局部缺口绑定到正式问题和准确字段，保留工作问题的去向；已回答项形成采用事实，有依据的排除保留说明。正式待确认项不接受以临时主题冒充业务对象，完整交付前必须核对这些缺口没有在绑定时丢失。

| 状态 | 含义 | resolution |
|---|---|---|
| `open` | 当前版本仍缺事实/决定或待处理 | null |
| `resolved` | 答案已随本次版本采用，目标已处理 | 决定 ID、应用请求 ID、简短处理说明 |
| `superseded` | 原问题因义务替换/退出或问题实质变化失效 | 替代问题或 lineage 引用、应用请求 ID、原因；不能冒充已回答 |

复用待确认使用现有问题结构：`targets` 至少包含有关 Task 的 `work_mode`，`evidence_refs` 指向具体历史候选和本期目标，`current_handling` 明确当前按新建出稿及待确认的实例/适用范围。一个候选影响多个 Task 时共用问题并列出各自目标；不能只因字段非空就关闭 open 问题。无具体业务关联的类型匹配不逐条生成复用问题。用户决定不用候选时，clarify 可在确认方案后保持新建并关闭问题；用户要使用时先明确实例/变化边界，按实际方案连同内容、分类和依据一起更新。

问题文字或目标含义实质改变时提升 revision，引用旧修订的答案要重新核对；单纯排版不改变语义。历史版本保留原问题快照。

部分答复采用后，仍有未决目标的问题保持 open，current_handling 明确已采用和剩余部分；不增加部分解决状态。若缩小 targets，提升 revision 并保留旧版本去向；问题实质拆成不同事项时原项 superseded，新项绑定实际目标。所有 open 目标必须在当前模型存在。保留的终态问题/历史决定引用退出对象时，必须通过 lineage 的 from_version_id 在确切旧版解析；这与当前引用缺失不同，不能凭“历史”说明跳过验证。删除义务本身不是已回答，按退出/替换记录 superseded，详见 D05。

`decisions.json` 含 `schema_version` 和 `items`；每项含 `id`、`kind`（`fact`/`scope_decision`，后者也记录用户明确选择的估算口径）、`text`、`evidence_refs`、`applies_to`，有替代关系再填 `supersedes`。回答原文作为最小必要的补充输入保留，决定记录采用了哪条事实及其范围；不要求保存闲聊。

Generate 分析后得到的明确 A1，可随用户已要求生成的初版采用，不额外要求批准 A1；clarify 的 A2 需待具体调整方案确认后与修改共同采用。模型引用依据 ID 或已应用决定 ID，解析时限定在本版本 manifest 所指的集合中。讨论草案不能通过更新全局 analysis/index 让当前版本提前读到新“事实”。

## 6. 候选检查的界限

| 机械检查，必须拒绝非法候选 | Agent 的必要专业检查 |
|---|---|
| 字段、枚举、唯一 ID、父引用、问题目标和依赖端点 | 业务/技术/交付范围是否遗漏，责任是否有依据 |
| 来源/标准行可定位，摘要/版本一致 | AC 是否忠实、有无限定条件或反例丢失 |
| 分类 null 与 open 问题、不适用标记一致；complexity 必须 S/M/L；工作未拆明标记/目标合法，非空字段允许复用或默认 M 的 open 问题 | 类型、计量单位、包含边界、模式/复杂度是否合理 |
| resolved 问题有同版解决依据；当前引用无孤儿，允许的历史引用通过 lineage 和确切版本可解析 | 公共建设、接入、内含核验是否重复计量 |
| 实际业务与元信息 diff 不越过确认范围 | 当前缺口能否隔离，是否已构成基础不足 |

机械检查通过只能表明合同可接纳，不证明内容正确。合法未知返回为可呈现的业务限制，不能驱动无休止的“修复必填值”循环。完整版本、确认和串行保存由 [D07](D07-tools-storage-and-recovery.md) 处理。
