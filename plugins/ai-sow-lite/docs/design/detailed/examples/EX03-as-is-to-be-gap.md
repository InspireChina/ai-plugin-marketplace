# EX03 · 历史条目、复用候选与本期实例

[D03 输入分析](../D03-input-analysis-and-exploration.md) · [D02 数据](../D02-shared-data-and-evidence.md) · [D04B 环路](../D04B-bounded-loops.md)

这是合成设计走读，未创建实际夹具、运行插件、生成 Excel 或测量 token。既覆盖历史实例明确的情况，也覆盖历史只有 Story/Task 简单说明的常见情况；当前 Task 的其他字段仍须按实际输入与模板判断。

## 1. 历史能读到什么，就保留到什么粒度

旧项目已提供 `prior-sow.xlsx`、`prd.md` 与 `hld.md`，无原型。下列历史条目只是材料原义的索引，内部 ID 不代表新增的本期工作。

| 历史来源 | 可保留的条目 | 缺失内容及处理 |
|---|---|---|
| W1 的“订单管理 → 订单查询” | Epic/Feature 标题及来源层级 | 不自动补 Story/Task |
| W1 的“订单详情查询”Story，说明为后台按订单号看详情 | Story 名称、说明及父项 | 无 AC，照常保留，不补造历史 AC |
| 该 Story 下 Task“开发订单详情查询 API” | H-ORDER，API 类型提示与来源；业务关联明确 | 服务归属、接口路径、权限/数据范围和当前适用条件未知；只作候选 |
| W1 的“向外发送订单状态事件” | H-EVENT，向外发送事件的类型提示与原文 | 发送/接收方、触发时机和契约不详，不能直接证明可用于本次 |
| W1 的“上线配套工作”说明，没有可靠 Task 列 | 范围/工作条目与原说明，类型为空 | 不强行分类为发布、部署或演练，不作为历史缺值问题逐条追问 |
| W1 的公共审计组件，有明确接口和使用边界 | H-AUDIT，已有能力的明确说明 | 本期是否使用它仍须看目标关联 |

只针对当前相关候选补必要内容；不先把全部历史重建成符合新 SOW Schema 的模型。旧标准和旧人天不成为本期规则。

## 2. 与本期目标对照，不能只对类型

P1/H1 明确本期查询订单所需的行为、返回内容和方案边界，但没有指定采用 H-ORDER；本期还需向外发送订单状态事件，已给目标接收方、触发及契约，但未说明与 H-EVENT 的关系。新建工作本身有足够依据，是否使用历史实例只是当前可以延期确认的事项。

| 对照结果 | 初版处理 | 原因 |
|---|---|---|
| 订单 API 类型与业务相近，历史实例是否本期可用未明 | 本期订单 API Task 按新建，附 P-ORDER | 历史有相关候选，不等于同一接口或适用于当前调用方/数据边界 |
| 两项工作都是向外发送订单状态事件，旧契约/接收方不详 | 本期事件 Task 按新建，附 P-EVENT | 类型相同不能证明发送方、业务时机、消费者与载荷契约相同 |
| 历史另有与订单无关的配置查询 API | 不列为订单 API 的复用候选 | 仅“都是 API”没有足够业务关联，不能制造长候选问卷 |
| HLD 明确本期沿用 H-AUDIT 的对应接口，既有契约已满足目标，仅新增调用处适配 | 公共建设不再计；消费 Task 按实际工作与标准判断接入复用或是否内含 | 实例及适用边界已明确，无需例行再问历史是否已交付 |
| HLD 明确修改某个历史订单 API，指明对应服务/接口和本次新增筛选 | 该 API 的变化按模板判断调整 | 不是通过相近标题猜实例，有明确目标关联 |
| 新订单看板在有关历史范围没有相关页面候选 | 页面 Task 默认新建，无复用问题 | 不能因为它调用已有 API 就把页面模式改成复用 |
| 历史发布方案属于上一版本，本期另有明确版本/组件/责任 | 本期发布准备按实际工作与模板判断 | 同名不等于同一次交付；不会因历史做过发布就省掉本次工作 |

只有确定具体实例适用于本期且无需变化，才在 gap 中扣除对应建设。候选仍未明确时保留本期新建工作，不同时创建“新建方案”和“复用方案”两组收费 Task，也不先算一个假定节省的人天。

如果本期目标、方案或责任本身缺失，新建也无法界定，则按基础缺口补料或局部缺值处理；不能用“默认新建”替用户设计。HLD 若明确禁止新建、只能改变指定旧接口，但未指明该接口，必须澄清这个输入约束。

## 3. 当前有值，也可以待确认

| 问题 | 当前处理 | 需要用户回答的内容 |
|---|---|---|
| P-ORDER | T-ORDER 的工作方式为新建；备注“当前按新建估算，历史候选 H-ORDER 是否适用待确认” | 是否在本期采用往期订单详情查询 API？如采用，请明确具体服务/接口及可用范围，或提供已有说明 |
| P-EVENT | T-EVENT 的工作方式为新建；备注关联历史候选 H-EVENT | 是否采用该历史订单状态事件？需明确其发送/接收关系、业务触发和契约与本期的关系 |

这些问题默认随 Excel 交付；没有必要为每个候选开一轮问答。若一个明确历史候选同时影响多个 Task，共用一个问题并关联全部真实目标；业务上不同的 API/事件不能因同属订单主题而套用同一个答案。

保存使用已有 pending 结构：`status=open`、`targets` 指向相应 `work_mode` 与必要对象、`evidence_refs` 关联目标和历史候选、`current_handling` 解释当前新建口径。问题不因字段非空而关闭；新建口径也不写成用户已经批准的决定。

其他分类有依据时模板可以计算当前新建口径的人天，工作簿内待确认说明和 Excel 备注内部链接保持可见。复杂度无法识别按默认 M 并另附问题；类型/必要集成属性等真缺值继续留空并列问题，插件不干预模板对这些输入的计算结果。没有用户答复，插件不会后台继续查找候选、等待定稿或自行换模式。

## 4. Clarify 确认实例后只调整相关切片

用户回复 P-ORDER：本期使用既有订单服务的详情查询接口，已有返回满足目标的大部分要求；本次增加输入中定义的状态筛选，明确调用方、权限和数据边界可沿用。该答案解决实例与适用范围，不等于直接批准一个尚未展示的修改方案。

Agent 合并相关输入，提出可审阅方案：T-ORDER 工作方式从新建改为符合标准的调整，名称/备注及实际工作内容限定为本次变化；复核复杂度、包含验证和相关 Story AC，保留仍适用的原义与 ID；同步分类依据和 P-ORDER 状态，模板生成新 Excel。只读订单查询及真实受影响的调用方/依赖，事件、看板和发布工作保持各自依据。

用户确认该具体方案后应用。若用户决定不采用历史 API，则方案可保持新建、记录不用候选的决定并关闭问题，不重新拆全案。如果用户只说“应该能复用”，仍没有足够实例/适用信息，不把问题关掉；按 D04B 的一次合并补充/修订机会讨论，到限保留原 Excel 和草案。

补进一份此前遗漏的历史 SOW，也可能影响原先无候选的新建判断。通过原判断保存的历史范围定位相关目标，形成候选或实例适用结论，不能因新文件含一个相近标题就自动改成调整，也不能只追踪已有正向匹配引用而漏掉原零匹配。

## 5. 环路走读

| 场景 | 批量与退出 |
|---|---|
| 历史只有粗粒度说明，补读一次仍无接口规格 | 保留候选，新建+待确认；不换关键词或逐 Task 反复探索 |
| 原型不断发现相同查询的其他入口 | 首轮代表性观察已足够则结束；新入口不自动产生新调查轮次 |
| 一个重要原型差异有明确新路径，但追加批次已用完 | 不再探索；可隔离则带问题，影响基础则列具体补料需求 |
| 首轮输入问题包只回答部分事实 | 合并仍必要且可回答的事项，最多一轮补问；不重复已答项 |
| 第二轮后仍缺本期方案 | 保留有效分析、列补料清单并结束，不再第三轮主动追问 |
| 第二轮后只剩 API/事件实例候选未定 | 按新建口径交付并带问题，不能因为问题 open 就再次提问 |
| 某候选涉及三项本期工作 | 一次来源阅读、一个具体候选问题关联三项目标；答案只复核这些工作 |
| 中断恢复或更换 session | 复用有效文件、候选及已使用次数，不能回到第一轮 |

这些是设计期预期。后续用真实夹具验证历史粒度与来源、用专业样例验证候选/实例判断、用实际 diff 验证局部修改，并用宿主事件验证轮数继承和到限出口；不把文档走读当执行通过。
