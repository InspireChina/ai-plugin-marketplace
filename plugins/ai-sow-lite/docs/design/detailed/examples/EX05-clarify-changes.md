# EX05 · Clarify 的有限修改走读

[D05 详细设计](../D05-clarify-and-change-scope.md) · [EX01 基线](EX01-generate-clarify.md) · [EX03 历史实例](EX03-as-is-to-be-gap.md) · [D07 保存](../D07-tools-storage-and-recovery.md)

下列是合成设计分支，各自从指定基线开始，不串成一份逐渐变化的项目。名称/ID 用于讲清前后差异，未创建真实项目或执行 Excel/插件测试；用户答复也是样例输入，不能当作真实客户事实。

## 1. 默认 M 的确认，不改变 Task 工作量口径

基线为 EX01 v1：T-06 迁移复杂度为默认 M，P-01 open，S-04/AC-06/T-06 已有明确的迁移资产及内含核验边界。本次用户只回复“P-01 就按 M”。

Agent 不再问条数，也不查生产数据。读入 T-06、P-01、有关默认依据和版本身份后给出方案：保留 M，将其依据更新为用户采用 M 的估算决定，关闭 P-01，更新同版 Excel 的问题说明；迁移工作、AC 和分类以外的字段保持原样。

| 计划内容 | 具体值或范围 |
|---|---|
| `changes` | T-06.complexity 保持 M；classification_basis 中 complexity 的默认说明改为用户估算决定；P-01 open → resolved；新增 D-M |
| `read_set` | v1、T-06、P-01 当前修订、原默认依据和模板对应标准；S-04 简要归属 |
| `write_set` | T-06 的 complexity 分类依据、P-01.status/resolution、D-M；不写 Task 六项专业值 |
| 回查 | 起点层 2，采用本次层 0 答复；最大深度 2，源仅为本次答复与已定位原依据 |
| 结果 | 确认前 current/P-01 不变；确认后新版本的 M 与原版相同，问题关闭、依据可追溯 |

用户随后说“按这个更新”，即可应用，不需要再批准 Excel。若用户只问“M 是什么意思”，返回模板标准及当前默认处理，不关闭问题；若 current 已经采用同一答复，则说明已处理并返回已有文件。

用户直接提出 S/L 时同理记录估算决定；不能为其编造条数。若输入已有明确 X/拆分事实，则先说明与标准的冲突，不能用任意档位隐藏超界工作。

## 2. 一次多条意见，部分执行与部分答复

### 2.1 已展示的独立子集

仍从 EX01 v1 开始，用户同时提出“迁移按 S”以及“公告查询 Story 的标题改为‘查询公告列表’，只是改名称”。Agent 一次准备两个明确改动：A 为迁移档位/依据/P-01/新决定，B 为 S-02.title 与相应改名依据/决定。其他义务不变，两组没有语义依赖。

用户看完说“只执行 A，B 先不改”。A 的前后值、读写集合和问题处理已经完整展示，因此直接形成 A 子集计划，用这条明确执行消息确认，不再问一遍“是否确认只改 A”。B 留在工作草案，不能变成已经生效的待确认项或已采用决定。

应用采用当前完整模型，只改 A 的明确集合，S-02 的标题保持原值。不是从讨论中的 A+B 候选直接提交；工具必须证明实际 diff 恰好是 A。已具体展示且闭合的子集提取无需新一轮专业修订；如果必须改值、重新判断义务或扩大范围，则计入 D04B 的唯一一次修订，用尽后保存草案退出。

反例：A 是删除公共实现，B 是将消费者改为采用已明确的外部能力。只删除 A 会使原义务或依赖不成立，不能把用户“只执行 A”视为闭合方案；需展示改变/退出哪些消费义务才能成立，并在剩余机会内讨论，否则不应用。

### 2.2 一道问题只回答部分目标

本分支额外定义一个合法基线：P-SCALE 同时询问两个独立迁移 Task TA、TB 的档位，二者当前都按默认 M 出稿，源目标/责任均已足够。用户仅确认 TA 按 M，TB 暂不回答。

方案只更新 TA 的估算决定和依据。P-SCALE 仍 open，`current_handling` 写明 TA 已采用 M、TB 仍默认 M 待确认；若将 targets 缩小为 TB 的 complexity，则提升 revision，旧范围保留在原版本。不会出现“已解决但 TB 仍缺答案”的状态，也不把 TA/TB 两项工作重新拆一遍。

后续用户拿旧修订回答“剩下那个按 S”，先核对它确实仍指 TB；不能因旧问题曾覆盖两个目标就同时修改 TA。若其中一个 Task 已拆分，先展示新对象去向，不能把答案广播到全部新 Task。

## 3. 修改 AC，以及拆分 Story 但保留独立 Task

### 3.1 局部 AC 更正

基线为 EX01 v1。用户补充：“资料页手动重试必须使用用户最后一次提交的查询条件；仅补清这条验收含义，API 契约不变。”

具体候选在 AC-02 保留统一失败提示与迟到响应规则，补入上述重试条件；引用本次答复。T-01 的相关工作说明/依据同步限定这一行为；T-02/API、公告页及公共客户端只有在实际接口义务改变时才写入。本例输入已明确 API 契约不变，不能为一条 AC 自动新增“重试功能 Task”并重复计量。

若在读取公共契约后发现客户端并不支持所需参数，必须在确认前把公共变更纳入方案或列具体缺口；不能先展示“只改 AC”，应用中再无声改 T-05。只有资料支持的分类才保留；本次变化无法定档可在方案中明确 M＋待确认。

### 3.2 将页面与 API 作为两个独立交付 Story

此分支重新从 EX01 v1 开始。用户的新增输入为：“资料查询页和资料查询 API 分别验收。页面保留原查询、重试、迟到响应规则；API 按原 HLD 约定条件查询并返回约定数据，现有权限及数据范围不变。工作内容和承担方都不改变。”

Agent 展示如下具体拆分候选：

| 原对象或义务 | 新去向 | 身份处理 |
|---|---|---|
| S-01 查询资料 | S-11 查询资料页面；S-12 提供资料查询 API，均属于原 F-01 | 两个新 Story ID，退出 S-01 |
| AC-01/AC-02 的页面验收 | 移至 S-11，原意和原文不变 | 保留 AC ID |
| 独立 API 验收 | S-12 下 AC-08，内容来自本次答复与原 HLD | 新 AC ID，不复制页面 AC 冒充 API 验收 |
| T-01 页面及公共客户端接入 | `story_id` 由 S-01 改为 S-11 | 保留 Task ID、名称与分类，工作未变 |
| T-02 资料查询 API | `story_id` 由 S-01 改为 S-12 | 保留 Task ID、名称与分类，工作未变 |
| S-01 使用 S-03 公共客户端 | S-11 使用 S-03 | 原端点实质替换，创建对应新依赖并记录原关系去向 |
| S-01 对 S-04 的资料可用前提 | S-12 依赖 S-04；S-11 使用 S-12 | 按原数据链路与新责任边界明确重接，不笛卡尔复制所有边 |

其他 S-02/S-03/S-04/S-05 及其 Task 均保持内容和身份。S-03/S-04 是有关读取端点，不因此自动进入业务写集合。F-01 继续容纳两个 Story，Epic/Feature 无需重建。

方案写集合包括 S-01 的退出、S-11/S-12 的完整内容、AC 迁移/新增、T-01/T-02 归属、新旧依赖、拆分依据/决定以及 lineage。AC 内嵌 Story，实际父对象 diff 也必须包含；不能以“AC ID 没改”漏掉父数组变化。

lineage 记录 `from_version_id=v1`、`from_ids=[S-01]`、`to_ids=[S-11,S-12]` 及拆分依据。关系替换也记录可验证的旧端点去向。已有历史决定若适用于原 S-01，其历史目标可以在 v1 精确核对；它不自动变成对新增义务的批准。

如果基线额外存在指向 S-01 的范围问题，拆分使原问法失效，应按方案将它 superseded，必要的新问题分别绑定 S-11/S-12。保留的终态问题通过 lineage 定位历史目标，所有仍 open 的问题必须绑定当前对象。

Task 没增加，人天权威仍是模板；Story 名称、任务列表、SIT/UAT 和汇总按新归属重算。不能承诺任意拆合后的取整结果一定相同，更不能为了保持总数手工改公式。公式差异由 D06 验证，业务检查确认没有重复工作。

## 4. 公共技术能力与消费适配，只改真实受影响方

重新从 EX01 v1 开始，用户给出明确的新技术要求：“公共客户端增加一个可选取消接口，调用后取消该次请求并忽略其迟到结果；仅资料页新增取消入口。原四个接口保持兼容，公告页保持原有行为。公共客户端和资料页这两项按 M 估算。”

| 处理 | 对象及具体范围 |
|---|---|
| 公共建设 | S-03/AC-05 增加有来源的可选取消契约；T-05 继续承担唯一公共实现和内含验证，复杂度 M 引用用户估算决定 |
| 消费适配 | S-01 增加来自本次答复的取消验收；T-01 增加页面入口/调用适配，复杂度 M；不重复建设公共实现 |
| 只读且保留 | S-02/T-03 的消费边界：旧接口兼容，公告无新入口；API、迁移与发布无本次变化 |
| 问题与决定 | 有关新增事实/估算决定只作用于上述对象；其余 open 问题继续保留 |

T-01/T-05 在本期原计划中是新建工作，本次只是修改尚未实施的 SOW，as-is 没变，所以仍按新建。不能因为“我们修改了 Task 内容”就把工作方式改为调整。只有用户或材料提供了实际现状变化，才重新判断实施模式。

回查最深为层 0 的本次答复及有关原契约，层 1 只更新这一公共能力/消费边界；写集合涵盖上述具体字段，不含公告、API 或交付工作的重新拆解。

反例：用户后来改成“原接口也废弃”，则公告消费受到影响，原确认失效。若尚有一次修订机会，批量列出实际新增对象和深度重新讨论；已用完则保存候选并退出，不从公告一路递归重开全案。

## 5. 交付条件与历史输入

| 分支 | 处理与有限范围 |
|---|---|
| 用户更正发布窗口，仍为单组件/单团队，六步规范及生产执行责任不变 | 只更新 S-05/T-07 的有关方案内容/依据及采用决定；引用迁移结果的义务不变，不因此重做迁移或新增部署执行 Task |
| 用户要求把整体回滚改为持续双写，但没有同步/切换/冲突处理方案 | 本次修改基础不足，批量索取必要 HLD/责任说明。原迁移资产、查询前提及发布候选暂不改，不先编一组双写 Task 或用 M 代替方案 |
| 用户补往期订单 SOW，命中原先按新建的查询 API | 使用 EX03 的历史范围与目标索引定位，包括旧零匹配；实例仍未明则保留新建并提出具体候选问题。实例和本次变化明确后，方案才改有关工作方式/内容/依据 |
| 用户确认已有 API 完全满足且无需本期建设，仅有调用适配 | 方案删除本期重复建设，保留有依据的消费工作；原问题按采用/退出语义处理，lineage 保留删除出处。不是把历史 Task 搬入本期后再计一次 |

这些分支只处理输入实际触及的业务、技术、交付义务；发布窗口变化不代表所有引用迁移的 Story 都需要改，双写影响深也不代表允许无上限探索。

## 6. 旧反馈、竞争与失败发生在哪里

| 事件顺序 | 预期结果与恢复边界 |
|---|---|
| 用户引用 v1 第 8 行，current 已因拆分出现不同的第 8 行 | 从 v1 的 Sheet/projection 还原对象，再看 current/lineage；若一对多，展示候选让用户定位，绝不直接改 current 第 8 行 |
| P-01 已采用 S，用户重复发送相同事实 | 返回当前采用依据和文件，不再次生成人天或关闭另一问题 |
| 候选已试算，确认前另一请求只改公告备注 | 核对本次读依赖/语义不变，可保留确认并对新 current 重建本片；旧完整 Excel 已缺公告修改，不能直接作为新结果复用 |
| 候选已试算，但模板或有关 Task 已变化 | 金额/候选失效，解释具体差异，在剩余修订机会内重讨论；不拿旧人天诱导确认 |
| 方案承诺 M→S，实际候选写入 L | 即使字段仍在 write_set，也拒绝；能按原方案定向纠正才使用剩余返修次数 |
| 确认后 Office 重算失败 | 当前版本保留；有明确修法才重试失败步骤一次，不重新提取资料或重拆 Story |
| 完整候选就绪但未切 current，宿主中断 | 候选仍未生效；续接先核对实际状态、取消/确认/基线和已用次数 |
| current 已切换但响应丢失 | recover 返回该请求已应用版本；若后来另有更新，不能倒回该版本覆盖 current |
| 取消发生在实际生效后 | 说明已经更新；若用户需撤回内容，从最新 current 形成有限修改，不回滚全部后续版本 |

检查允许对本版所有 ID/引用进行廉价校验；专业阅读仍限于本片和真实依赖。旧坐标、历史目标与全局校验不是全量语义重跑的理由。

## 7. 如何验证，不把走读当运行结果

后续交互夹具覆盖用户只给事实、确认 M、指定 S/L、部分选择、歧义目标和取消；合同夹具覆盖前后值、拆合身份、历史 lineage 定位、open 问题当前目标及无关字段保留。Excel 沿 D06 验证归属、SIT/UAT、取整、试算与缓存失效；保存故障沿 D07 注入。

性能对照至少包括：默认 M 的问题关闭、一个分类改变、两个原片中的小修改、公共能力一建多用、需要补输入才能闭合的修改。记录首次有用回复、具体方案、确认后应用的耗时和真实 token，以及读取/回传量、修订数、Office 次数；本例不预填秒数、token 或人天收益。

对应 D09 中 CL01—CL29、AN08、FS03—FS08/FS15—FS16 和 X02—X06。案例只给出业务条件、必须保留的边界及失败出口，不要求真实 Agent 逐字复刻此处的标题或固定动作顺序。
