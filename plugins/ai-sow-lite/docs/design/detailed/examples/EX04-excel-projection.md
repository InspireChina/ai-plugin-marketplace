## 1. EX01 初版：迁移复杂度默认 M，直接出稿

EX01 v1 有 3 Epic、5 Feature、5 Story、7 AC、7 Task。资料条数不足以识别 T-06 的复杂度，直接填 M，P-01 针对 complexity 保持待确认；不回头搜索或追问条数。公共建设 T-05 只计一次。

| Story | 01 表行 | F：SIT / G：UAT | D / E / I 的关键预期 |
|---|---|---|---|
| S-01 查询资料 | 5 | 否 / 是 | D 保留 AC-01、02；E 引用公共客户端和迁移前提；I 可计算 |
| S-02 查询公告 | 6 | 否 / 是 | D 保留 AC-03、04；E 引用公共客户端；I 可计算 |
| S-03 交付公共查询客户端 | 7 | 否 / 是 | D 保留 AC-05；I 仅计 T-05，不叠加消费方工作 |
| S-04 承接历史资料 | 8 | 否 / 否 | D 保留 AC-06；E 引用 P-01；I 按 T-06 默认 M 计算 |
| S-05 编制本次发布与切换方案 | 9 | 否 / 否 | D 保留 AC-07；E 保留迁移核验前提；I 可计算 |

A/B/C 分别填写 EX01 的 Epic、Feature、Story 显示名，完整名称和层级不变。SOWStoryTable 为 A4:J9；七个 Task 写入 02 表第 5—11 行，TaskTable 为 A4:L11。

T-06 在 02 表第 10 行：C 为“历史数据迁移”、D 为“新建”、E 为 M、F 空白（不适用）、G 保留备注及“复杂度默认 M，见 P-01”。J 按 M 计算，K 为真实 0。该类型不适用 SIT/UAT，与复杂度暂定无关。

04 表 P-01 的显示内容为：

| 内容 | 预期 |
|---|---|
| 编号 / 状态 | P-01 / 待确认 |
| 涉及内容 | 资料域迁移资产与核验：复杂度 |
| 待确认事项 | 当前默认 M，请确认或提供调整意见；也可补充资料条数等事实 |
| 当前处理方式 | 按 M 估算，未声称材料已证明 M |
| 来源定位 | EX01 H-D1/A1 的实际登记位置；本例不编造行号 |
| 已采用答复 | 空白 |
| 关联位置 | 02 表 E10，内部对应 T-06.complexity |

本例七个 Task 均可估算，汇总 B5/B7/B8 可有当前口径的完整人天，B6 为 0，C5:C8 留空。顶部明确“含 1 项默认复杂度待确认”，不把 P-01 当成未估算工作，也不把金额完整说成全部事实已确认。SIT 仍按集成 Task 计算支持人天；UAT 仍按适用 Story 下的 Task 原人天计取，不拿 Story I 的取整数再次计取。

## 2. Clarify：用户确认或调整默认 M

用户 A2 提供 8 万条且其余条件不变，方案 CP-01 把 T-06 从默认 M 调整为 S，更新依据、关闭 P-01并记录决定。用户确认具体方案后应用。

| 阶段 | 文件结果 |
|---|---|
| 收到 A2，还在讨论 | v1 的 E10 仍为 M，P-01 仍待确认 |
| 方案确认且 apply 成功 | E10 为 S；T-06 J、S-04 I、项目 B5/B8 按模板更新；P-01 已解决 |
| 用户直接确认 M 可用 | 值仍为 M，只更新其估算口径确认、问题及相应版本说明，不为补条数继续追问 |
| 用户指定改 S/L | 如当前没有已知标准冲突，记录为用户估算决定，展示有限方案；不编造规模事实证明该档位 |
| Office 失败 | 保留候选和 v1；仅恢复导出，不重拆其他 Task |
| apply 成功但响应丢失 | recover 返回已成功版本，不重复重算/应用 |

对象数量、行顺序、名称和 ID 不变；SIT/UAT 金额在本例不因迁移档位调整而变化。实际业务写范围仍只有确认的字段、依据、问题与决定。

## 3. EX03：新建非空且复用问题 open

这是一份独立候选变体，不往 EX01 偷加订单需求。EX03 的 T-ORDER/T-EVENT 分别有具体历史 API/事件候选，但实例适用未明；当前按新建出稿。若各自类型和必要集成属性有依据，复杂度已有判断或采用默认 M，则 Task 人天照常计算，P-ORDER/P-EVENT 保持 open。

备注必须能读出“当前按新建估算；历史候选尚未确认适用”，问题表展示候选与待确认事实。若全项目其余估算输入也完整，B 列可以有完整人天，顶部仍显示含复用待确认；C 不重复列一份新建或假想复用成本。

若 T-EVENT 同时缺必要集成类型，则其开发人天可以已知，SIT 和项目总量仍不能完整计算。这项缺值与复用问题分别指向真实字段，不能因为 D 列新建已填就关闭两项问题。

用户明确指定历史 API 且说明需新增过滤条件后，clarify 检查实际内容、模式、复杂度及相关依赖，给出具体方案。不能只把“新建”替换为“调整”并自动沿用旧档位。

## 4. 名称和长内容变体

两个不同 Feature 下恰好都有名为“查询订单”的 Story：

- 初次生成时按稳定 ID 分配显示名；遇到冲突的对象使用可辨身份后缀。每个 Task 的“所属故事”取同一映射结果。
- v2 新增同名 Story 时优先保留 v1 原对象别名，只给新增对象分配未占用别名，不因此改原 Story 的业务标题。
- 名称为 `查询*?~订单` 时，UAT、任务列表、故事人天、故事校验和项目 UAT 金额都按字面关联；不能只验证 SIT/UAT 两列。
- 超过关联显示上限的名称变为短显示名加身份后缀，完整名称可在续页读取；AC/备注过长同理。原模型内容及 AC ID 不变。
- 名称或 AC 以 `=SUM(...)` 等字符串开头时仍是文本；安全写入不能靠改变原文或名称父键来实现。

原始 F 单元格只有局部可读内容时必须有明确的续页入口。续页全部片段按原顺序重组后与源字段相同，回链、projection 的片段坐标及最终文件一致。任务清单很长时，缩短的是列表显示，不是 TaskTable 的计量行。

## 5. 必须提前区分的失败

| 变体 | 预期出口 |
|---|---|
| 复杂度无法识别，其他分类齐备 | 默认 M 并附待确认，可以计算；不回查补证，不伪造规模 |
| 已知适用 Task 与未知类型 Task 同属一 Story | UAT为是，但该 Story 人天和 UAT支持不完整；未知 Task 不能从总量消失 |
| 所有 Task 都无法计算 | 汇总不可用，说明真实缺项；不显示“已知部分 0”；若已是基础严重不足，D04 在导出前退出 |
| 没有本期 gap，来源和责任已足够 | 明确无新增工作，空数据区与真实零汇总；不生成虚假 Story/Task |
| 只有空骨架，实际范围未知 | 返回输入不足，不沿用“无 gap”的零估算出口 |
| 第 61 个 Story、第 201 个 Task | 正常一次扩表；新增/末行公式、数组 ref、校验、保护和打印都覆盖 |
| 计算后又修改公式或普通保存导致缓存丢失 | 原实算记录不能证明最终文件；定向处理并计入修复次数，失败不激活 |
| 模板规则或投影版本变化但数据路径相同 | 原缓存不适用；检查新身份和兼容原型，不能按路径直接复用 |

验证要先落可执行的 Excel 差异夹具，再接 generate 的专业全流程。D09 将“走读预期”“既有模板通过”和“Lite 投影实际通过”分开记录，不用本文件代替实算或原生打开证据。
