## 2. 优先吸收的专业方法

现有设计已确定三类需求、来源 AC、公共能力单计、稀疏 as-is 和有限修改。下表补充具体判断边界，由 Agent 在现有活动内使用；代码只检查可确定的数据与文件约束。

| 主题及旧资料 | Lite 应吸收的方法 | 对应位置与成本控制 |
|---|---|---|
| **NFR 与独立技术能力**：`technical-work-classification.md`、`story-authoring.md`、`acceptance-criteria.md` | 性能、安全、审计等目标不自动成为技术 Story。业务触发约束落到实际适用 Story 的来源 AC；有依据的独立公共能力才单列建设，消费者只承担自身功能/适配。项目级约束保留在主题、依据或备注，不能因不单列 Story 而丢失 | [D04](detailed/D04-generate-and-context.md)、[I2.2](implementation/P02-generate.md)。与骨架/片内生成一起判断，不新增 NFR 实体或分类轮次 |
| **交付范围与责任**：`delivery-work-classification.md`、`delivery-decomposition.md` | 主动识别迁移、演练、上线准备等输入义务；区分本期成果、外部依赖和普通实施活动。迁移脚本、演练资产、生产执行只有确属不同责任和标准单元时才分别计量 | D04、I2.2、[I4.2](implementation/P04-scope-and-performance.md)。按既有输入合批确认责任，不套默认交付清单 |
| **层级与 AC 语义**：`epic-authoring.md`、`feature-authoring.md`、`story-authoring.md`、`acceptance-criteria.md` | 按目标与交付边界组织层级，不按章节/页面机械建树。保留来源中的角色、触发、阈值、时限、否定/排除及异常条件；AC 与所在 Story 的行为一致。正常/异常分支通常在同一结果下表达 | I2.2 的 `references/generate-slices.md`。不增加最低子项数、Task 上限、逐条 AC→Task 或逐字匹配校验 |
| **标准单元与模式**：`task-authoring.md`、`stage3-task.md`、复杂度标准设计 | 看当前模板行的单位、交付物、包含边界和模式说明。底层平台存在不等于本次形成的业务对象是复用；调整看实际变化与必要回归，接入复用看项目侧适配。普通使用现成能力不自动产生收费 Task | I2.2。相关标准按片合批读取；确有歧义才比较相邻类型，不为每个 Task 强制再开检索轮次 |
| **跨类型重复计量**：`review-task-estimation.md`、`repair-task.md`、复杂度案例复核 | 类型不同也可能计算同一成果；来源相同也不证明成果重复。重点看公共建设与消费者、集成与内部同步、迁移与核验、IaC 与普通配置、自动化资产与重复执行 | D04、I2.2/I4.2。生成时标明公共归属，合并时按关联成果核对；不增加全量 Task 两两评审或独立 Reviewer |
| **历史 Excel 语义**：`prior-analyze-v2.md`、`prior-consolidate-v2.md` | 表头、合并单元格、附注与跨行结构共同解释条目；分页边界不等于业务边界。目录/模板示例不等于历史交付；明确取消、排除或未来内容不进入当前 as-is。部分相同不等于整条历史重复 | [D03](detailed/D03-input-analysis-and-exploration.md)、[I2.1/I2.2](implementation/P02-generate.md)。复用读取，保留稀疏条目和限定；不补历史 AC/Task，不建合同状态引擎 |
| **原型观察可信度**：`prototype-analyze.md`、`prototype-scenario.md` | 区分静态代码表达、实际观察行为与未能观察的部分。点击成功不等于状态改变；类似控件不等于同一路径；Mock 页面不证明真实后端或历史实现 | D03、[I4.1](implementation/P04-scope-and-performance.md)。Agent 自选代表性目标、复用观察；不要求预枚举全部动作、逐项双跑或未发现即判不存在 |
| **错误归因与有限修改**：`candidate-repair-v1.md`、`fragments/roles/reviewer.md` | 分清输入缺事实、Agent 误读已有事实和程序结构错误；不能把后两类转成用户补料。合批处理兼容问题，保留未受影响内容；修改前展示具体范围和前后值 | [D05](detailed/D05-clarify-and-change-scope.md)、[I3.1/I3.2](implementation/P03-clarify.md)。直接使用 Lite 候选与差异合同，不迁入 repair slot DSL、Owner 回退链或复审收据 |

### 两个值得保留的判断例子

**NFR 的承载。** 输入要求订单查询在指定负载下达到给定响应时间，先把已有阈值与条件放入查询 Story 的 AC。仅有目标不能推导出新建缓存、监控平台或“性能治理” Story。HLD 若明确本期建设独立查询加速公共能力，才形成对应技术工作，业务侧保留真实接入工作。监控看板能测量响应时间，不等于已经满足响应时间要求。

**复用与重复计量。** 集成 Task 内部的落库同步，不能仅因标准表存在数据同步类型而再计一次。输入另有独立可维护、可验收的数据同步成果时才考虑单列；判定依据是本期实际成果与模板边界，不能只按名称或类型去重。

这些是判断方法。新增机制、责任和验收条件仍须来自本项目输入。

## 3. 需要舍弃或改写的内容

| 旧资料中的做法 | Lite 采用的边界 |
|---|---|
| `delivery-lifecycle-policy.md` 默认增加 SIT/UAT 自动化与上线义务 | 主动识别输入中有依据的交付需求。SIT/UAT 适用性由任务类型和 Story 公式得出，适用不等于采购自动化或额外执行工作 |
| Story UAT 由业务/技术分类或旧策略填写 | 只使用 Lite 标准及受保护公式；Agent 不填写或覆盖 |
| `stage3-task.md` 每个 Story 最多四个 Task，以及严格层级数量/命名规则 | 按来源、目标与模板单元拆解，不用数量或措辞门禁替代语义判断 |
| 复杂度资料要求“事实不足判 X、补证据、不默认 M”，或估算疑问全解决后才交付 | **仅复杂度无法判断时立即 M + 待确认**，不为定档回头调查；已明确超界/多实例则有限拆分或保留未估工作，不能用 M 掩盖已知超界。范围/方案缺失仍按基础不足或局部缺口处理 |
| 所有历史能力先证明当前存在，或固定缺失前提继续估算 | 稀疏历史作为估算 as-is；无候选默认新建，相关候选实例适用未定则新建 + 问题。不能猜复用，也不追加完整历史交付审计 |
| 完整义务 IR、多层历史汇聚、Owner 模型、来源派生 ID | 轻量主题/依据/历史条目和现有 SOW 模型足够。实施对象保留为分析视角，不新增实体或转换阶段 |
| 每阶段 fresh worker/reviewer、read allowlist、mandatory hydrate、checkpoint/seal 与审计闭环 | 保留单主 session 基线、按片专业自主和有限机械检查。原始资料按需可达，不靠反复“发现—返修—复审”推进 |
| 问题全部解完、输入变化重开全流程、每次导出逐页 PDF 加独立视觉 PASS、最终批准/定稿 | 合法未知随稿交付，反馈由 clarify 有限修改。视觉检查用于实现回归和实际布局变更，用户拿到 Excel 即可离开 |
| `runtime-environment.md` 的旧路径长度常量、旧参数环境与扩展解析依赖 | 迁入隔离环境、UTF-8、PowerShell/Bash 编码等适用经验；按 Lite 路径和平台测试，不直接复制旧阈值，不引入 PDF/OCR 等非首版依赖 |

旧资料自身也有适用条件差异：复杂度说明一处要求共享能力调整与接入分别验收后才拆，一处又写成必须两行。Lite 应保留成果边界判断，不能把整份文档视为一致的新规则源。

`Dev-TL全生命周期标准人天基准表_v5.4_讨论稿.md` 仅为历史链接占位；v6 权威依据文档也区分方法参考与组织内部参数。这些适合作为标准维护背景，不能证明人天、系数或全部阈值已获外部标准验证。

## 4. 示例如何转成早期验证素材

旧复现 JSON 包含 **3 个 Epic、11 个 Feature、22 个 Story、44 条 AC、59 个 Task**，另有公开来源记录和 **11 项示例既有资产假设**。它是带预期结果的投影数据，不能直接验证 Lite 从 PRD/HLD 自主生成的效果。

旧工作簿使用隐藏辅助列、旧 Story UAT 字段和公式布局。不能把它的任务数、金额、分类或缓存值直接作为 Lite 验收答案。建议改成合成夹具，并入 P02/P04 已安排的变体：

| 素材 | 需要验证的判断 | 最早消费者 |
|---|---|---|
| 业务 NFR 与独立公共能力的有/无设计对照 | 约束不漏；不凭目标创造方案；真实公共建设单计 | I2.2 三类需求 |
| 既有订单 API 与本期相似 API | 实例未定新建 + 问题；明确实例后才支持调整/复用/已满足 | I2.2 稀疏历史 |
| 集成、同步、核验、测试适配包交叠 | 同一成果不因不同类型重复计算；不同成果不因共用来源错误合并 | I2.2 共享工作、I4.2 |
| 跨行历史、附注、夹带标准表的往期 SOW | 合并/分页不改变语义边界；目录不变成资产；排除条件保留 | I2.1 读取、I2.2 分析 |
| 已知小范围但定档证据不足；已知多个独立实例 | 前者 M + 问题后继续，后者按已知边界有限拆分，不来回追问 | I2.2 默认值与环路 |
| 迁移开发、演练、上线执行及外部责任变化 | 按实际标准成果计量；一次答复只改变相关范围与派生输出 | I3/I4.2 clarify |

夹具把允许采用的事实显式写成可读 PRD/HLD/历史材料。示例假设只有作为**明确合成输入**才是测试依据，不能训练 Agent 自动补同类假设。继续使用开源事实时保留其来源边界；本次没有重新联网验证。

语义验收保留逐义务的期待与禁用推断，允许多种合理拆解。预制 projection 可用于迁入后的机械投影测试，但应与真实 Agent 输入隔离，不能把渲染准备好的模型当作自动生成通过。旧金额如需比较，先用当前模板和实际 Office 建立新的独立预期。

## 5. 如何吸收而不增加上下文和循环开销

沿现有实施计划的三个专业参考文件组织：

| 计划中的文件 | 应放的内容 | 使用时机 |
|---|---|---|
| `references/input-analysis.md` | 用途、历史表格、来源限定、候选与实例、原型观察边界 | 输入分析读相关段；原型细节只在有原型时读 |
| `references/generate-slices.md` | 三类需求承载、AC 语义、模板单元、模式、共享/交叠与未知出口 | 首次专业生成读取；后续片只带必要规则和标准行 |
| `references/clarify-changes.md` | 错误归因、具体修改方案、有限读写与未改内容保留 | clarify 使用，不重新灌入 generate 全部分析 |

复杂案例留在测试夹具/开发文档；Skill 正文只放入口、产物和必需边界。专业规则维护一份，不在 author/reviewer/repair 中重复。标准候选说明按片合批读取；原件和提取结果可复用就不重写；历史合并只提出新增关系或必要修正，避免重新生成全部条目。

以上是减少重复读取和输出的方向，不是已证实的 token 节省。仍按 [D08](detailed/D08-telemetry-and-performance.md)、I2.3/I4.3 测量首版时间、重读/重写/交互次数、语义覆盖及实际可得 usage，不增加资源预算审批或逐 Task 埋点调用。文件化与少读新资料也不会清空主 session 的历史上下文。

所有探索、补问、修订、返修与恢复共用 [D04B](detailed/D04B-bounded-loops.md) 的计数和出口；更多专业参考不构成额外调查、复审或延期交付的理由。
