# 03 · Agent 自主执行、上下文与必要检查

[返回总览](README.md)

## 1. 自由度放在哪里

两个 Skill 各自拥有清楚的目标和完成条件。专业活动的选择与顺序交给 agent；版本和文件的可靠性由小而明确的工具接口保证。共享文件协议不演变为串联所有专业动作的流程引擎。

| 由 agent 自主处理 | 由代码可靠执行 | 由用户决定 |
|---|---|---|
| 材料阅读顺序、主题划分、原型探索路径 | 输入与文件读写、来源定位和可得工具状态 | 材料外的真实事实及授权 |
| 冲突调查、范围分析、上下文取舍 | ID/父子关系/引用/必需字段检查 | 本期范围、交付责任和取舍 |
| Epic/Feature/Story/AC/Task 的拆合与措辞 | 复制原模板填值并调用 Office 保留模板结果 | clarify 的具体调整方案 |
| 按模板标准判断 Task 及解释依据 | 比较写集合与已确认方案的结构边界 | 是否接受改变原方案的范围扩张 |
| 选择值得追加的证据或针对性语义核对 | 一致提交、冲突检测、文件复读和埋点 | 后续是否再反馈 |

代码不试图证明所有语义影响都已覆盖。切片外的隐含依赖需 agent 判断；代码能验证真实改动没超出声明对象，不能靠 ID 集合证明业务判断一定正确。

## 2. 每个入口如何工作

**Generate** 开场完成两件事：确定新旧项目；按类型收集必要输入，包括 PRD、高阶设计和旧项目往期 SOW，原型可选，已有信息直接复用。分析全部输入时从往期 SOW 构建 as-is，从其余项目材料构建 to-be，主动识别业务、技术和交付 gap，包括 NFR 公共能力、业务接入、迁移和上线工作。分析后仅澄清和确认这些输入相关的事实、含义、冲突与决定；补足后由 agent 形成整体骨架，按片形成 Story/来源 AC、组织 Task 并完成四项定性匹配，最后按模板出稿。切片、拆解、分类与出稿不提交用户逐项审批；agent 自主选择切片粒度和片内工作顺序，专业步骤之间可以联合处理对象。

| 组织方式 | 必须保持的边界 |
|---|---|
| 整体骨架 | 表达业务/技术/交付 Epic/Feature，识别公共能力、接入方、交付责任与依赖；不提前写尽所有明细，也不把骨架永久冻结 |
| 分片选择 | 按业务关联、证据量和处理复杂度选择；强相关内容可以联合处理，大 Feature 可以拆片 |
| 片内工作 | 联合形成 Story 标题、来源 AC、备注，以及 Task 名称、四项分类和备注；必要自查后保存，工具调用顺序由 agent 决定 |
| 下一片 | 读取最新全局摘要、本片证据与关联对象，不重复注入所有已完成片全文；同一 session 的既有历史仍可能保留 |
| 跨片合并 | 对照三类范围检查遗漏、公共建设与接入的边界、交付责任和重复计量，复用仍有效的片内判断，不逐片重新做同样的语义审查 |

片内区分 AC 的验收结果与 Task 的实施工作，同时考虑它们的关联、材料约束及模板包含边界；不按 AC 数量机械拆 Task，也不要求先生成全部 AC 再开始 Task。分析“对什么做什么改变”融入当前工作，不额外派发实施对象任务或建立独立成果层。具体语义与例子见 [02](02-inputs-and-domain-model.md)。

识别非业务需求是 agent 的主动职责，不能等待用户提供已经拆好的技术或交付标题。NFR、迁移、切换、交接等只是帮助发现遗漏的视角，不是每个项目都要执行的默认清单；依照材料和责任判断独立建设、业务接入、局部约束、外部依赖或待确认。公共能力的工作定义足以界定使用边界后，相关接入片即可继续；这里只是在估算交付工作，不要求能力先真实开发完成。

首次生成的切片用于组织工作和限制上下文，不是必须逐片批准的修改权限。后续 clarify 的切片由本次反馈重新界定，可以只改原片的一部分，或包含多个原片中紧密关联的对象；仍须遵守已确认方案。

片内发现新公共义务或已有骨架不准确时，agent 先界定受影响的骨架元素、切片集合和必要回查点，再局部补正。已完成片只在相关依据、公共规则或语义发生变化时重新处理，不因骨架版本号变化而全部失效。超出可闭合范围或同因无进展时，按本次请求的异常出口处理，不自动扩大成全项目重写。

骨架来自 as-is/to-be 之间本期负责的 gap、责任与来源，分片按目标、证据关联、依赖边界和实际规模安排；不先生成全部 Story/Task 再按数量分割。具体来源、EX01 分片示意、执行方式及并发条件见 [D04](detailed/D04-generate-and-context.md)。

**Clarify** 从共享有效版本出发，先把用户反馈变成可评估的修改方案，再执行已确认切片。它不调用 generate 重走全流程，也不要求恢复 generate 的聊天或内部步骤位置。

两个 Skill 可以共用文件 I/O、模型检查、Excel 和埋点工具，不互相依赖私有执行步骤。是否抽公共库由实现复杂度决定，先避免重复计算口径和不一致的文件格式。

agent 的自由度受事实边界约束：不猜前提或方案，不新增输入没有的 AC；复杂度无法识别默认 M 并附问题，其他缺依据字段留空并记录。资料在分析后仍不足时按 D04B 的剩余轮次批量澄清，到限请求具体材料并退出，不能以“先出结果”为由跨过基础缺口。后期其他未知按留空处理；有相关历史候选但实例未定时工作方式按新建并附确认，既不强制清空，也不将候选当已确认。

## 3. 先分析单 session 的信息流，再决定上下文优化

默认分析一个 generate Skill 指导同一个主 session 完成全流程，不引入 subagent。逐步输入、产物、实际新进入会话的内容及历史累积见 [D04A 全景](detailed/D04A-single-session-panorama.md)。当前活动需要的信息包括：

- 本次目标和入口；当前有效内容版本。
- 全局范围摘要、公共责任、模板标准，以及必须保持的跨对象约束。
- 当前生成片或修改切片内的对象、待确认项、相关决定；尚未覆盖的目标和相关片的简洁索引。
- 必要证据摘录和原件定位；已经尝试的关键方法、失败原因及可复用结果。
- 当前交互位置：generate 是否已结束分析后问答，或 clarify 的方案是否已确认。

需要新证据时按定位补读，不在每一步重新注入所有原文、Excel、聊天和工具输出。上下文摘要不是完整推理日志，也不提前删除与当前判断有关的反例和限制。

轻量索引与提取结果按实际输入版本、读取方式和用途复用；材料已登记不表示已完整读取。片内发现摘要缺失相关细节时，只补读对应原文并更新关联结论，不要求全量重建中间表示。新增用途可能需要重新理解同一份内容，但不必重复已经有效的物理解析；来源或解释条件变化时再判断具体失效范围。

本片完成后把结果、证据定位、未决项和依赖写回文件，再缩减下一片新增的工作包。这不会自动删除同一会话的历史；真实压缩依赖宿主，独立子上下文须避免默认继承全部父历史。换上下文不能丢掉已完成覆盖或公共计量归属，也不要求用户为每片启动新聊天。

上述信息是本步需要的内容，不是实际上下文只剩这些内容的承诺。Agent 生成文件中的业务内容仍有输出成本；候选再被全文回显、全量合并后再次读回，会增加重复输入。全局覆盖核对也不能仅靠计数和标题，要能读到必要义务与关联明细。

先观察单 session 的成本，再减少重复读取/重写和冗长工具返回，验证宿主压缩后的恢复与质量。只有仍有明确瓶颈时才评估局部子上下文；并发再单独评估。备选边界保留在 D04，不把多 agent 设为完成首次出稿的前提。

## 4. 必要检查如何前置且不过度循环

提前识别失败条件，优先检查成本低、可能推翻后续工作的事项：

| 位置 | 提前检查什么 | 避免什么浪费 |
|---|---|---|
| 接收与全输入分析 | 必需材料、业务/技术/交付基础充分性、不可读内容、模板可用性、范围与责任冲突、相关历史基线读取缺口 | 到估算或导出才发现非业务范围遗漏或无依据 |
| 骨架与切片安排 | 三类范围覆盖、NFR 公共能力与接入边界、迁移/上线责任、共享依赖和合理分片 | 各片各自完成却整体遗漏或重复计量 |
| 片内联合形成 Story、AC 与 Task | 输入明确的业务结果、验收意图、责任边界及模板包含范围；AC 不机械映射为 Task，无来源 AC 不新增 | 按 AC 重复计量、先拆完 Task 再整体改范围或强造验收关系 |
| Task 判定 | 工作类型适用、as-is 匹配范围与方式依据（无候选新建，候选实例未定则新建+待确认）、复杂度标准或默认 M+待确认（不追加补证）、集成属性、共享计量归属及留空原因 | 擅自默认其他字段、掩盖缺口或再大面积返修 |
| clarify 方案讨论 | 变化是否闭合、跨切片影响、回查深度、用户决定点 | 用户确认后才发现实际要改全项目 |
| 跨片合并与交付前 | 骨架覆盖、跨片引用、公共义务、重复工作、分类输入、待确认项一致性、文件可读 | 用户带走损坏或误导性的 Excel |

已知的局部业务空缺是允许的模型状态。代码分别检查缺失、不适用与非法值；合法留空有明确待确认项，非集成任务的集成类型空白不误报缺失。模板“必填项缺失”提示需核对原因，不自动触发全流程失败；结构损坏和漏写已知值仍须修复。

形成内容时 agent 做针对性自查；代码执行可确定验证。另一个上下文的语义核对可以用于影响大、证据冲突或容易漏公共义务的部分，但不是每个阶段必配一个 Reviewer。核对范围和投入理由必须明确，结果只适用于其实际检查的内容。

专业意见分歧不触发无限“作者修改—Reviewer 重审”。先判断是明确错误、可并存表达还是业务决定：明确错误在局部修；可并存表达不为迎合措辞重写；业务决定在 generate 后期进入待确认项，在 clarify 中若改变已确认方案则回到讨论。

## 5. 出错后的收敛规则

修复须能说明根因、具体修法、影响对象和续接位置；保留其他有效成果。相同根因没有新的证据、工具条件或修法时停止自动重试。切换 worker、改报错文案或改切片编号不算进展。

全部环路采用 [D04B](detailed/D04B-bounded-loops.md) 的默认策略：批量首次处理，调查/补问最多一次追加；同一操作或候选最多一次重试/修正，整个请求自动返修最多两批，先到上限即停止。无进展提前退出，重开会话/换片继承计数。正常首次分页和有限目标遍历另按游标推进，不能用两轮限制漏掉未处理范围；业务分歧不靠重试解决。检查失败不能直接跳过，也不把坏文件标成“含待确认项的成功结果”。

首次生成中的局部修复只涉及失败对象及必要依赖。Clarify 的任何修复还须服从已确认方案，超出时先重新讨论。资源记录失败不使专业工作失败；内容和文件是否可用必须独立判断。

这里追求的是减少可避免的错误与返工，不承诺在设计阶段穷尽所有 corner case。通过 [08 场景](08-scenario-catalog.md) 优先验证高代价边界，并用 [06 观测](06-observability-and-validation.md) 判断新增检查是否值得。
