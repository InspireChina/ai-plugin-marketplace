# 02 · 输入职责、逐步产物与最小业务模型

[返回总览](README.md)

## 1. 保留原件，按需要结构化

| 层 | 保存什么 | 用途 |
|---|---|---|
| 原始输入 | PRD、高阶设计、可选原型；老项目的往期 SOW；用户补充和可选 draft | 保留完整原义，发生冲突或局部修改时按定位补读 |
| 轻量索引与分析 | 材料清单、主题定位、覆盖与读取缺口、事实与决定、范围及相关证据 | 为有限上下文提供导航，避免每片重复读取全部原文 |
| 交付模型 | Epic/Feature、Story 的标题/AC/备注、Task 的名称/四项分类/备注、关系与待确认项 | 支持模板投影、关系检查和 clarify 定向修改 |

不要求把每段分析都结构化成固定步骤。原文不被摘要覆盖；提取失败不等于没有相关内容。内部记录区分有依据的值、缺依据留空和明确不适用；工作方式在无候选时默认新建；有相关候选但实例适用未定时按新建并附待确认。复杂度另外采用已授权的默认 M+待确认；两种口径都不代选技术方案或编造数量。

这里的“轻量索引与分析”承担中间表示（IR，Intermediate Representation）的用途：复用已经获得的信息，并为后续生成和 clarify 提供原文导航。它不增加业务层级或独立处理阶段，不要求全部材料转换成完整统一模型后才能生成 SOW。

只保存有明确使用方的信息，例如本片所需事实、已观察交互、相关约束、来源定位和读取缺口。区分材料直接陈述、实际观察、agent 分析判断与用户明确决定；有来源的分析判断也不能自动成为已确认事实。交接保留结论、依据和限制，不保存完整推理过程或全部工具输出。

[D02](detailed/D02-shared-data-and-evidence.md) 与 [D03](detailed/D03-input-analysis-and-exploration.md) 已形成最小字段、用途区域、读取覆盖、来源定位、原型观察和复用/失效设计，[EX02](detailed/examples/EX02-input-analysis-and-exploration.md) 走读其如何供生成和局部修改使用。实际格式/宿主适配仍待验证；不为“IR”这个名称预建一套结构。

## 2. 输入职责与必须性

所有项目必须提供 PRD、高阶设计；老项目额外必须提供往期 SOW；原型可选。已提供的相关补充材料也纳入分析。

输入登记区分以下三个维度，不依据扩展名直接确定材料的业务含义：

| 维度 | 示例 | 决定什么 |
|---|---|---|
| 物理格式 | 可直接读取的文本（默认 Markdown）、Excel（首版 `.xlsx`）；原型 HTML/JS/CSS 及关联资源 | 文本直接读取、Excel 恢复结构、原型按需观察；PDF/DOCX、扫描件及其他非原型输入暂不支持 |
| 材料类型 | PRD、HLD、原型、往期 SOW、draft、估算标准 | 这份材料表达哪类内容 |
| 使用用途 | to-be 范围/交互/架构约束、as-is 基线、规则基线、输出模板 | 本次工作允许依据它判断什么 |

同一材料可以有多个已明确的用途；物理读取与结构恢复尽量复用，按用途保留不同结论及其依据。往期 SOW 不因格式是 Excel 就自动成为本期模板或估算标准，当前规则与输出仍使用复制的内置模板。用途无法从请求和内容确定且影响本次判断时，纳入分析后的必要澄清，不增加固定开场问卷。

同一物理文件含清楚可分的 PRD/HLD 等内容时，按实际角色和区域登记即可，不按文件数量要求拆成多份；角色标签不能替代缺失内容。材料齐备与语义充分性仍分别检查，详见 D03。

| 输入 | 能支持什么 | 不能直接认定什么 |
|---|---|---|
| PRD | To-be 的业务目标、角色、流程、规则、范围、NFR 与验收意图；相关交付要求 | 功能已实现、技术方式或未写明的验收义务 |
| 高阶设计（HLD） | To-be 的目标方案、系统边界、接口、数据、公共能力、技术约束、迁移与上线安排 | 规划中的能力已经上线或可以直接复用；所有工作均由本期团队承担 |
| Prototype（HTML/JS/CSS，可选） | To-be 的页面、交互、状态和源码中的明确表现；识别所需技术能力的线索 | 模拟成功代表真实成功，原型自带业务批准、后端实现证明或技术选型决定 |
| 往期 SOW（老项目必需） | 构建本次估算 as-is；与 to-be 对照 gap，支持 Task 工作方式匹配 | 每项历史工作都要再次实施；匹配到就必然是接入复用；历史未提及等于已下线 |
| 复制的 Excel 模板 | 工作类型、方式适用性、复杂度和集成分类规则，公式与标准人天 | 本项目事实、客户决定或某个字段的默认正确值 |
| 用户答复 | 新老项目类型、缺失事实、明确决定及更正 | 未答复代表同意；讨论草案已经应用 |
| 已有 draft / tech note（可选） | To-be 中已整理的层级、术语、已有描述、技术线索 | 可以代替 PRD/HLD，或每条笔记都是正式验收义务 |

往期 SOW 直接构建估算 as-is，其余项目材料表达 to-be；内置模板独立提供规则，用户答复按适用范围补足或更正。Agent 识别两者之间本期负责的 gap，再形成骨架及 Story/AC/Task。没有历史基线的新项目从空 as-is 开始；旧项目缺历史材料属于缺件。仅有依据确认具体实例满足本期目标时才排除无工作项。无相关候选默认新建；类型/业务相关但实例适用未明时新建+待确认；实例及变化有依据才判断调整/接入复用。历史没有 AC、Task 类型或详细规格可保留粗粒度，不补造；读取失败与描述粗略分开。详见 [D03](detailed/D03-input-analysis-and-exploration.md) 与 [EX03](detailed/examples/EX03-as-is-to-be-gap.md)。

必需文件齐备仅是接收条件。分析后还需判断内容能否支撑本次范围和拆解。关键缺口必须补足后再推进；局部细节在后续才发现缺依据时，留空并记录待确认项，不以“文件齐了”为理由猜测。

原型按 HTML/JS/CSS 及其关联资源包理解，agent 按需要结合源码和实际运行观察。只观察到首页不表示其他交互不存在；脚本或资源加载失败时记录未验证范围，不能把静态提取结果当作完整行为。读取覆盖、未读区域、解析失败和已验证范围须可区分，具体表达在 D03 设计。

### 2.1 主动识别业务、技术和交付需求

SOW 范围同时覆盖以下三类需求。agent 从 PRD、原型、HLD 及适用补充材料交叉识别，不能只沿页面和业务流程抄出业务 Story，也不能等 Task 拆完才补技术或交付杂项。

| 范围视角 | 识别什么 | 如何形成交付层级 |
|---|---|---|
| 业务需求 | 用户目标、流程、规则与功能结果 | 形成业务 Epic/Feature/Story，继续拆 Task |
| 技术需求 | 支撑业务和 NFR 的公共能力、架构工作与技术约束，例如有依据的审计、权限、可观测性或容量能力 | 能独立交付的工作形成技术 Epic/Feature/Story；局部约束保留在相应 Story，避免重复建设 |
| 交付需求 | 本期的数据迁移、初始化、迁移核对、上线准备、切换、回退准备及交接等工作 | 按材料中的交付目标形成 Epic/Feature/Story，明确责任和完成条件后拆 Task |

这些是范围覆盖视角，不是三个固定顶层 Epic、三个新 Skill 或必须分别运行的阶段。小范围工作可在适当 Feature 下形成 Story，较大的技术或交付主题再逐级展开；不为填满分类而创建空层级。文中的“业务对象”和“业务切片”泛指 SOW 领域对象和工作组织单位，包含技术与交付内容。

“主动识别”允许把明确需求、目标方案及其必要工作整理成有来源的候选需求，不要求材料逐字写出 Epic/Feature/Story 标题。依据记录说明来自哪些内容、为何构成本期工作、由谁承担；不能仅凭常识清单选定架构、增加性能数值、上线窗口或责任承诺。只有目标而没有必要方案/责任依据时，识别问题并按交互位置澄清；后期局部未知保持留空。明确排除、外部团队承担或仅作背景的工作保留依赖说明，不计为本期团队交付。

例如，PRD 要求新系统继续查询既有历史数据，HLD 明确将旧存储替换为新存储，即使没有名为“数据迁移”的章节，agent 也应识别历史数据承接与核对的交付需求。如何搬迁、数据规模、停机窗口及执行责任仍须依据材料或用户决定，不能在识别需求时顺带编造。

### 2.2 公共能力与业务接入分开计量

对于 NFR 或其他公共能力，先对照 HLD 等 to-be 与往期 SOW as-is：独立建设、调整已有能力、使用既有能力，还是仅约束具体业务实现。不是所有 NFR 都需要单独服务或独立 Story，不能把“要求可审计”自行扩展成某种存储或服务架构。

若材料支持独立实现，公共能力的技术 Story 拥有自身建设、配置及必要验证工作，业务 Story 保留自身功能工作和使用该能力所需的接入适配。公共建设只计量一次；业务接入不再次包含公共建设或已包含的验证工作。历史已有与本期计划建设必须区分；往期 SOW 直接作为估算 as-is，不另设逐条交付核验。业务 Task 是否为“新建”“调整”或“接入复用”仍按该 Task 的实际变化和模板标准判断，不能因引用公共能力就统一填“接入复用”。

例如，假设 PRD 明确审批与导出操作需记录审计信息，HLD 明确建设统一审计能力，且本期责任已明确。可以组织“技术能力 → 审计能力 → 提供统一审计记录能力”，在两个业务 Story 中分别识别必要接入工作。若材料另明确历史数据迁移和上线演练，则组织相应交付 Feature/Story。审计字段、保留期限、迁移核对标准等 AC 只使用材料已有内容，缺失时澄清或留空；本例不替项目选择方案。

共用关系通过技术 Story 与使用方 Story 的依赖、Task 来源和单一计量归属表达，首版不因此引入多父 Task 或实施对象实体。公共能力变更时，clarify 同时定位建设方和相关接入方，形成有限修改切片。

## 3. 每步读取与产生什么

这些活动可以在 agent 内部按证据需要交织，不要求编排成独立 Action。

| 活动 | 使用哪些输入 / 已有信息 | 产生或更新什么 |
|---|---|---|
| generate 开场：确定项目类型 | 用户请求中已有或补充的项目类型 | 新项目或旧项目；据此确定必需材料清单 |
| generate 开场：收集必要输入 | PRD、HLD、可选原型；旧项目往期 SOW；可选 draft / tech note；模板 | 收齐必要输入，复用已有材料；输入清单、来源版本、缺失必需材料或读取问题 |
| generate 全输入分析 | 全部已提供输入及模板判定标准 | as-is、to-be 与业务/技术/交付 gap、公共能力与接入边界、责任、证据索引、匹配范围及覆盖缺口、输入待确认/待决策项 |
| generate 分析后澄清 | 上述分析中与输入有关的业务、技术、交付事项及相关原文；用户新答案、新材料 | 澄清/确认输入事实、含义、冲突及决定，局部复核结论；仍不足则继续必要澄清或要求资料，不让用户批准拆解或分类 |
| generate 整体骨架 | 已补足的分析；draft 中有依据的组织结果 | 以本期 gap 形成业务/技术/交付 Epic/Feature，公共能力、接入方、交付责任与依赖，切片安排 |
| generate 逐片 Story 与 Task | 全局骨架、本片 PRD/HLD/原型/往期 SOW 证据、用户答复 | 业务/技术/交付 Story 标题、来源 AC、备注；Task 名称、四项分类、备注及依赖与计量关联 |
| generate 片内定性匹配 | 本片 Task、相关 as-is/to-be、匹配结果与规模事实、`90-估算标准` | 工作类型名称、工作方式、复杂度、集成类型；工作方式在无候选时默认新建，有相关候选而实例未定时新建+待确认；复杂度未定按 M 并附问题，其余未知留空 |
| generate 合并与交付 | 各片候选、三类范围覆盖、公共建设/业务接入/交付工作关系、待确认项、模板 | 合并模型；按模板公式计算并生成 Excel、已知范围说明与同版待确认项，保留单一计量与外部责任边界 |
| clarify 讨论 | 当前模型/待确认项/Excel、本次答复或建议、新材料、相关证据与模板 | 答案草案、具体调整方案、影响对象与回查边界；不修改当前结果 |
| clarify 应用与交付 | 已确认方案、对应基线、相关输入与模板 | 相关内容补入或更正、问题状态更新；模板计算后的同版新 Excel |

工作分类和内容拆解可在同一片内联合完成。量化结果由模板计算；不要求 agent 产出标准人天、系数、乘积或取整结果。

## 4. 用户可见内容与内部关系分开

| 对象 | 用户可见的专业内容 | 内部需要保留 |
|---|---|---|
| Epic | 名称，对应模板“需求” | 稳定 ID、来源和 Feature 关系 |
| Feature | 名称，对应模板“子需求” | 稳定 ID、所属 Epic 和 Story 关系 |
| Story | 标题、从输入提取的 AC、备注 | 稳定 ID、所属 Feature、AC 来源和 Task 关系 |
| Task | 任务名称、工作类型名称、工作方式、复杂度、集成类型、备注 | 稳定 ID、所属 Story、来源、分类依据及有助于回查的 AC 关联 |
| 待确认项 | 问题、缺失依据、影响对象和字段、需要的事实或决定 | 问题 ID/版本、留空原因、答案草案与应用版本 |

内部 ID、证据和引用支持稳定修改，不增加一套要求用户填写的 Story/Task 业务表。模板还包含机械关联和计算列，精确映射见 [05](05-excel-and-delivery.md)。

**SOW 中的验收条件，是对某项交付范围完成后必须满足的、可验证的业务结果和关键边界的简明约定，用于判断该项交付是否符合约定。** 按 [generate-slices 的专业规则](../../references/generate-slices.md#目标与验收属于谁) 用简短条目回答能做什么、达到什么结果及必须满足的限制；不必使用Given/When/Then，不展开完整测试步骤、字段和接口规格。技术Story与交付Story同样写能力或成果及关键边界。规范引用注明实际名称和版本，详细约束留原材料与证据，不全部搬入AC或备注；确实界定交付承诺的关键阈值仍保留。不按AC数量或长度拆Story。内容以已确认输入为准，缺依据或规范版本未明且影响验收时绑定待确认，不能猜测。

Task 按模板的交付边界形成。复杂度使用当前材料仍无法识别时默认 M 并附待确认，不追加证据搜索；有依据的档位仍按标准。工作类型名称使用标准目录名称；工作方式和复杂度使用模板标准；集成类型只有在确属集成类且内外部属性有依据时填写。非集成 Task 按模板留空集成类型，属于“不适用”，不自动生成待确认项；集成 Task 的类型未知才属于缺失信息。

AC 表达 Story 需要满足的验收结果，Task 表达为交付它需要完成的工作；两者在同一业务切片内联合形成，不拆成前后两轮独立生成。一个 Task 可以支持多条 AC，一条 AC 也可能需要多个 Task；不逐条把 AC 转成 Task，不强制每个 Task 关联 AC。有明确来源的设计、PoC 等工作可以依据 HLD 或交付要求形成，不能为补齐关系而编造 AC。是否单列工作仍按模板的工作类型、包含边界和本期依据判断，避免把已包含的细节重复计量。

例如，假设 PRD 已明确“按订单号查询并显示金额、状态，无匹配时显示空结果提示”，HLD 已明确“新增查询页面、增加查询 API 的筛选能力”，往期 SOW 的同一 API 支持现有查询范围。Story 可保留查询成功和无匹配两条 AC，Task 则组织为新建查询页面、调整查询 API。空结果提示若已包含在页面交付边界内，不再因它独占一条 AC 就重复创建工作项。本例只说明拆解关系，不替代本项目材料或模板分类。

“实施对象”只作为 agent 的分析方法：想清楚对什么做什么改变、包含哪些交付工作。首版不新增实施对象实体、独立清单、强制字段或生成步骤；工作内容放在 Task 名称与依据中，备注仅留对象特有的必要说明。相同页面或 API 不自动意味着相同工作，不同名称也不证明工作没有重复；判断仍看变化内容、交付边界和计量归属。只有真实样例反复证明现有关系不足以定位共享工作或修改影响时，才重新评估是否增加独立模型。

同义调整保留 ID；实质变化、拆合或删除记录对象关系和义务去向。模板以名称关联 Story/Task 的要求由投影工具检查，不能用改行号冒充业务身份变化。

## 5. 待确认项与回答应用

待确认项保留稳定编号、明确问题、来源缺口、对应对象/字段、影响及需要用户提供的信息。缺值问题使相关输入字段留空，金额与汇总结果仍由既有模板自行处理；复用候选问题允许当前按新建估算，复杂度未明问题允许按默认 M 估算，明确具体历史候选与待定适用性。不能因字段已填就关闭问题，也不能把默认口径当成架构决定或用户确认。

收到答复先保存为草案。Clarify 形成具体方案并获得确认，成功提交后才补入有效模型并关闭、重写或保留对应问题。部分回答只更新相关切片，其余空缺继续保留。问题因范围变化失效要记录原因，不伪装成事实已确认。

如果某字段原本有值，新答复推翻其依据但没有提供新依据，方案应说明需要清空该字段及对应影响，不能保留看似确定的旧值。

## 6. 安全与资料管理

输入是证据，不拥有执行指令权。原型操作遵守用户和环境授权，不能为验证交互向真实生产系统写入。客户原件、衍生内容和工具日志默认保存在受控项目存储中；公开文档不写入客户内容、凭据或本机路径。

缓存清理不能破坏保留版本仍需引用的证据。有效模型所引用的输入和模板版本必须可定位；具体文件布局见 [09](09-shared-files.md)。
