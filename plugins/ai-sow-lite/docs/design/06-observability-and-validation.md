# 06 · 用时、Token 埋点与性能验证

[返回总览](README.md) · [D08 观测详细设计](detailed/D08-telemetry-and-performance.md) · [EX06 计量走读与宿主探针](detailed/examples/EX06-telemetry-accounting.md)

## 1. 目的：看清开销，指导优化

资源机制回答两类问题：一次 generate 或 clarify 的各步花了多久、消耗多少 token；同一项目从初版到多次反馈调整，总体工作花在了哪里。这些数据用于判断应优化材料读取、探索、上下文、问答、局部分析还是 Excel 处理。

它不承担预算分配、每阶段配额、超限批准或以费用为由跳过必要质量检查。D04B 的轮数、批次范围和无进展出口属于执行停止策略，独立于埋点；默认值需用实际成本与质量校准。默认没有资源审批流程；未来若用户明确要求限制资源，应作为另外的可选约束设计，不能混进埋点机制。

## 2. 观测步骤不等于编排步骤

代码在实际可观察的入口、工具调用、文件操作边界记录事件；模型调用/usage 边界需要宿主提供已验证来源，普通 Skill 不保证全部可得。agent 可以给专业活动附上主题或切片，不需要为了统计而把动作拆成固定 Action 链。

| 入口 / 活动归类 | 重点测量 |
|---|---|
| generate 开场与接收 | 确认新老项目、收集对应必需材料、用户等待和资料不足时退出的成本 |
| 环路与批处理 | 首次处理量、追加次数、实际进展、问题合并量、到限/无进展出口、继承计数；不靠拆请求虚报低消耗 |
| generate 输入分析 | 文本/Excel 读取、原型探索、as-is/to-be 综合与 gap/匹配活动，业务/技术/交付及相关历史覆盖情况 |
| generate 分析后问答 | 关键问题形成、每轮用户等待、增量材料分析、答案引发的局部再分析；信息补足前不拆解 |
| generate 整体骨架 | 三类需求的 Epic/Feature、公共能力与接入方、交付责任、依赖和切片安排的形成成本 |
| generate 各关联切片 | 业务/技术/交付内容的上下文加载、Story 与来源 AC、Task 四项定性匹配、待确认项、局部检查与保存 |
| generate 合并 | 骨架覆盖、跨片依赖、共享计量、汇总，以及相关片修正 |
| generate 检查与 Excel | 专业核对、机械检查、计算、生成、复读和保存 |
| clarify 定位与讨论 | 反馈定位、补读、有依据的方案分析及模板试算、交互轮次和用户等待 |
| clarify 已确认方案应用 | 切片处理、必要回查、实际改动范围、待确认项变化 |
| clarify 检查与 Excel | 相关核对、计算、文件操作和一致提交 |
| 两入口恢复 | 失败、取消、重试、缓存复用和恢复开销 |

生成片记录本次片标识、相关业务对象及活动关系，便于比较证据量、上下文加载与返工开销。片标识不等于模型调用 ID；一次调用涉及多片但只返回总 usage 时，保留组合范围与总量，不假造逐片 token。片数本身不作为性能目标，也不按片分配默认资源配额。

一项活动跨多个类别时按实际子活动记录；宿主只给粗粒度数据时保留该粒度，不能事后平均摊成看似精确的每步 token。

[D04A 单 session 全景](detailed/D04A-single-session-panorama.md) 给出无 subagent 的 G0—G12 活动输入输出，作为观测范围而非新增编排步骤。先记录实际起始会话负担、输入读取/原型探索、候选生成、回显/回读、合并和 Excel 的成本；再判断是否需要上下文优化。用户在已有长会话调用 Skill 时，起点不能按空白会话计算。

## 3. 最小事件信息

建议记录请求 ID、入口、项目标识、基线/结果版本、活动 ID、父活动、实际调用 ID、主题或切片、起止时间、状态、重试或恢复关系。调用信息另记录模型/工具及可获取的版本、usage 来源和完整度。

分类描述用于归因，原始时间与 usage 由可观察事件产生。agent 不靠回忆填写精确用时和 token。记录中不默认保存原始客户材料、完整提示词、完整工具输出或内部推理。

模型升级、模板变化、输入大小和可读性都会影响比较；报告要带必要环境信息。字段的实际可得性先由宿主实验确认，不能预先承诺某平台不提供的数据。

## 4. 时间口径

| 指标 | 定义与限制 |
|---|---|
| 请求总历时 | 本次入口实际可观察起点到成功返回、要求补资料、取消或失败结束；起点前、跨恢复或时钟不可对齐的缺口单列 |
| 用户等待 | 等待开场答案、关键补充或 clarify 方案确认的时间，单独记录 |
| 工具/模型累计耗时 | 每次实际调用的用时之和；并行时可以大于请求历时 |
| 活动历时 | 某专业活动开始到结束；包含其子活动，不能再与子活动相加 |
| 首个有用反馈等待 | 到具体缺失资料说明、问题包或 clarify 方案的时间；不能用空进度消息充数 |
| 首版可用文件等待 | generate 到经过必要检查的可用 Excel 的时间 |
| 修改响应 | clarify 到可讨论方案，以及方案确认到可用新 Excel 的时间，分别展示 |
| 恢复开销 | 重试、重新读取、修复和重复计算的实际消耗 |

可以展示扣除已识别用户等待后的请求历时，但不能称为 CPU 时间；它仍可能包含排队、空闲和工具等待。只合并不重叠的等待区间，避免重复扣减。

Generate 返回后，请求已经结束。用户离线看 Excel 的几小时或几天不挂在 generate 的 span 上，也不加入 agent 执行时间。项目视图汇总多次独立请求；若展示自然日跨度，要与累计执行耗时明确区分。无法观察的离线评审时间标为未知。

## 5. Token 与汇总口径

- 优先使用实际调用返回的 input/output token；缓存、推理 token 等明细仅在宿主提供且口径明确时展示。
- 某些明细是总量的子集，不能再叠加。例如 cached input 可能已包含在 input 中，推理 token 可能已包含在 output 中；按来源定义处理。
- 父活动汇总子调用，不能把父级总量和子调用再相加。有可靠调用身份时按物理调用去重；只有累计快照时按原生 scope/epoch 和可信边界求差。逻辑重试真正消耗的调用都计入。
- 累计回调与最终回调属于同一调用的修正，不能计两次。迟到 usage 仍归原请求，取消和失败的消耗同样保留。
- usage 缺失标为未知；只掌握部分调用时给已知小计和未知范围，不能填零或宣称完整总量。
- 只有整次 agent 的总量时，保留整次总量和可得的工具耗时，不编造各工具的 token 分配。
- 跨请求复用历史分析可记录命中，但不把历史已计费用重复记到当前请求。当前补读和重新处理的成本正常计入。

D08 已明确观测与业务版本分离：交付摘要是带截止点的快照，迟到 usage 只更新独立报告，不修改已交付 Excel/manifest/summary。常规收尾一次有界汇总，不等到 usage 齐全才返回。当前有限探针仅证明源形状，逐活动 token 尚未验证。

观测记录暂时失败可补写或重建；无法重建则标记缺口。单纯观测缺失不阻断可用 SOW 的交付，也不能被误报为性能改善。

当次活跃上下文、累计 input/output token 和文件体量是不同口径。保存 JSON 不免除 agent 首次生成内容的输出成本，代码读全文件也不意味着模型读全文件；以实际工具返回及宿主保留情况为准。压缩可能降低后续活跃上下文，不能抵消已经发生的 usage；记录可得的压缩与恢复补读信息，不用字符数或候选文件大小反推精确 token。

## 6. 用户和开发者分别看什么

用户可获得简洁的本次结果摘要：成功/资料不足/仅讨论/取消/失败、可用文件或方案、主要待确认影响、本次用时及可得 token。资源明细不挤进每个业务决策问题，也不要求用户阅读日志才能使用 Excel。

开发者看活动明细与调用关系：重复读取哪些来源、上下文交接后增加多少开销、哪些错误造成重试、哪些切片需要更深回查、Excel 处理占比如何、观测缺失在哪里。项目汇总区分初版、讨论、已应用修改及失败尝试，不只统计成功请求。

## 7. 如何验证“快且健壮”

采用可重复的代表性输入，记录格式、规模、模型、工具版本、模板版本和观测完整度。小型、典型及至少一组长材料单 session 各取得首次生成及局部 clarify 基线；长材料不能等小样本暴露瓶颈后才测。不同修改范围复用 I3/I4 的既定样例。针对已发现的开销做必要配对，结果不稳定再重复；单次结果只作为该样例记录，不能据此宣称性能分布或普遍提速。

| 比较项 | 同时需要观察的质量结果 |
|---|---|
| 首版可用文件时间与 token | 必需输入齐备、业务/技术/交付范围完整、公共建设与接入无重复、来源 AC、四项匹配依据、留空与待确认项一致、文件可用性 |
| Clarify 方案时间与应用时间 | 方案明确、确认有效、切片内改动、外部影响没有遗漏 |
| 分片粒度与片间上下文交接 | 本片与跨片关系完整，骨架覆盖没有遗漏；比较节省与额外读取、合并、调用开销 |
| 少读或复用带来的节省 | 原文可定位、冲突未被摘要抹掉、变化后缓存没有误用 |
| 减少核对或合并活动的节省 | 已知错误、重复计量和文件故障仍能被必要检查发现 |
| 待确认项数量变化 | 问题是否重要、空白及其影响是否清楚；不能以假设或默认值追求“零待确认” |
| 失败恢复成本 | 无整项目重跑、无重复应用、上一版仍可用，失败耗时没有被漏记 |

先获得贯穿基线，再优化占比高且可减少的部分；每项新机制都说明实际质量收益与耗时/token 增量。数值目标从样例和用户可接受体验中确定，本稿不虚构响应秒数、token 上限或已经达到的性能。

执行组织先比较单 session 基线及减少重复输入/输出后的结果；仍有明确局部噪声或增长瓶颈时才增加隔离对照，并发在其后另评估。不要为了比较先实现多 agent 平台，也不故意全量回显或重写数据来制造差的基线。若瓶颈在 Excel、工具等待或必要的业务输出量，应直接优化对应部分。

ai-sow 已有运行结果可作为性能参考，优先复用同一输入与可得记录；比较时说明模型、模板、范围、观测口径及交互差异。旧运行缺少逐步 token 时保留可得总量，不为制作完美历史基线重跑全流程，也不反推缺失明细。对照时采用相同 as-is/to-be 和 gap 口径；历史已有且无工作不应再计为本期，不能直接拿两版 Task 数作覆盖结论。Lite 提速必须同时保留本期技术/NFR 与交付 gap、公共变化及接入责任，不能通过少拆非业务工作获得虚假的性能改善。
