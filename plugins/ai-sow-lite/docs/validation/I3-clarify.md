# I3 · 文件独立的局部修改验证

状态：I3.1/I3.2 已接通有限编辑、确认绑定和独立 clarify Skill，三类文件独立的实际反馈已交付。I3.3 接续串行使用周期与恢复；复杂子集和修订计数的组合风险在 I4.2 收口，当前不宣称整体开发或性能目标已完成。阶段范围见 [P03](../design/implementation/P03-clarify.md)，自主取舍见 [决策记录](implementation-decisions.md)。

## 验收边界

- 讨论时保留当前有效 SOW；只在取得具体方案的实际执行确认后应用。
- 确认既有默认 M 可以只改变依据、决定和问题状态；真正已采用的重复答复不创建空版本。
- 对原文的误读修正只影响相关 AC/备注及必要依据，不改变 Task 的实施方式，也不要求用户重新提供已有证据。
- 每项实际变化均按稳定对象身份和字段核对；相同字段、不同新值不能复用确认。当前版本改变时拒绝旧候选，不尝试合并。
- Excel 沿用原模板计算。测试分别说明受控业务数据、机械故障、真实 Office 与新会话专业行为，不相互替代。

## I3.1 已接通的行为与 TDD

`check` 接受有限编辑稿，由程序复制基线并派生实际差异、读写集合、候选和可读方案。未知地址、矛盾编辑、隐式级联、过期基线及越界变化合批诊断；未改字段和存续数组顺序保留。问题、决定、分类依据、来源采用及 lineage 都进入实际差异，不能仅用“字段允许修改”放行不同的新值。

最初公开调用以 `OPERATION_UNSUPPORTED` 失败，再逐项补通候选构造与消费链。后续实际 Red 暴露了嵌入 AC 结构、确认字节变化、登记来源缺失、非法方案修订、摘要尾随换行、退出对象引用、未拆明义务被静默删除和归档合同等问题，均在相应范围修复后转绿。测试夹具中的错误键名、路径和初始目录问题单独归因，不记成产品缺陷。

展示方案保存为不可变文件，确认记录绑定该文件、实际答复原件与摘录，以及全部具体变化。首次有效核对会绑定确认文件的精确字节；后来换文件或改字节会失败。方案采用的输入快照允许经核对的追加登记，但旧条目及其顺序必须一致；全输入成员查询会因追加失效，明确限定输入的查询仅在所选结果未变时可继续。确认答复不会被自动加入业务事实。

新版归档包含计划、展示计划、候选、prepared 及可复核的确认记录。相同候选、模板、基线与计划内容保持有效时，确认及新的检查引用不会要求再次 Office。原件或业务依赖变化仍拒绝，不能用预览缓存跳过检查。

## 独立审查与最终回归

独立审查发现一项 P2：机器计划已绑定条件、未决事项和回查边界，但可读方案未展示这些内容。公开 `check/edits` 反例复现后，在原投影中补齐这些字段及已有对象/问题的可读名称，空集合明确显示“无”。两个新增变体由 Red 转 Green；定点复审关闭该项，结论为 Spec PASS、Quality APPROVED，剩余问题为零。

完整 Lite 套件在该可读投影修正前为 **522 通过、12 跳过，470.09 s**。修正只增加可读投影及两项测试，独立复审通过还原后的文件摘要确认其余实现精确未变；修正后执行 **215 项定向回归通过，34.59 s**，三项真实 Office 用例复用上述未改变机制的证据，不重复计算。Reviewer 另复跑三项聚焦测试，全部通过。

修正后的独立副本完成真实 Generate 交付、幂等与恢复，一次 Office，31 份 Python 审计收据、零越界，并清理自身临时目录。这仍是既有 Generate copy smoke；I3.3 才补实际历史依赖链和逐进程收据对账，不将当前数量记录称作全系统追踪。

仓库根 42 项测试和验证器通过。旧插件锁定同步、388 项 Skill 测试与151项插件测试通过，4项跳过；独立副本 setup/generate 均成功并清理自身目录。`git diff --check` 通过，原模板与旧插件源码保持不变。

## I3.2 文件独立的实际讨论与交付

新增 [Clarify Skill](../../skills/clarify/SKILL.md) 和 [局部修改参考](../../references/clarify-changes.md)，双宿主 manifest 同时发现 generate/clarify。入口先读现版与本次反馈，按实际对象、关系及必要依据限定影响；工具从有限编辑派生完整候选和具体差异。只有当前用户对已展示方案的真实执行意思才接入确认，公式和金额仍交给原模板。

发现与链接测试先出现6个缺文件失败，真实确认示例消费测试先出现1个缺参考文件失败；实现后19项通过。示例实际创建计划、登记控制器答复、读取精确文本区域、附确认并再次通过公开 check；不是仅检查关键字。独立源码审查 Spec PASS、Quality APPROVED、无发现。静态发现不代表新增宿主安装或认证后的运行实证。

三个新会话只获得独立插件运行面、真实已交付的合成项目文件及[原始反馈](../../tests/fixtures/clarify/cases/README.md)，没有生成聊天、测试期待或预制改稿。控制器读完实际方案才发送执行确认，各场景只在确认后运行一次 Office。结果和脱敏计量见 [实际观察数据](I3.2-feedback-observations.json)。

| 场景 | 实际结果 | 未改变的内容 |
|---|---|---|
| 首次采用默认 M | 第1版方案通过；保留 M，更新 Task 说明/依据、增加实际决定，解决对应估算问题；真实交付新版本 | 记录条数仍未知；其他模型对象及原全部版本文件保持 |
| 改为 S | 第1次检查发现主题误关联待确认项 ID；只修关联到业务对象，登记新主题并以第2版通过。用户确认后改为 S 并处理依据/决定/问题 | 工作方式、其他分类、迁移范围和责任不变；不补造条数或声称满足 S 的数量门槛 |
| 修正原文误读 | 第1版方案直接定位 PRD“不显示上一请求的迟到结果”，恢复一条 AC，确认后交付 | 其他 AC、全部 Task、分类和责任不变；迁移默认 M 的原问题仍 open |

误读基线的错误是测试主动植入后经真实 I1 交付，不称作原 Agent 自发错误。应用后独立核对每个未涉及对象、数组顺序、原版本和插件源文件摘要；新版的全部输出、依赖及确认引用可达。M 场景随后收到同一内容的重复确认，只返回现版；所有 current/versions 字节保持，无新版本、无再次 render/apply。

无新 Skill 的对照也能正确提出 M→M 的采用方案并停在确认前，但同样因主题关联问题经历一次机械更正。不能将其已有语义能力写成新 Skill 的提升。实际两次错误促成共用编写参考的一行澄清：related_object_ids 只用模型对象，答复问题时关联其目标。最终提示通过19项局部回归和定点源码复核；保留原演员的失败记录，不声称已经用新提示重新演练并证明错误消失。

第二次交付版本为 `63cfa0cc-3b1d-4546-88c2-25b80990b3f3`，manifest 为 `eebc11feed06a1b0eedf7c6522418eed98f68c04883491fada40c294df07374a`。独立复核只改变一条 Story 的备注和反馈依据；全部 Task、AC、分类及 M 采用决定保持，pending/decisions 文件字节不变，27个旧版本文件与35个插件源文件未变，新版67个输出/依赖引用摘要有效。详见 [串行实测记录](I3.3-serial-observations.json)。

### 确认原件的恢复反例

完整recover反例发现：已应用后修改登记的确认答复原文件，旧实现仍可能返回成功。原件在应用时核验，却未进入manifest依赖。修复只把确认原文件及其摘要加入现有依赖清单，复用保存、锁内重检和恢复验证；不改轻量inspect/current的职责，也不新增专业门禁。受控篡改后完整recover现在拒绝。

首次测试误用轻量inspect/current，另一次日志文件名含green但内容仍失败；这些调查记录保留，不能算有效Red/Green。有效反例改用完整recover并撤回补丁复现后，再恢复最小修复转绿。历史演员版本保持原字节，不迁移其manifest或修改其期待；修复后的新包另行检查机械依赖完整性。

### 旧 Generate 的重复调用

标准完整套件在无外部capture设置下实际建立基线、预览与两次串行应用，542项通过、12项跳过；唯一失败位于扩展后的独立副本smoke。完整周期已完成Generate和Clarify，但再次调用旧Generate时，旧输入索引快照与后来合法追加的登记不同，导致相同成功意图被误拒绝。受控克隆复现：新检查有效、候选语义摘要相同，只有依赖快照不同。

修复保留历史版本全量摘要验证及新的候选语义核对。只对已经证实成功的Generate，不再要求可变登记索引等于首次应用前快照；仍须匹配原语义意图才能返回旧成功事实，current保持末版。未应用候选继续完整匹配检查记录。新增反例先失败，再证明原调用幂等、修改Task备注后即使结构合法仍返回REQUEST_ID_CONFLICT，旧版本和现指针不变。smoke的旧“一次Office/数量门槛”验收也改为两次转换、精确进程收据对账以及实际Clarify结果检查。

### 恢复、审计和阶段验证

真实准备包的取消测试覆盖render前、锁前和指针后；指针后保留成功事实。两个子进程分别在apply前和真实提交完成但响应前被kill，一次recover后使用原意图续接，不重算或重复应用。短锁繁忙立即返回WRITE_BUSY；过期草稿返回BASE_STALE且保留原字节。提交后观测收尾失败只降级资源记录。
