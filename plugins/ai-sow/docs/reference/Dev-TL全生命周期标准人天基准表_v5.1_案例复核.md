# Dev / TL 全生命周期标准人天基准表 v5.1 案例复核

- 复核对象：[v5.1 讨论稿](Dev-TL全生命周期标准人天基准表_v5.1_讨论稿.md)
- 样本批次：A
- 日期：2026-09-02
- 样本要求：不复用 v5.0 已使用的八个案例；每一行对应一个独立可验收 Task

本批次使用七类企业项目场景检验 v5.1。表中“缺口”表示 v5.1 没有准确类型；相近类型不能仅为完成映射而代用。
PD 均按标准复杂度展示，不计算项目总价。

## 案例 A1：金融数据保留、归档与到期销毁

场景：交易系统必须按产品和地区执行 7 年保留、低频归档、法律冻结和到期销毁，并提供审计证据。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析保留规则对数据、接口、备份和审计的影响 | 需求与变更技术影响分析 | 新增 | 1.0 | 可准确映射。 |
| 设计归档、冻结、恢复和销毁方案 | 专项技术方案设计 | 新增 | 2.0 | 可准确映射。 |
| 建立按数据域执行的保留与销毁策略 | **缺口：数据生命周期治理** | 新增 | 2.0 | 数据迁移关注一次性搬迁，批处理只表达触发方式，都不能表达持续生效的治理策略。 |
| 建立归档与销毁调度 | 批量处理与定时调度任务 | 新增 | 2.5 | 调度本身可独立运行和恢复时单列。 |
| 建立法律冻结操作权限 | 功能与资源访问控制 | 修改 | 1.5 | 可准确映射。 |
| 建立销毁记录和证据审计 | 业务操作审计追踪 | 修改 | 1.0 | 可准确映射。 |
| 建立归档恢复与到期销毁自动化回归 | API 自动化回归测试 | 新增 | 1.0 | 独立回归资产。 |

结论：v5.1 缺少持续性的数据保留、归档、冻结和销毁能力。新增类型不能扩展成泛化“数据治理”，
否则会与数据权限、数据安全、数据质量和迁移重叠。

## 案例 A2：Java 与 Spring Boot 主版本升级

场景：已有 12 个服务从 Java 17、Spring Boot 2 升级到 Java 21、Spring Boot 3，包含依赖替换、构建调整和兼容验证。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析运行时、框架、库和部署兼容性 | 需求与变更技术影响分析 | 新增 | 1.0 | 一个升级专题一项，不按依赖数量计量。 |
| 验证关键第三方库的替代方案 | 技术问题探索（Spike） | 新增 | 1.5 | 仅在存在明确技术未知时计量。 |
| 升级一个服务的运行时、框架和依赖 | **缺口：应用技术栈与依赖升级** | 修改 | 2.5 | 应用工程初始化描述从无到有的工程骨架，不能准确表达既有应用技术栈迁移。每个服务仍需一行。 |
| 调整服务构建流水线 | 构建与发布自动化 | 修改 | 1.5 | 流水线行为改变时计量。 |
| 适配 Java 21 运行镜像 | 应用部署与运行环境接入 | 适配 | 1.0 | 既有运行平台保持不变。 |
| 执行运行时和中间件兼容验证 | 目标环境兼容性验证 | 新增 | 1.5 | 可准确映射。 |
| 调整关键 API 自动化回归 | API 自动化回归测试 | 修改 | 0.5 | 只修改独立测试资产。 |

结论：技术栈主版本升级是常见、可验收的纯技术交付，不能拆散到每个业务 API 或页面，也不等同于工程初始化。

## 案例 A3：客户门户满足 WCAG 2.2 AA

场景：现有客户门户改造键盘导航、焦点管理、语义结构、对比度和屏幕阅读器提示，并完成正式审计。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析组件、页面和浏览器辅助技术影响 | 需求与变更技术影响分析 | 新增 | 1.0 | 可准确映射。 |
| 建立应用级焦点、语义和辅助提示基础能力 | **缺口：无障碍与可访问性基础能力** | 新增 | 1.5 | 多页面共享的可访问性机制不是单一页面修改。 |
| 调整可复用表单和导航组件 | 可复用应用组件或程序库 | 修改 | 1.0 | 可准确映射。 |
| 调整登录与账户查询页面 | 信息展示与查询页面 | 修改 | 1.0 | 每个独立页面实例一行。 |
| 调整申请提交页面 | 数据编辑与业务交互页面 | 修改 | 1.0 | 页面内部控件不重复计量。 |
| 建立键盘导航端到端自动化 | 用户界面端到端自动化测试 | 新增 | 1.5 | 可准确映射。 |
| 完成浏览器、读屏软件和 WCAG 验证 | 目标环境兼容性验证 | 新增 | 1.5 | 可以承接，但名称只写“目标环境”不足以清楚表达无障碍标准。 |

结论：应新增应用级可访问性建设类型，并把现有验证类型改名为“兼容性与无障碍验证”；
不需要再按键盘、读屏、对比度分别增加类型。

## 案例 A4：核心支付服务建设跨地域灾备

场景：支付服务实现跨地域热备、流量切换、数据恢复、降级和定期演练，RTO 30 分钟、RPO 5 分钟。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 设计 RTO、RPO、流量、数据和降级方案 | 专项技术方案设计 | 新增 | 2.0 | 可准确映射。 |
| 建立跨地域网络和数据库资源栈 | 基础设施资源栈建设 | 新增 | 3.0 | 网络与数据库若可独立验收，应拆成两行；此处表示一个统一交付栈。 |
| 建立灾备资源 IaC 模块 | 基础设施自动化模块 | 新增 | 2.5 | 可准确映射。 |
| 实现应用流量切换、降级和数据恢复机制 | **缺口：业务连续性与灾备能力建设** | 新增 | 3.0 | v5.1 只有基础设施与灾备验证，没有应用实际可切换、可恢复的能力类型。 |
| 接入灾备区域日志、指标与追踪 | 应用日志、指标与链路追踪接入 | 适配 | 1.0 | 可准确映射。 |
| 建立 RTO、RPO 与复制延迟告警 | 应用监控与告警 | 新增 | 1.5 | 可准确映射。 |
| 执行故障切换与数据恢复验证 | 系统韧性与灾难恢复验证 | 新增 | 2.5 | 建设与验证是不同交付对象。 |
| 编制灾备切换和恢复手册 | 应用运行维护手册 | 新增 | 1.0 | 可准确映射。 |

结论：不能把“灾备能力建设”计入“灾备验证”，也不能只按资源栈计量应用侧的切换和恢复机制。

## 案例 A5：高并发抢票链路性能治理

场景：抢票高峰出现库存锁竞争和响应超时，需要完成瓶颈定位、限流、缓存、并发控制和容量复测。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 通过压测和 Profiling 定位主要瓶颈 | 技术问题探索（Spike） | 新增 | 1.5 | 交付未知消除和推荐方案。 |
| 实施限流、缓存和并发控制改进 | **缺口：性能与可靠性工程** | 修改 | 2.5 | 性能验证只输出结论；把跨切面的技术改进硬套到业务 API 修改会丢失交付边界。 |
| 调整库存查询事务 | 业务数据查询 API | 修改 | 1.5 | 只有业务查询行为确实改变时计量。 |
| 调整下单并发控制事务 | 业务操作 API | 修改 | 2.0 | 可准确映射。 |
| 完成容量、负载和稳定性复测 | 性能、容量与稳定性验证 | 修改 | 1.5 | 建设与验证分别计量。 |
| 调整高峰期延迟和拒绝率告警 | 应用监控与告警 | 修改 | 1.0 | 可准确映射。 |

结论：需要增加“性能与可靠性工程”，但只计具有明确技术目标和可验证改进结果的跨切面工作；
普通 SQL 调优、索引、缓存或重试仍包含在所属主 Task 中。

## 案例 A6：单体系统按领域边界模块化重构

场景：不改变外部业务行为，将订单、库存和结算从一个耦合单体中划分为稳定模块，建立依赖规则和契约测试。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析模块依赖、数据所有权和发布影响 | 需求与变更技术影响分析 | 新增 | 1.0 | 可准确映射。 |
| 设计目标模块边界和迁移顺序 | 专项技术方案设计 | 新增 | 2.0 | 可准确映射。 |
| 记录共享数据库拆分决策 | 架构与技术决策记录（ADR） | 新增 | 1.0 | 可准确映射。 |
| 重构订单模块并建立依赖边界 | **缺口：技术债治理与结构性重构** | 修改 | 2.5 | 外部业务行为不变，不能虚构一个业务 API 修改；每个可独立验收模块一行。 |
| 重构库存模块并建立依赖边界 | **缺口：技术债治理与结构性重构** | 修改 | 2.5 | 与订单模块是不同交付对象。 |
| 建立订单与库存模块契约测试 | 接口契约测试 | 新增 | 1.5 | 可准确映射。 |
| 调整模块依赖质量门禁 | 应用工程初始化与开发规范接入 | 修改 | 1.0 | 既有工程规则发生变化。 |

结论：纯结构性重构是 Dev / TL 常见工作；只有明确质量目标、作用范围和回归证据时才可计量，
普通代码整理仍包含在主工作单元中。

## 案例 A7：应用安全加固与高危依赖修复

场景：互联网应用修复高危依赖，增加安全响应头、密钥轮换、出站访问限制和敏感日志清理，并完成复测。

| Task 实例 | v5.1 类型 | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析漏洞、攻击面和兼容影响 | 需求与变更技术影响分析 | 新增 | 1.0 | 可准确映射。 |
| 升级存在高危漏洞的框架和依赖 | **缺口：应用技术栈与依赖升级** | 修改 | 2.5 | 与 A2 使用同一候选类型。 |
| 建立安全响应头、出站限制和日志清理控制 | **缺口：应用安全与隐私工程** | 修改 | 2.0 | 数据安全处理只覆盖业务数据加密、脱敏和签名，不足以表达应用整体安全控制。 |
| 调整密钥轮换配置和开关 | 应用配置与功能开关 | 修改 | 1.0 | 可准确映射。 |
| 将应用适配到既有密钥轮换机制 | 应用部署与运行环境接入 | 适配 | 1.0 | 平台保持不变，只计应用侧接入。 |
| 完成漏洞、攻击面和配置安全复测 | 应用安全验证 | 修改 | 1.5 | 建设与验证分开。 |
| 形成修复发布和回滚方案 | 生产发布与切换方案 | 修改 | 1.0 | 可准确映射。 |

结论：安全功能不能全部归入数据安全；需要增加应用级安全与隐私工程，但不按漏洞编号、响应头或扫描规则拆类型。

## 复核发现与审核决定

| Finding | 改进建议 | 审核决定 | 决定理由 |
|---|---|---|---|
| A-F01 | 新增“数据生命周期治理” | **吸收** | 有持续策略和可独立审计结果，且无法由迁移或批处理准确表达。 |
| A-F02 | 新增“应用技术栈与依赖升级” | **吸收** | 纯技术升级频繁发生，外部业务行为不变，工程初始化不能替代。 |
| A-F03 | 新增“无障碍与可访问性基础能力” | **吸收** | 跨页面共享机制是独立交付对象，具体页面仍按修改计量。 |
| A-F04 | 新增“业务连续性与灾备能力建设” | **吸收** | 建设与验证、基础设施与应用机制是不同对象。 |
| A-F05 | 新增“性能与可靠性工程” | **吸收** | 补齐性能验证发现问题后的跨切面实施工作。 |
| A-F06 | 新增“技术债治理与结构性重构” | **吸收** | 具有明确质量目标和验收证据的重构不能虚构为功能修改。 |
| A-F07 | 新增“应用安全与隐私工程” | **吸收** | 补齐非业务数据类的安全控制建设。 |
| A-F08 | 把“目标环境兼容性验证”改为“兼容性与无障碍验证” | **吸收** | 无障碍验证不只是一个目标运行环境，改名后边界更完整。 |
| A-F09 | 在任务列表中继续用序号或名称引用工作类型 | **不吸收** | 名称和排序会随版本调整；下一版增加稳定“工作类型 ID”，Task 应引用 ID。 |
| A-F10 | 为漏洞修复、备份恢复和每项 WCAG 规则分别建类型 | **不吸收** | 分别由安全工程、灾备能力和可访问性能力覆盖；继续细分会把实现机制变成 StandardPD Key。 |

## v5.2 变更输入

1. 增加 7 个类型：数据生命周期治理、应用技术栈与依赖升级、无障碍与可访问性基础能力、
   业务连续性与灾备能力建设、性能与可靠性工程、技术债治理与结构性重构、应用安全与隐私工程。
2. 将“目标环境兼容性验证”改名为“兼容性与无障碍验证”。
3. 给全部工作类型增加稳定 ID；后续版本改名或排序不复用旧 ID 指代新语义。
4. 不增加协议、依赖、漏洞、备份、WCAG 规则等实现机制类型。

本批次产生了新的有效改进建议，因此 v5.1 尚未稳定，进入 v5.2。
