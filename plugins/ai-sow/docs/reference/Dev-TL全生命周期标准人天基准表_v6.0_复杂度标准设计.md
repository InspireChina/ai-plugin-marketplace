# Dev / TL 全生命周期标准人天基准表 v6.0：复杂度标准设计基线

- 状态：设计基线，待评审
- 日期：2026-09-02
- 基础版本：[v5.4 模式校准稿](Dev-TL全生命周期标准人天基准表_v5.4_讨论稿.md)
- 适用对象：后续 v6.0 复杂度标准、案例复核和参数校准
- 计量方式：基础表不使用 `quantity`；真实任务清单每个基础工作单元实例一行

> 本文定义 v6.0 的复杂度判断结构和验收边界，不修改 v5.4 的 71 个工作类型、工作模式、基础人天或当前插件模板。本文也不替代当前 SOW v1.3 和项目模板的计算权威。

## 1. 目标

v6.0 在 v5.4 的基础上补齐以下能力：

1. 为 71 个工作类型分别提供可复核的 `S / M / L / X` 判断标准；
2. 同时使用定量锚点和定性约束，不用单一主观描述或总分代替专业判断；
3. 明确“新建 / 调整 / 接入复用”三种模式下复杂度所衡量的范围；
4. 覆盖每个实际适用的“工作类型 × 工作模式”组合，不为 `-` 模式虚构复杂度标准；
5. 复用真实案例进行多轮拆分、判档和反向校正规则，直到结论稳定、边界明确、用语统一；
6. 区分行业标准可以支持的原则与必须由组织历史数据校准的内部参数。

## 2. 不变边界

除非案例复核证明存在明确缺陷，v6.0 继承 v5.4 的以下内容：

- 71 个工作类型 ID、分类、中文名称和计量单位；
- 每个工作类型适用的工作模式；
- “新建 / 调整 / 接入复用”的 M 档基础人天；
- 标准交付对象、模式化完成标准和说明；
- 一行 Task 对应一个独立基础工作单元实例，不设置数量字段；
- `X` 不进入正式估算，必须先拆分、澄清或形成专题分析与设计。

v6.0 不把复杂度用作修补目录边界或合并多个独立交付对象的手段。若交付对象可以独立验收、发布或结算，应拆成多行 Task，而不是提高到 L。

## 3. 权威依据及可采用范围

| 来源 | 可吸收的原则 | 在 v6.0 中的使用方式 | 不用于证明的内容 |
|---|---|---|---|
| [ISO/IEC 14143-1:2007](https://www.iso.org/standard/38931.html) | 功能规模测量关注用户要求的功能，强调一致的测量概念 | 功能型工作优先按可观察的业务过程、数据交互和结果划定范围 | 不直接提供本表的人天或复杂度倍率 |
| [ISO/IEC 19761:2011（COSMIC）](https://www.iso.org/standard/54849.html) 与 [COSMIC Measurement Process](https://cosmic-sizing.org/cosmic-sizing/intro/measurement-process/) | 先确定测量目的、范围、分解层级和边界；按功能过程及 Entry、Exit、Read、Write 数据移动衡量功能规模；修改规模只计算新增、修改、删除部分 | 校准功能/API/数据类工作类型的“一个实例”边界；调整模式只度量实际变更范围；识别应拆分的独立功能过程 | 不机械把 CFP 转换为本表 PD，也不要求所有非功能工作使用 COSMIC |
| [ISO/IEC/IEEE 32430:2025](https://www.iso.org/standard/86303.html) | 非功能规模与功能规模互补，需避免重复计算 | 性能、安全、可靠性、兼容性、运维等约束单独作为定性升级条件或独立工作类型，不重复计入功能数量 | 不提供开发工时或复杂度系数 |
| [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) | 产品质量模型支持质量需求、设计目标、测试目标和验收标准的一致表达 | 用性能效率、可靠性、安全性、兼容性、可维护性等质量约束检查 L 档升级条件 | 不把九项质量特性简单相加成分数 |
| [ISO/IEC/IEEE 15939:2017](https://www.iso.org/standard/71197.html) | 测量过程应由信息需要驱动，定义测量项、应用方式并验证结果 | 记录复杂度判定依据、估算与实际偏差，定期验证规则与倍率是否有效 | 不提供通用的 S/M/L 阈值 |
| [GAO Cost Estimating and Assessment Guide](https://www.gao.gov/products/gao-20-195g) | 估算应有技术基线、产品导向 WBS、假设、数据、风险分析，并用实际结果更新 | 要求任务先形成可审查边界和假设；案例复核保留估算依据与偏差原因 | 不把政府项目方法直接等同于本表的逐 Task 人天算法 |
| [NASA SWE-015](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695400/SWE-015%2B-%2BCost%2BEstimation) 与 [NASA SWE-142](https://swehb.nasa.gov/spaces/SWEHBVC/pages/50888972/SWE-142%2B-%2BSoftware%2BCost%2BRepositories) | 小型任务可以结合类比和本地校准；历史库应保存计划/实际规模、工时、复杂度及成本驱动因素 | 用历史 Task 实绩验证倍率，记录偏差和影响因素，避免仅凭专家记忆长期固化参数 | 不提供适用于本组织的固定倍率 |
| [IFPUG SNAP](https://ifpug.org/ifpug-standards/snap) | 非功能规模应补充功能规模；资源预测依赖历史生产率 | 检查功能范围与非功能约束是否缺项，并用历史生产率做本地校准 | 不把 SNAP 点数直接换算成本表 PD |

由此得到两个明确结论：

1. 行业标准可以支持“先确定边界、功能与非功能分开、使用可观察测量项、用历史实绩校准”的方法；
2. `S = 0.6 / M = 1.0 / L = 1.5` 是当前内部经验参数，不是 ISO、COSMIC、NASA、GAO 或 IFPUG 给出的通用结论。

## 4. 复杂度模型

采用“工作类型专属标准 + 工作模式范围覆盖 + 统一决策算法”的混合模型。

### 4.1 工作类型专属标准

每个工作类型必须单独列出：

| 字段 | 要求 |
|---|---|
| 工作类型 ID | 与 v5.4 稳定 ID 完全一致 |
| 主要计量维度 | 2～5 个与该类型直接相关的可观察维度，不罗列无关通用因素 |
| S（简单） | 给出本类型内部的定量上限，并同时说明允许的定性约束 |
| M（标准） | 给出常见范围的定量区间和典型约束；作为默认档 |
| L（复杂） | 给出仍属于一个独立实例的定量上限，或任何一个不可被平均抵消的强约束 |
| X / 拆分条件 | 多个独立交付对象、边界不明、关键前提缺失，或超出该基础单元承载范围时的处理 |
| 模式适用说明 | 说明本类型在调整或接入复用时是否需要覆盖规则之外的专门口径 |

定量锚点优先选择实例内部的状态、规则、数据组、映射、场景、角色、环境、资源、依赖或验证矩阵。不得用“代码行数”“文件数量”“开发人数”作为跨类型通用尺度。

定性约束描述定量数量无法表达的成本驱动因素，例如：

- 一致性、幂等、补偿、状态恢复和零停机；
- 高敏感数据、强监管、职责分离和防篡改审计；
- 严格性能、可用性、恢复目标或业务连续性；
- 跨团队、外部方、联合窗口和受限测试环境；
- 多语言、从右向左书写、无障碍、遗留兼容或多终端矩阵；
- 高风险迁移、复杂回滚和大规模数据核对。

### 4.2 工作模式范围覆盖

复杂度始终衡量“当前 Task 这一行实际负责的交付范围”，不能跟随目标系统的总体复杂程度。

| 工作模式 | 复杂度计量范围 | 不计入当前 Task 的范围 |
|---|---|---|
| 新建 | 新交付对象从无到有形成标准交付结果所需的全部范围 | 与该对象无独立交付关系的存量系统复杂度 |
| 调整 | 已有对象中本次新增、修改、删除的内容，受影响路径，以及完成本次调整必须执行的回归范围 | 未发生变化且无需因耦合重新验证的整个存量对象 |
| 接入复用 | 本项目侧的注册、配置、封装、映射、适配、认证、租户设置、权限设置和专项验证 | 保持不变的共享平台、外部能力或公共组件内部实现 |

每个 v5.4 标记为适用的模式都必须可以判定 `S / M / L`。标记为 `-` 的模式不生成 Task，也没有复杂度档位。v5.4 当前共有 71 个工作类型和 155 个适用的“工作类型 × 工作模式”组合，v6.0 必须逐一覆盖。

若共享能力本身要调整，同时本项目还要完成接入，必须拆为两行：

```text
共享能力调整 Task：复杂度只看共享能力的实际变更和必要回归
项目接入复用 Task：复杂度只看本项目侧接入、配置、映射和专项验证
```

### 4.3 统一决策算法

所有工作类型按同一顺序判定：

```text
1. 先检查 X：是否含多个独立实例、边界不清或关键前提缺失。
2. 按工作模式确定本 Task 的实际计量范围。
3. 使用该工作类型的专属定量锚点和定性约束判断。
4. 命中任一明确 L 强约束时判 L，不允许其他简单因素把它平均为 M。
5. 仅当主要定量指标全部落入 S，且没有 M/L 定性约束时判 S。
6. 未命中 X、S 或 L 时判 M。
```

不采用跨维度加权总分。原因是高敏感数据、零停机、强监管、严格恢复目标等单项约束不能被“页面少”“字段少”等低分项抵消。

### 4.4 定量与定性冲突

定量锚点表示常见规模，定性约束表示交付风险和验证强度。两者冲突时按以下规则处理：

- 数量落入 S，但命中 M 或 L 定性条件：按较高档；
- 数量落入 L，但工作内容实际由成熟机制自动完成：除非专属标准明确允许降档，否则仍按 L；成熟机制应优先体现为“接入复用”或较小调整范围；
- 数量超过 L，但仍可分成独立交付对象：判 X 并拆分；
- 数量超过 L，但不能合理拆分且仍是单一原子结果：在该类型标准中明确 L 的开放上限和适用条件，不临时使用例外；
- 事实不足以判断：判 X，补充证据，不默认 M。

## 5. S、M、L、X 的统一语义

| 档位 | 统一语义 | 使用要求 |
|---|---|---|
| S | 同类工作中明显低于标准实例，范围小、依赖少、规则直接、验证矩阵有限 | 必须写出低于 M 的具体事实；不能只写“简单” |
| M | 本类型最常见、边界清楚、约束常规的标准实例 | 默认档；不保存复杂度理由 |
| L | 仍为一个独立实例，但规模接近单元上限，或存在明显增加设计、实现、协调、验证工作的强约束 | 必须写出高于 M 的具体事实及对应标准 |
| X | 不是可直接估算的复杂档位；表示应拆分、应澄清或应先完成专题分析/设计 | 不应用复杂度系数，不进入正式任务估算 |

复杂度理由只记录实例事实，不复制标准原文。例如：

```text
复杂度=L：该业务操作包含 6 个相互转换的状态，并要求失败后幂等重试和人工补偿；
相较 M 档的常规多规则事务，状态恢复和补偿验证显著扩大。
```

## 6. 倍率状态与历史校准

v6.0 初稿暂时沿用：

| 档位 | 当前倍率 | 参数状态 |
|---|---:|---|
| S | 0.6 | 内部经验参数，待历史实绩校准 |
| M | 1.0 | 基准参数 |
| L | 1.5 | 内部经验参数，待历史实绩校准 |

正式使用时，倍率仍由项目模板管理；基础文档只说明口径和状态，不成为第二计算权威。

历史校准数据放在独立任务实绩或分析数据中，不增加到基础表，也不引入 `quantity`。每个样本至少保留：

- 工作类型 ID、工作模式、复杂度和复杂度理由；
- 估算时使用的 M 档基础人天和倍率；
- 实际 Dev / TL 有效投入人天；
- 返工、等待、需求变化、外部阻塞等不可归因于复杂度标准的偏差原因；
- 是否按相同基础单元边界完成，是否中途发生拆分或合并。

校准时先剔除范围变化和不可比样本，再按工作类型族、工作模式和复杂度观察实际人天相对 M 档基础人天的分布。样本不足时保留“待校准”状态，不因少数极端案例直接修改全局倍率。任何倍率调整都应单独评审，并同步模板、参数状态和回归案例。

## 8. 案例迭代设计

使用同一组案例反复验证规则，避免每轮更换案例导致结论不可比。至少覆盖：

1. 系统多语言支持：国际化机制、页面/模板适配、资源处理、兼容验证；
2. SSO 或统一身份接入：身份系统、业务权限、用户映射、专项验证；
3. 订单或交易功能：页面、组件、查询 API、业务操作 API、数据模型和发布；
4. 跨系统数据同步与数据权限：集成、同步、对账、安全和监控；
5. 自动化测试与测试工具：测试框架、用例、数据和环境；
6. CI/CD、IaC 与基础设施：流水线、运行环境、资源栈、治理和发布；
7. 数据迁移、切换与回滚：迁移、核对、发布切换和下线；
8. 生产问题诊断、同一根因整改和运维交接。

每轮按以下顺序执行：

```text
按真实交付对象拆成一行一个 Task
→ 选择工作类型和工作模式
→ 检查 X
→ 根据定量与定性标准判 S/M/L
→ 复核是否重复计量或遗漏工作类型
→ 记录规则无法解释、不同人可能得出不同结论的点
→ 只吸收可泛化且不破坏既有边界的建议
→ 用同一案例集重新回归
```

建议至少完成三轮：

- 第一轮检查完整性：是否缺工作类型、缺模式口径或缺关键计量维度；
- 第二轮检查一致性：相近工作类型、三种模式和 S/M/L 档位是否使用同一语义；
- 第三轮检查稳定性：同一事实在不查看上轮答案时能否得到相同拆分和判档。

达到以下全部条件才可标记为“稳定候选”：

- 71 个工作类型均有专属 S/M/L/X 标准；
- 155 个适用模式组合全部有明确计量范围；
- 所有案例均可拆成独立 Task，且没有用 L 代替应拆分的 X；
- 连续两轮没有新增工作类型或改变核心档位定义；
- 同类定量术语、区间边界和定性升级条件不存在相互矛盾；
- 仍需历史数据验证的倍率明确标记为“待校准”，没有伪装成外部标准结论。

## 9. 验证要求

正式 v6.0 生成后必须执行机械检查：

- v5.4 与 v6.0 的 71 个工作类型 ID、模式和 M 档基础人天逐行一致，除非案例复核文件记录并批准变更；
- 71 个复杂度标准行 ID 唯一、无遗漏、无多余；
- 每行 `S / M / L / X` 和主要计量维度均非空；
- 155 个适用模式组合都有覆盖说明，`-` 模式没有被误写为适用；
- 不出现 `quantity` 字段或按数量乘基础人天的口径；
- 文档内相对链接可解析；
- 运行仓库根测试、仓库验证器和 `git diff --check`。

## 10. 评审决策

本设计选择混合模型，不选择以下两种方案：

- 仅使用全局评分卡：难以表达工作类型差异，强约束可能被其他低分项抵消；
- 为 155 个模式组合分别复制完整 S/M/L/X 表：重复内容过多，后续容易发生同义规则漂移。

混合模型把“不同工作类型测什么”放在 71 行专属标准中，把“不同模式测哪一部分”放在统一覆盖规则中；只有确有差异的工作类型再写模式例外。这样既能逐组合覆盖，又能保持标准统一和可维护。
