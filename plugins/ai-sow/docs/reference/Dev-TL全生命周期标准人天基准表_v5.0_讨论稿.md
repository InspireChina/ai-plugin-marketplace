## 生命周期案例拆分与目录复核

以下案例用于检验目录边界，不代表具体项目承诺。每一行都是一个可独立估算、验收的 Task 实例；
普通详细设计、编码、Unit Test、开发自测、常规异常处理和代码评审仍包含在主工作单元内。
表中的 PD 是标准复杂度下的基准值；“候选新增”表示当前 56 行尚无准确类型，不能为了完成映射而硬套到相近条目。

### 案例一：现有业务系统支持中英文

需求边界：现有中文 Web 系统新增英文界面，支持用户切换语言、日期和数字本地化、英文业务文档、
缺失翻译回退，并在目标浏览器中完成验证。

| 工程化覆盖 | 部分完整 | CI/CD、IaC、运行环境和可观测性方向正确，但缺应用工程初始化，且资源栈与共享平台边界混合。 |
| 生产与退役覆盖 | 不完整 | 有发布、迁移执行、复盘和 RCA，但缺生产故障恢复与系统退役。 |
| 参数成熟度 | 可用于讨论，不宜定稿 | 多数相对大小合理，但复用组件、跨系统集成、指标数据集、测试工具和 RCA 偏低；发布任务存在重复。 |

结论：56 行作为讨论基线是成立的，但还不能视为完整且互斥的正式目录。按下述建议，目录将从
56 行增加 8 个类型，同时合并 1 组重复类型，形成 **63 个候选标准工作类型**。

### 建议增补的工作类型

| 候选工作类型 | 建议分类 | 计量单位 | 新增 PD | 修改 PD | 适配 PD | 增补理由与边界 |
|---|---|---|---:|---:|---:|---|
| 国际化与本地化基础能力 | 应用共性能力 | 每应用 / 本地化机制 | 2.0 | 1.0 | 1.0 | 覆盖资源加载、Locale 解析、回退、格式化和翻译发布机制；具体页面、文档和兼容性验证仍分别计量。 |
| 应用工程初始化与开发规范接入 | 工程化 | 每应用 / 代码库 | 2.0 | 1.0 | 1.0 | 覆盖工程骨架、依赖管理、本地开发、静态检查和质量门禁；不包含 CI/CD 和运行环境。 |
| 应用配置与功能开关 | 应用共性能力 | 每配置域 / 开关组 | 1.5 | 1.0 | 0.5 | 只用于可发布、可回退、可验证的配置或开关能力；普通常量和单一环境变量包含在主工作单元中。 |

### 建议调整的类型名称与边界

| 当前类型 | 建议调整 | 原因 |
|---|---|---|
| 文件处理 API | 改为“文件传输接口” | 文件解析、数据导入、数据输出和文档生成已有独立类型；本类型只保留上传、下载和传输契约，避免重复。 |
| 外部系统接口集成 | 改为“跨系统业务集成” | 内部系统、集团系统和共享平台同样可能形成独立集成，内外部属性不应决定基础类型。 |
| 数据清洗与转换 | 改为“独立数据加工与转换” | 强调只有独立可运行、可验收的数据结果才单列；迁移、导入、同步内部步骤不重复计量。 |
| 构建与发布自动化 | 保留类型，明确模式边界 | 新增用于从零建立模板或流水线，修改用于改变既有行为，适配用于应用接入既有模板。 |
| 基础设施环境建设 | 改为“基础设施资源栈建设” | 收窄为一个可独立部署和验收的资源栈；共享平台能力移入新增类型。 |
| 生产上线技术准备 + 生产上线实施方案 | 合并为“生产发布与切换方案” | 两者通常共同形成一次 Release 的就绪、部署、切换、回滚和验证包，分别计量容易双算。 |

分类层级也建议从单一“功能开发”拆成“功能与接口、集成与数据、身份安全与治理”，仅用于浏览和统计，
不参与 StandardPD 查表。

### 建议调整的基准参数

| 工作类型 | 当前 新增 / 修改 / 适配 | 建议 新增 / 修改 / 适配 | 调整理由 |
|---|---:|---:|---|
| 可复用应用组件或程序库 | 1.0 / 0.5 / 0.5 | **1.5 / 1.0 / 0.5** | 真正可复用资产通常包含稳定接口、示例、文档和独立验证，当前新增与修改值偏低。 |
| 外部系统接口集成（建议改名） | 2.5 / 2.0 / 1.5 | **3.0 / 2.0 / 1.5** | 新增集成通常额外承担契约、认证、映射、异常和联调；适配既有能力维持 1.5。 |
| 业务指标与看板数据集 | 1.5 / 1.0 / 1.0 | **2.0 / 1.5 / 1.0** | 标准交付通常包含口径实现、聚合、校验和发布，工作量不应低于普通数据加工。 |
| 自动化测试支撑工具 | 1.5 / 1.0 / 1.0 | **2.0 / 1.0 / 1.0** | 可复用 Mock、数据生成或 Test Harness 的新增成本与独立程序库相近。 |
| 生产问题根因分析（RCA） | 1.0 / - / - | **1.5 / - / -** | 标准 RCA 应包含证据、时间线、根因验证、影响和改进项；简单问题可再乘简单复杂度系数。 |
| 生产上线技术准备 + 生产上线实施方案 | 1.5 + 1.5 / 1.0 + 1.0 / - | **合并后 2.0 / 1.0 / -** | 降低同一 Release 交付包重复计量，同时保留正式发布方案成本。 |

其余参数在八个案例中没有出现明显的相对失衡，可以暂时保留，等待历史项目数据校准。
特别是基础设施、迁移和生产执行，实际跨度很大，不能仅靠提高基础 PD 解决，必须配合复杂度和拆分条件。

### 参数使用前还需补齐的公共规则

1. **标准 PD 的包含边界：** 每个开发型 Task 默认包含必要设计、实现、Unit Test、开发自测、基本联调、
   常规异常处理和评审修正；只有形成独立正式成果的方案、自动化测试、联调或验证才能另行计量。
2. **工作模式边界：** “适配”只用于既有能力保持不变、项目侧存在可独立验收的配置、映射、封装、认证、
   环境接入或专项验证；普通依赖引入和普通调用不生成 Task。
3. **复杂度建议：** 简单 0.6、标准 1.0、复杂 1.5。简单或复杂必须写出相对标准实例的具体差异，
   不能只凭主观判断选择。
4. **超范围条件：** 一个 Task 同时包含多个独立页面、业务事务、数据域、系统、环境、资源栈或发布批次时，
   应先拆成多行；无法形成稳定边界时标记为 X 并澄清，不能用复杂度掩盖范围不清。
5. **实际投入例外：** War Room 待命、专职驻场、固定班次、多人并行切换和 24×7 支持属于服务容量，
   不按本表固定 PD 估算；需要按明确的人员与实际投入时间单独处理。

### 本轮建议

- 原 56 行继续保留为 v5.0 讨论基线，不立即改号，便于逐项评审。
- 下一版候选目录按“新增 8 项、合并 1 组、调整 6 组参数”的范围形成 v5.1 草案。
- 在进入模板前，至少使用 3 至 5 个已完成项目的实际 Task 与耗时进行回放，分别校准新增、修改和适配；
  没有历史数据支撑前，上述 PD 仍是结构化专家判断，不应表述为统计结论。
