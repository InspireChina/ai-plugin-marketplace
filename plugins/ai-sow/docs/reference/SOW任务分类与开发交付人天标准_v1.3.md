# SOW 任务分类与开发交付人天标准

状态：v1.3 当前标准（插件 0.1.0-beta.1）

日期：2026-09-03

适用插件版本：0.1.0-beta.1

SOW 标准版本：v1.3

## 1. 权威来源与适用边界

本文解释 Task 的分类、拆分、字段、判断方法和验收原则，不保存当前基础单元目录，也不复制基础人天、S/M/L/X 判定矩阵、公式、取整或汇总规则。上述 Task 专业标准只以运行时模板的 `90-估算标准` Sheet 为权威；需要查看当前可选项或数值时，应打开模板，而不是从本文推断。

当前只支持 XLSX 模板。项目模板位于 `.ai-sow/templates/sow-template.xlsx`；每轮运行开始时，系统把它冻结为本轮专用副本 `.ai-sow/work/run-template.xlsx`，后续编译与评审均使用该副本。项目模板发生变化时，下一轮必须重新编译 Delivery 并重新评审，不能沿用上轮 Delivery；发布后的生成包还会保存 `input/sow-template.xlsx` 及其哈希，以闭合输入证据。

本文中的例子只帮助理解判断过程，不是目录、默认人天或复杂度规则的替代来源。模板与本文冲突时，以模板为准。

## 2. 交付层级与基本对象

交付层级统一为 `Epic → Feature → Story → Task`。

```text
Epic
  └── Feature
        └── Story
              └── Task

Task ──选择──> 基础单元
任务族 ──包含──> 基础单元
Story ──关联──> Integration
集成 Task ──integrationId──> Integration
```

- **Epic**：围绕同一业务结果或技术目标的一组 Feature。
- **Feature**：可以独立纳入、排除、延期和评审的需求范围。
- **Story**：相对有效起点仍需交付、可独立验收和结算的结果。
- **Task**：Story 下直接估算的最小明细。一行 Task 对应一个基础单元实例。
- **基础单元**：模板定义的标准工作类型；Task 选择基础单元后，任务族由模板关系确定。

Story 不保存任务类型。前端、后端、数据、集成、测试、迁移和共性技术能力等性质由子 Task 表达。Task 描述一个完整交付对象，不把设计、实现、自测和基本联调机械拆成多行，也不以复杂度表达对象数量。

## 3. Task 最小字段

| 字段 | 含义 | 填写要求 |
|---|---|---|
| `taskId` | Task 稳定标识 | 语义未变时保持稳定；实质含义变化时创建新 ID |
| `storyId` | 所属 Story | 必须引用已通过自动终审的 Story |
| `taskKind` | Task 类型 | 只使用 `DESIGN` 或 `IMPLEMENTATION` |
| `name` | 可读名称 | 使用简体中文说明交付对象和单一基础单元实例 |
| `baseUnit` | 基础单元 | 从本轮模板 `90-估算标准` 的有效目录选择 |
| `workMode` | 工作模式 | 只使用 `新建`、`调整`、`接入复用` |
| `workModeRationale` | 工作模式理由 | 结合当前实例与 Effective Start 说明选择依据 |
| `workModeEvidence` | 结构化现状证据 | `调整` 或 `接入复用` 时必填；精确引用一个 `effectiveStartItemId` |
| `complexity` | 稳定复杂度 | 只使用 `S`、`M`、`L`，并按模板的基础单元专属标准判断 |
| `complexityRationale` | 复杂度理由 | `S` 或 `L` 时必填并说明偏离 M 档的事实；`M` 时不得填写 |
| `acceptanceCriterionIds` | AC 引用 | 至少引用一条同 Story 的 AcceptanceCriterion |
| `designItemIds` | Design Item 引用 | 引用本 Task 实现或补齐的 Design Item；不适用时为空集合 |
| `integrationIds` | Integration 引用 | 引用本 Task 实现或约束的 Integration；不适用时为空集合 |
| `nfrIds` | NFR 引用 | 引用本 Task 满足或设计的 NFR；不适用时为空集合 |
| `rationale` | 单实例边界 | 说明计数对象、包含范围和排除范围 |

Task 不保存任务族、数量、活动、人天、倍率或公式结果。任务族和计算值由模板投影；稳定业务 JSON 不成为第二套计算权威。

`workModeEvidence` 对 `新建` 禁止，对 `调整` 和 `接入复用` 必填。两种模式都必须包含
`effectiveStartItemId`；`接入复用` 还必须包含非空 `projectSideWorkTypes` 和
`projectSideWorkCommitment`，而 `调整` 不得携带这两个接入复用字段。

## 4. 拆分与判断顺序

每个 Task 按固定顺序判断：

1. 明确相对有效起点仍需交付的单一对象及其验收边界。
2. 在本轮模板的有效目录中选择最匹配的基础单元。
3. 判断工作模式，并为 `调整` 或 `接入复用` 提供可核验依据。
4. 按该基础单元在模板中的专属复杂度标准选择稳定值 `S`、`M` 或 `L`；命中 X/拆分条件时按模板要求拆分、澄清或形成有边界的设计/调研 Task。
5. 补齐适用的 Integration 引用、依赖和完成标准。
6. 如果范围、现状或复杂度驱动因素仍不明确，提出自包含问题；问题必须同时说明为什么要问、答案决定什么和未回答后果。

模板中的基础单元目录与 M 档基础人天合并为一张表；使用者不应把目录和数值重新抄入 Markdown。统一复杂度系数（例如命名项 `K_COMPLEXITY_S`）及其公式也由模板拥有，生成器只投影结构化输入并保留公式。

## 5. 工作模式

工作模式只使用 `新建 / 调整 / 接入复用`；具体是否可选仍由本轮模板约束。

### 5.1 新建

适用于没有可复用有效起点，需要形成新的可验收交付对象的情况。判断重点是对象是否从无到有，而不是代码文件是否全新。

### 5.2 调整

适用于已有对象仍然有效，但需要在其上修改、扩展或修复。必须说明现状位置、已有能力、拟改范围和保持不变的边界；没有现状证据时不能仅凭措辞选为 `调整`。

### 5.3 接入复用

适用于已有能力原则上可以直接使用，本次工作主要是接入、映射、参数配置、适配或验证。必须证明被复用能力确实存在并满足约束；若需要实质重构或新增主体能力，应改用相应基础单元与工作模式。

替换、迁移、切换和退役不是工作模式。它们应按照实际交付对象拆成明确 Task，并分别选择适用的基础单元。

## 6. 复杂度

稳定 `complexity` 只允许 `S / M / L`。这些值表示同一基础单元内部的复杂度档位，不是跨基础单元比较规模的通用标签。判断时只使用该基础单元在本轮模板中列出的驱动因素与门槛，并按合同在 `complexityRationale` 中记录偏离 M 档的证据。

- `S`：满足该基础单元的小型情形。
- `M`：满足标准情形，也是模板中基础人天的档位语义。
- `L`：满足该基础单元的大型情形。

模板列名中的 `X/拆分条件` 不是稳定 `complexity` 值。命中该条件时必须拆分、澄清，或形成范围明确的设计/调研 Task；不得把 `X` 写入稳定 Delivery。

以下因素不能单独作为提高复杂度的理由：团队熟练度、排期紧张、一般沟通成本、未定位的不确定性或把多个对象压在同一 Task。多个对象应拆分；未定位不确定性应进入问题、前提或 Uncertainty。

## 7. Integration、SIT、UAT 与不确定性

- Integration 是独立稳定对象，用于描述系统边界、方向、协议、所有者和责任；集成类 Task 通过 `integrationIds` 引用它，不复制其事实。
- SIT 和 UAT 的范围、轮次、责任与证据按模板和批准数据投影，不在 Task 中硬编码通用人天。
- 当未知项会改变范围、方案、基础单元、工作模式、复杂度、Integration 引用或验收边界时，应记录 Uncertainty，并设置 `affectsEstimate = true`。
- `affectsEstimate = true` 的问题未解决时，不得给出最终正式估算；系统应生成可读评审材料，由用户基于自然语言结论或可打开的 Markdown、Excel 文件确认。

## 8. 工作簿字段与计算边界

生成器把已批准的 Epic、Feature、Story、Task、Integration、SIT、UAT、风险、前提和追溯关系投影到模板。所有基础人天、复杂度系数、公式、跨 Sheet 引用、风险计算、取整与汇总只来自模板。

概念关系如下；它用于解释，不授权 Python 或 JSON 复制模板数值：

```text
Task 人天 = 模板中该基础单元与工作模式的 M 档基础人天 × 模板复杂度系数
Story 人天 = Story 下全部 Task 人天之和
```

填表逻辑必须保留命名 Table、公式原型、样式、行高、自动筛选和跨 Sheet 引用，并通过重新打开工作簿验证。普通文本即使以 `=`、`+`、`-` 或 `@` 开头，也必须按文本安全写入。

## 9. 非权威示例

以下例子只演示拆分思路，所用基础单元名称是否有效、适用模式、复杂度档位和人天都必须回到本轮模板确认。

### 9.1 单一页面调整

若已有页面只需改变一个可独立验收的展示行为，可以创建一个 Task，记录现状证据并考虑 `调整`。若同一 Story 还需要新增独立接口或数据迁移，应分别建 Task，不把多个交付对象塞入一行。

### 9.2 复用既有服务

若现有服务契约和能力已经满足目标，本次仅做调用接入、字段映射与联调，可以考虑 `接入复用`。若服务主体能力也要新增或重构，则需要独立 Task，不能用 `接入复用` 掩盖新增范围。

### 9.3 系统替换

“替换旧系统”本身不是一个工作模式。应按实际范围拆出新能力、数据迁移、切换、验证和退役等可验收对象；每个对象分别从模板选择基础单元、模式和复杂度。

## 10. 质量门禁

Task 候选在发布前至少满足：

- 每行只有一个基础单元实例，且属于已批准 Story。
- `baseUnit`、`workMode` 和 `complexity` 对本轮模板有效。
- `调整` 与 `接入复用` 有可核验现状依据。
- 适用的 Integration 引用完整且指向稳定数据。
- 复杂度理由对应模板的基础单元专属标准。
- 所有影响估算的问题、前提和不确定性已关闭，或明确阻塞正式估算。
- 系统已完成自动 fresh-context Reviewer 终审；只有确实需要用户输入或确认时，才通过自然语言结论或可打开的 Markdown、Excel 文件展示内容，内部 packet 与 hash 不作为用户审批对象。

## 11. 维护规则

- 修改 Task 专业标准时，只更新 XLSX 模板的 `90-估算标准`，并同步模板哈希、fixture、副本和生成测试。
- 修改概念、字段或评审合同，才更新本文及相关公开文档。
- 不在本文增加当前目录总数、逐行基础单元清单、人天矩阵或 S/M/L/X 全量规则。
- 模板变化后的运行必须冻结新副本、重新编译 Delivery、重新评审并生成新的输入证据；不得把模板变化降级为只重渲染。
