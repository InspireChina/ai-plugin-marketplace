# SOW 任务分类与开发交付人天标准

状态：v1.3 评审稿（模板尚未发布）

日期：2026-08-21

适用插件版本：0.1.0

SOW 标准版本：v1.3

维护说明：本文件负责解释任务分类、拆分、填写、验收与估算规则；数值、公式和可选组合的计算依据是同版本的 [SOW 模板](../../skills/setup/assets/sow-template.xlsx)。面向 PMO 与财务评审的仿真 Brownfield 参考结果见 [SOW 估算与生成示例](SOW估算与生成示例_v1.3.xlsx)。

## 1. 背景与结论

现有 Task 估算同时使用 Story 类型、专业域、活动、基础单元、数量、工作模式和复杂度。这些维度有不少重复：一个 Story 可能同时涉及前端、后端和系统对接；设计与实现通常成套出现；数量字段会把多个实际交付对象挤在同一行；统一的工作模式倍率也无法准确反映不同基础单元在新建、调整和接入复用时的成本差异。把替换和下线也当作工作模式，还容易漏掉数据迁移、发布切换和旧功能下线等工作。

本设计选择以下模型：

1. 交付层级统一为 `Epic → Feature → Story → Task`。
2. Story 不再具有类型；一个 Story 可以包含任意任务族的 Task。
3. 任务类型保留两层：`任务族 → 基础单元`。
4. 一个 Task 对应一个基础单元实例的完整工作。
5. Task 只保存基础单元；系统根据基础单元自动确定任务族。
6. 删除活动和数量。
7. `基础单元 + 工作模式` 选择 M 档基础人天；复杂度按基础单元专属标准判断，再通过统一系数调整。
8. Task 工作模式只保留 `新建 / 调整 / 接入复用`；替换和退役通过明确基础单元拆分，不作为工作模式。

最终公式为：

```text
Task 人天 = M档基础人天（基础单元，工作模式） × 复杂度系数
Story 人天 = Story 下全部 Task 人天之和
```

## 2. 目标

1. 让每行 Task 对应一个可识别、可追溯、可估算的交付对象。
2. 消除 Story 类型、任务族、活动和数量之间的重复表达。
3. 让不同基础单元拥有与其实际难度驱动因素匹配的复杂度标准。
4. 让工作模式改变基线，而不是依赖失真的全局倍率。
5. 继续以工作簿中的基础人天、系数、公式、取整和总计作为唯一计算依据。
6. 以后可以根据实际项目数据逐步校准基础人天，而不改变正式数据格式所表达的含义。

## 4. 交付层级与对象

```text
Epic
  └── Feature
        └── Story
              └── Task

Task ──选择──> 基础单元
任务族 ──包含──> 基础单元
Story ──关联──> Integration
集成 Task ──integrationId──> Integration
```

### 4.1 Epic、Feature 与 Story

- **Epic**：围绕同一业务结果或技术目标的一组 Feature。
- **Feature**：可以独立纳入、排除、延期和评审的最小需求范围。
- **Story**：相对有效起点仍需交付、可独立验收和结算的结果。
- Story 不保存类型。前端、后端、数据、集成、测试、迁移和共性技术能力等性质由子 Task 表达。
- 每个 Story 至少有一个 Task；验收条件与 Task 不要求一一对应。

### 4.2 Task

Task 是 Story 下直接估算人天的最小明细。一行 Task 对应一个基础单元实例需要完成的全部工作，而不是其中某个单独步骤。

对普通开发类基础单元来说，完整工作通常包括必要的设计、实现或配置、开发自测、单元级验证、技术说明和基本联调。架构、调研和支持类基础单元以达到各自的完成标准为准，不要求一定产生代码。

一个 Task 必须满足：

- 只有一个基础单元实例；
- 具有清晰的目标对象和工作范围；
- 只有一种工作模式和一个复杂度结论；
- 重复实例拆成多个 Task；
- 只有计数口径明确允许的基础单元可以覆盖多个紧密相关对象。

## 5. Task 数据模型

| 字段 | 必填 | 说明 |
|---|---|---|
| `taskId` | 是 | 固定且唯一的 Task ID |
| `storyId` | 是 | 所属 Story |
| `name` | 是 | 具体交付对象和工作范围 |
| `baseUnit` | 是 | 基础单元的固定值或 ID |
| `workMode` | 是 | `新建 / 调整 / 接入复用` |
| `workModeRationale` | 是 | 工作模式判断及现状依据 |
| `workModeEvidence` | 调整/复用必填 | 精确引用一项匹配的 Effective Start ID 和名称；接入复用还列出项目侧工作类型及标准正向交付承诺 |
| `complexity` | 是 | 正式数据只允许 `S / M / L` |
| `complexityRationale` | S/L 必填 | 说明哪些已知事实使当前实例偏离 M 档；M 档省略 |
| `integrationId` | 集成 Task 必填 | 内部或外部系统对接 Task 所实现的唯一 Integration；其他 Task 省略 |
| `matchedEffectiveStartItemIds` | 条件必填 | 对应的 Effective Start ID |
| `rationale` | 是 | 基础单元选择、工作范围及拆分理由 |

任务族不由使用者填写。模板根据 `baseUnit → taskFamily` 的对应关系自动带出，并以只读方式显示。

Story 删除 `type`。Task 删除以下字段：

- `professionalDomain`
- `activity`
- `quantity`

## 6. 任务类型目录

任务类型为两层目录：任务族用于组织、汇总和查漏补缺；基础单元用于实际选择、计数和估算。每个基础单元只能属于一个任务族，基础单元 ID 全局唯一。

基础单元使用符合中文习惯的交付对象名称，不用“包、组、集、边界”等后缀代替计数规则。一个 Task 可以包含多少工作，由计数口径、具体工作内容和复杂度标准共同确定。

本版目录包含 13 个任务族、37 个基础单元：

| 任务族 | 基础单元 |
|---|---|
| 前端 | 界面与交互；通用界面组件 |
| 后端 | 业务服务与接口；后台任务；事件与消息处理 |
| 数据与报表 | 数据模型与存储结构；报表与指标；数据处理流程 |
| 系统集成 | 内部系统对接；外部系统对接 |
| 质量验证 | 人工测试；自动化测试框架；自动化测试用例；性能与容量测试；安全与隐私测试；兼容性与无障碍测试 |
| 共性技术能力 | 国际化支持；身份与权限管理；安全与隐私保护；监控、追踪与审计；性能与稳定性保障；公共技术组件；配置与功能开关 |
| 工程平台 | 应用工程初始化；构建与部署流水线；运行环境；基础设施资源；开发工具与工程规范 |
| 数据迁移 | 数据迁移 |
| 发布与切换 | 发布切换；系统功能下线 |
| 问题处理 | 问题诊断与恢复；同一根因问题整改 |
| 架构设计 | 架构方案设计 |
| 分析与调研 | 专题调研 |
| 交付与移交 | 运维交接与操作手册；用户培训与使用材料 |

新增基础单元必须同时满足：

1. 有明确且可以重复使用的计数口径；
2. M 档基础人天与现有单元存在实质差异；
3. 可以定义可执行、可审计的 `S / M / L` 判断标准。

目录不设“其他”选项。现有基础单元无法准确描述工作时，先标记为 `X`，再拆分任务、澄清内容或补充目录。

## 7. 复杂度模型

### 7.1 含义

复杂度用于比较同一个基础单元、同一种工作模式下，当前任务与 M 档常规任务的难易差异。

先按该基础单元自己的标准判断复杂度，再使用模板中统一配置的系数。默认系数沿用当前设置：

| 复杂度 | 系数 |
|---|---:|
| S | 0.6 |
| M | 1.0 |
| L | 1.5 |

`X` 只在评审阶段使用，表示任务需要继续拆分、澄清，或者先完成调研和架构设计；标记为 `X` 的任务不能进入正式估算数据。

### 7.2 判断方法

1. 验证 Task 是否只包含一个基础单元实例。
2. 读取该基础单元的专属 `S / M / L` 标准。
3. 依据已知事实判断当前实例是否偏离 M 档。
4. 所有影响工作量的判断项都符合 S 档时，结果才是 S。
5. 只要有一项符合 L 档且会明显增加工作量，结果就是 L。
6. 其余已经明确、且没有超出当前基础单元范围的情况为 M。
7. S 或 L 必须说明导致下调或上调的事实；M 不填写复杂度理由。
8. 工作范围不清、超过 L 档上限或混入多个实例时为 X。

复杂度不得代替重复实例的数量，也不得表达未确认事项、人员经验、排期、一般管理沟通成本或工作模式本身。单个实例内部确实会增加实现和验证难度的状态数、规则数、依赖数等，可以作为复杂度判断依据。

### 7.3 复杂度说明怎么写

`complexityRationale` 的用途是解释为什么当前 Task 偏离默认 M 档，不是抄写一遍标准。只有 `complexity = S / L` 时必填；`complexity = M` 时省略。

理由必须写出造成偏离的具体事实，以及这些事实为什么足以让结果低于或高于 M。例如：

```text
复杂度=L：该界面包含6种相互转换的业务状态，并要求跨界面恢复未完成状态；
相较M档的3～5种状态和普通条件联动，状态机和恢复要求显著增加实现与验证范围。
```

S 档理由同样说明为什么明显简单于 M，例如“仅有一个只读正常态，使用现成组件，无条件联动和角色差异”。不接受复制标准、逐项罗列未造成偏离的 M 档事实，或使用“需求复杂”“工作量较大”“技术难度高”等无法复核的理由。

## 8. 各基础单元复杂度标准

下表列出各基础单元的判断依据和拆分上限。每行标准都针对一个基础单元实例；多个互相独立的对象必须拆成多个 Task，不能靠提高复杂度合并估算。命中“X / 拆分条件”时，先拆分任务、澄清范围，或者另立调研、架构设计及平台建设任务，不能直接套用 L 档系数。

### 8.1 前端

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 界面与交互 | 1～2 种主要状态；标准组件；简单校验；单一角色 | 3～5 种主要状态；条件联动；复杂表格、上传或多角色 | 复杂状态机；实时或离线处理；跨界面状态恢复；严格无障碍或多终端适配 | 包含多条可独立验收的交互流程，或跨多个应用 |
| 通用界面组件 | 单一基础组件；状态和样式少；沿用现有设计规范 | 一个组件及其紧密相关的状态变体；需要响应式、主题或无障碍适配 | 复杂组合组件；自定义交互和状态管理；跨应用使用；涉及版本兼容或扩展机制 | 包含多个可独立发布的组件，或需要建设完整组件库、设计规范体系 |

### 8.2 后端

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 业务服务与接口 | 单个业务对象的增删改查；简单规则；单一事务；标准权限 | 一个业务操作涉及多个业务对象；多条业务规则；异步处理或多角色权限 | 单个业务操作需要跨服务编排、复杂状态机、幂等补偿、高并发或严格一致性 | 包含多个可独立验收的业务操作，或需要跨多个服务分别交付 |
| 后台任务 | 单源单目标；简单调度；小数据量 | 多步骤依赖；重试续跑；中等数据量；需要监控 | 分片并行；严格批次窗口；断点恢复；大数据量或复杂补偿 | 包含多个可独立调度的任务，或需要建设调度平台本身 |
| 事件与消息处理 | 单生产者、单消费者；简单映射；允许重复 | 单一事件方向下存在多个相关操作或消费者；需要顺序、重试、幂等或死信处理 | 单一事件方向需要分布式事务、版本兼容、高吞吐或跨地域处理 | 包含多个独立事件方向或消息类别，或需要建设消息平台本身 |

### 8.3 数据与报表

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 数据模型与存储结构 | 1～2 个对象；简单关系和索引 | 一组必须同时演进的 3～6 个相关对象；多约束、索引和结构迁移 | 单一对象组存在复杂层级或图关系、分区分片、历史版本或零停机结构演进 | 包含多个可独立演进的业务对象组，或需要整体重构存储架构 |
| 报表与指标 | 单一来源；简单汇总；固定筛选 | 一张报表或一组同口径指标需要多表关联、计算、钻取或按角色过滤 | 单一验收范围需要统一多个来源口径、复杂计算、近实时、大数据量或严格审计 | 包含多张可独立验收的报表，或多组相互独立的指标口径 |
| 数据处理流程 | 单源单目标；简单映射；全量处理 | 一条流程包含多步转换、增量处理、质量规则和调度依赖 | 单一流程涉及多源血缘、CDC、流批结合、回放补数或严格时效 | 包含多条可独立调度的处理流程，或需要建设数据处理平台本身 |

### 8.4 系统集成

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 内部系统对接 | 同组织；稳定接口；单向；简单映射 | 一个交互方向包含多个相关操作；跨团队；需要认证、重试或版本管理 | 单一交互方向跨业务域；复杂一致性；联合发布或严格 SLA | 包含多个 Integration、多个交互方向，或对端系统改造也在本项目范围内 |
| 外部系统对接 | 文档完整；标准协议和认证；单向 | 一个交互方向包含多个相关接口；复杂映射；幂等重试；依赖外部测试环境 | 单一交互方向使用专有协议；复杂对账；多方协调；严格安全、性能或可用性 | 包含多个 Integration、多个交互方向，或外部方实现也计入本项目范围 |

### 8.5 质量验证

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 人工测试 | 约 10 条线性场景；单角色；环境和数据稳定 | 约 10 条场景中存在多分支、多角色、跨模块或专门数据准备 | 单一测试范围涉及跨系统异步、复杂权限或数据矩阵，并需要合规证据 | 场景明显超过约 10 条，且可以分成多个独立测试范围 |
| 自动化测试框架 | 标准技术栈；单应用；基础 CI 执行 | 单应用包含 UI 与 API 多层、测试数据准备、报告和并行执行 | 单应用需要多平台、服务虚拟化、大规模并行或复杂环境隔离 | 包含多个应用，或多类彼此独立的自动化测试框架 |
| 自动化测试用例 | 约 10 条稳定 API 或简单 UI 场景；固定测试数据 | 约 10 条场景存在分支流程、动态数据、异步等待或模拟外部依赖 | 单一场景组贯穿多个系统，存在复杂流程协同、外部依赖或非功能检查 | 场景明显超过约 10 条，或可以分成多个独立场景组 |
| 性能与容量测试 | 单接口或界面；单一负载模型；标准阈值 | 一个负载模型包含多场景、多指标、代表性数据和调优复测 | 单一测试范围涉及分布式链路、峰值和长稳模型、容量评估或生产级数据规模 | 包含多个独立负载模型，或需要长期专项调优 |
| 安全与隐私测试 | 标准扫描；单应用；常见配置检查 | 认证授权、API 和数据流专项验证；部分人工检查 | 高敏感数据；威胁建模；较深人工验证；需要较强合规证据 | 需要由独立专业团队开展正式渗透测试或认证，或包含多个独立测试范围 |
| 兼容性与无障碍测试 | 单浏览器或设备；标准检查 | 一个明确矩阵内的多浏览器或设备、响应式、键盘和读屏验证 | 单一产品范围涉及较大兼容矩阵、遗留环境或较深入的无障碍检查 | 包含多个独立产品或平台矩阵，或需要正式无障碍审计 |

### 8.6 共性技术能力

| 基础单元 | S | M | L | X / 拆分条件 |
|---|---|---|---|---|
| 国际化支持 | 资源提取；单一新增语言；标准格式 | 一个应用或模块涉及复数、日期、货币和本地内容差异 | 单一应用或模块涉及多语言工作流、从右向左书写、大量硬编码改造或动态内容 | 包含多个可独立发布的应用或模块 |
| 身份与权限管理 | 少量角色；标准 RBAC；单应用 | 单一资源范围存在多角色、多资源或租户，并接入统一身份平台 | 单一资源范围涉及 ABAC、委托授权、职责分离或跨系统权限一致性 | 包含多个独立资源域，或需要改造统一身份平台本身 |

## 9. 工作模式模型

### 9.1 含义

工作模式说明当前基础单元相对于 Effective Start 是新做、修改现有内容，还是接入已有能力。不同工作模式对应不同的工作内容和 M 档基础人天，不能用一个统一倍率处理所有基础单元，也不能直接照搬目标系统的整体变化类型。

| 工作模式 | 判断标准 |
|---|---|
| 新建 | 创建原来不存在的基础单元实例；包括新建数据迁移、发布切换、问题整改或下线工作，不表示其所作用的目标系统一定是全新系统 |
| 调整 | 保留已有对象及其主要工作范围，只改变其行为、规则、结构、配置或内容 |
| 接入复用 | 使用已有的公共能力、平台能力或外部能力，不修改这些能力本身；本 Task 只负责本项目一侧的接入、配置、映射、适配和必要验证 |

`调整 / 接入复用` 至少要引用一个相关的 Effective Start。`新建` 通常不需要引用，但工作本身依赖现有对象时仍然必须引用：数据迁移要引用现有数据来源，系统功能下线要引用被下线的对象，同一根因问题整改要引用受影响的现状；发布切换涉及现有运行能力时也必须引用。

`调整 / 接入复用` 还必须保存结构化 `workModeEvidence`。其中 `effectiveStartItemId` 必须是 `matchedEffectiveStartItemIds` 中的一项，`effectiveStartItemName` 必须与该 Effective Start 的名称完全一致，并在 Task 名称或理由中明确出现。`接入复用` 另存非空 `projectSideWorkTypes`，枚举本项目侧实际要完成的注册、配置、封装、映射、适配、认证、租户设置、权限设置或专项验证工作，并按枚举顺序确定性生成 `projectSideWorkCommitment = 本项目负责并交付：<中文工作类型>`。此时 `workModeRationale` 必须严格等于 `<effectiveStartItemName>保持不变；<projectSideWorkCommitment>。`，不从任意自由文本猜测责任边界；任何否定、责任转移或宽泛关键词都会因不匹配而 fail closed。

区分 `调整` 和 `接入复用`，关键看是否修改已有能力本身。例如，修改现有公共服务属于“调整”；公共服务保持不变，只为当前项目配置租户、权限、映射或适配器，则属于“接入复用”。两类工作同时存在时，要拆成两个 Task。

工作模式判断针对当前基础单元实例，不能跟随它所作用的业务系统：

- 人工测试、自动化测试用例、性能与容量测试、安全与隐私测试、兼容性与无障碍测试，只有在修改已有测试方案、用例、脚本或测试配置时才使用“调整”；被测功能是调整现有功能，不代表测试 Task 也应使用“调整”。为本次交付重新形成测试范围和结果时使用“新建”。
- 数据迁移和发布切换，只有在修改已有迁移脚本、迁移方案、切换方案或切换清单时才使用“调整”；为调整后的系统新做一次迁移或切换仍使用“新建”。
- “接入复用”必须存在本项目一侧可以独立估算的接入工作。通用界面组件、公共技术组件、应用工程初始化等已有能力，只有在当前项目需要注册、配置、封装、适配或专门验证时才生成“接入复用”Task；普通依赖引入、常规调用或直接按既有约定使用，不单独生成 Task。

“替换”描述的是整体变化，不是一种单独的工作模式。完整替换要根据实际情况拆成：

```text
新建替代能力，或接入复用既有替代能力
+ 数据迁移（存在数据或状态迁移时）
+ 发布切换（存在双跑、切流或回滚时）
+ 系统功能下线（旧系统、服务、模块或功能退出范围时）
```

如果原有对象和主要工作范围保持不变，只是更新内部实现，则使用“调整”，不按替换拆分。设计阶段仍可用 `REPLACE / RETIRE` 描述 ArchitectureDelta，但这些设计变化不直接成为 Task 工作模式。

### 9.2 为什么不用全局工作模式系数

工作模式对不同基础单元的影响比例不稳定：界面调整可能显著低于新建，外部系统对接的调整可能因重新认证接近或超过新建；接入复用公共技术组件可能只需配置，也可能需要复杂安全适配。

因此，正式模板直接记录每个适用组合的 M 档基础人天：

```text
BaseEffort(baseUnit, workMode) = M档基础人天
```

只配置实际适用的组合。虽然可以根据这些数值反算某个基础单元在不同工作模式下的比例，但这个比例只用于分析和校准，正式计算仍直接读取对应的基础人天。

## 10. 完整估算流程

```text
选择基础单元
  → 自动确定任务族
  → 根据 Effective Start 判断工作模式
  → 使用“基础单元 + 工作模式”选择 M 档基础人天
  → 按基础单元专属标准判断 S / M / L
  → 应用复杂度系数
  → 得到 Task 人天
  → 汇总 Story 人天
```

Task 估算不使用数量、活动或 Story 类型。

## 11. Integration、SIT、UAT 与不确定性

- **Integration**：独立记录一次有明确方向的系统交互，包括 source、target、trigger、direction、purpose 和 internal/external ownership，并关联受影响的 Story。`generate-story` 只根据来源需求、现状和目标设计中的证据记录 Integration，不判断是否需要生成集成 Task，也不根据 Story 类型推断 Integration。
- **集成 Task**：由 `generate-task` 根据 Story、Integration 和 Effective Start 生成。每个需要交付的 Integration 恰好对应一个基础单元为“内部系统对接”或“外部系统对接”的 Task，并由该 Task 的 `integrationId` 建立引用；工作模式、复杂度和人天均在 Task 阶段确定。
- **遗漏的系统交互**：如果拆分 Task 时发现 Story 还涉及未登记的系统交互，`generate-task` 必须退回 `generate-story` 或 `generate-design`，先补充或澄清 Integration。不能为了完成估算而临时编造集成关系，也不能生成没有 `integrationId` 的集成 Task。
- **SIT**：由内部或外部系统对接 Task 触发，不再依赖 `SYSINT` Story 类型，也不能仅凭一条 Integration 记录触发。一次有明确方向的系统交互对应一个集成 Task。
- **UAT**：Story 单独保存“适用/不适用”，不从任务族推导。技术型 Story 也可能需要业务验收。
- **不确定性**：每条 Uncertainty 显式保存 `affectsEstimate`。答案可能改变范围、责任、设计、交付对象、工作量或人天时必须为 `true`，相关工作不开始，也不通过复杂度或风险倍率估算；只有确认不影响正式估算时才可为 `false`。`impact` 只解释影响，不通过关键词猜测门禁结论。

### 12.1 基础单元与基础人天配置表

基础单元名称
计数口径

不包含内容

三个人天列直接表达工作模式是否适用及其 M 档基础人天：正数表示该组合可用，`❌` 表示不适用。模板不再维护“允许工作模式”文本、工作模式说明或独立的基础人天明细表。

### 12.2 复杂度系数参数

S/M/L 的判定标准已经按基础单元保存在同一配置表中。全局只保留 `K_COMPLEXITY_S`、`K_COMPLEXITY_M`、`K_COMPLEXITY_L` 三个系数，并将其放入 `91-项目参数`；不再保留独立的复杂度规则工作表。系数缺失、重复、非正数或尚未校准时，不允许进入正式估算。

### 12.3 推荐 M 档基础人天矩阵

下表单位为人天，表示一个 M 档基础单元实例通常需要的工作量。“计数口径”规定一条 Task 最多可以覆盖什么范围；“具体工作内容”说明这个基础单元一般要完成什么，以及哪些工作不计算在内，并不是规定固定的执行步骤。现有模板已经配置的组合继续沿用“设计 + 实现”的合计值，并改用新的中文名称：原“采用”改为“接入复用”；“系统功能下线”原来在“退役”模式下的 1.5 人天，以及“同一根因问题整改”原来在“调整”模式下的 1.5 人天，都改记为“新建”，数值不变。原“替换”组合不直接迁移，要按替代功能、数据迁移、发布切换和系统功能下线等 Task 分开估算。通用界面组件等新增基础单元和新增组合暂用建议值，实施前还要结合历史 SOW 和实际交付数据校准。`❌` 表示这种组合不适用，不是零人天。

工作模式针对基础单元实例判断。例如，新编一份运维操作手册、下线方案或问题整改方案均使用“新建”，修改既有操作手册使用“调整”；系统级“替换”则按实际涉及的基础单元拆成多行。`❌` 组合出现实际需求时，应选择更合适的基础单元、拆分工作，或者经过目录评审新增允许组合。

表中的“调整”只适用于已有基础单元实例本身发生修改，“接入复用”只适用于存在可独立估算的项目侧接入工作。不能因为目标业务功能是调整、项目使用了某个现成组件，或已有能力名称相同，就直接选择相应工作模式。

### 12.4 Task 表

Task 表只让用户选择基础单元、工作模式和复杂度，并填写工作模式理由和现状依据。“内部系统对接”或“外部系统对接”Task 还必须选择一个 `integrationId`，其他基础单元不得填写。`complexity = S / L` 时要说明为什么偏离 M 档；`complexity = M` 时不用填写。任务族由系统自动带出且不能修改；基础人天、系数和 Task 人天由公式计算。

## 13. 现有模板怎么调整

1. 同一基础单元和工作模式下的“设计 + 实现”人天相加，作为新的 M 档基础人天。
2. 原“采用”组合改名为“接入复用”；现有只配置“实现”的组合，暂时把当前实现人天作为建议基础人天。
3. 原“替换”工作模式不迁移。涉及替换的范围重新分解为替代功能、数据迁移、发布切换和系统功能下线，并分别匹配基线。
4. 原“退役”工作模式删除；“系统功能下线”的 1.5 人天迁移到该基础单元的“新建”组合。
5. “同一根因问题整改”的 1.5 人天从“调整”迁移到“新建”，因为新建的是一项整改工作；受影响现状仍通过 Effective Start 引用表达。
6. 删除活动列、数量列和数量乘法。
7. 将现有专业域迁移为任务族目录；Task 不再人工填写任务族。
8. 为新增基础单元单独校准三个工作模式列的 M 档基础人天；不适用的组合明确填写 `❌`。
9. 使用历史 SOW 和实际交付数据检验各工作模式的基础人天和复杂度系数；反算结果只能用于校准，不能改变本设计对各字段和基础单元的定义。
10. 将数据迁移和发布切换拆为独立任务族，把问题诊断/根因整改合并到“问题处理”，把运维交接/用户培训归入“交付与移交”；仅新增“用户培训与使用材料”，保留其他基础单元 ID。

## 14. 对 Schema、Skill 和校验规则的影响

### 14.1 正式数据格式

- Story 删除 `type`，保留明确表达 UAT 适用性的 `uatRelevant`。
- Task 删除 `professionalDomain`、`activity` 和 `quantity`。
- Task `workMode` 只允许 `新建 / 调整 / 接入复用`；原“采用”改名，原“替换 / 退役”不再是 Task 工作模式。
- Task 保留或新增 `baseUnit`、`workMode`、`workModeRationale`、条件字段 `workModeEvidence`、`complexity`、条件字段 `complexityRationale`、条件字段 `integrationId`、`matchedEffectiveStartItemIds` 和 `rationale`；`workModeEvidence` 仅在调整/接入复用时存在，`complexityRationale` 仅在 S/L 时存在，`integrationId` 仅在内部或外部系统对接 Task 中存在。
- Uncertainty 新增必填布尔值 `affectsEstimate`，替代从 `impact` 文本推测是否阻止估算。
- 正式 JSON 数据不保存任务族、基础人天、复杂度系数或最终人天。

### 14.2 Skill

- `generate-story` 不再选择 Story 类型，直接形成可验收交付结果并明确 UAT 适用性；同时记录有证据支持的独立 Integration 关系，但不判断或生成集成 Task。
- `generate-task` 按一个基础单元实例拆分 Task，从项目模板的单张配置表读取基础单元、三种工作模式的 M 档基础人天和逐单元复杂度标准，并从项目参数读取 S/M/L 系数；根据 Story、Integration 和 Effective Start 生成内部或外部系统对接 Task，并填写 `integrationId`。
- `generate-task` 评审必须检查任务范围是否清楚、是否重复或遗漏、每个 Integration 是否恰好对应一个集成 Task、工作模式是否有现状依据、S/L 是否说明偏离 M 档的原因，以及所有 X 项是否已经处理；发现未登记的集成关系时退回上一步补齐。
- `generate-sow` 只把批准后的正式数据写入工作簿，自动带出和计算工作交给模板完成。

### 14.3 验证

出现以下情况时，校验必须不通过：

- 无 Task 的 Story；
- 未知基础单元或未配置的工作模式组合；
- 缺失或空泛的工作模式理由；
- `调整 / 接入复用` 引用了与当前 Task 对象无关的 Effective Start；
- `workModeEvidence` 未精确匹配已引用 Effective Start 的 ID/名称，或接入复用的 `projectSideWorkTypes`、`projectSideWorkCommitment` 与标准格式的工作模式理由不完全一致；
- 测试、数据迁移或发布切换 Task 选择“调整”，但没有指出被修改的既有测试资产、迁移资产或切换资产；
- 同一 Story 生成多个“发布切换”Task，或把数据迁移执行/核对并入发布切换重复计价；
- 同一 Story 同时用“问题诊断与恢复”和“同一根因问题整改”计算同一段诊断工作；
- “接入复用”Task 只有普通调用或直接使用，没有可独立估算的注册、配置、封装、映射、适配或专门验证工作；
- S/L 缺少解释偏离 M 档的复杂度理由，或者复杂度理由只是复制标准；
- `调整 / 接入复用` 缺少 Effective Start 引用；
- 数据迁移、系统功能下线、同一根因问题整改或涉及既有运行能力的发布切换缺少必要 Effective Start 引用；
- Task 使用已删除的“采用 / 替换 / 退役”工作模式，或者用单个 Task 的工作模式表达复合替换；
- Integration 没有对应的集成 Task，或者对应了多个集成 Task；
- 内部或外部系统对接 Task 缺少 `integrationId`、引用未知 Integration，或者非集成 Task 填写 `integrationId`；
- 正式估算数据中出现 X；
- S/M/L 系数缺失、重复、非正数，或状态不是固定规则、已校准或已批准；
- 仍有 `affectsEstimate = true` 的未关闭 Uncertainty，或该字段缺失/不是布尔值；
- Task 保存任务族、活动、数量或计算人天；
- 一个 Task 明显混合多个基础单元实例；
- SIT、UAT 仍依赖已删除的 Story 类型。

## 15. 验收标准

1. 全链路只使用 `Epic → Feature → Story → Task`。
2. Story 的正式数据、Skill 和工作簿中不存在 Story 类型。
3. Task 一行对应一个基础单元实例，不存在活动和数量。
4. 每个基础单元只对应一个任务族，Task 不需要人工选择任务族。
5. 目录包含 13 个任务族、37 个基础单元及各自的 `S / M / L` 标准。
6. 每个 Task 都有可复核的工作模式理由；S/L Task 具有解释偏离 M 档原因的复杂度理由，M Task 不要求解释。
7. Task 工作模式只包括 `新建 / 调整 / 接入复用`；“调整”和“接入复用”的区别明确，替换和退役通过基础单元拆分表达。
8. `基础单元 + 工作模式` 通过基础单元配置表中的对应人天列唯一选择 M 档基础人天；工作模式不使用全局系数。
9. 复杂度按各基础单元自己的标准判断，再使用 `91-项目参数` 中配置的 S/M/L 系数；不存在独立复杂度规则工作表。
10. 多个基础单元实例必须拆成多个 Task，不能通过数量或复杂度合并。
11. Integration 的识别和记录不依赖 Story 类型；`generate-story` 不负责判断集成 Task。
12. 每个需要交付的 Integration 都有且只有一个带正确 `integrationId` 的“内部系统对接”或“外部系统对接”Task。
13. SIT 由集成 Task 触发；UAT 由 Story 适用性明确表达。
14. 不确定性未关闭时不开始相关工作，也不进入正式估算。
15. 工作簿中的基础人天、系数、公式、取整和总计是唯一计算依据。
