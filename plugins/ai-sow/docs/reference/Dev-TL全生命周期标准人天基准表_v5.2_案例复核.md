# Dev / TL 全生命周期标准人天基准表 v5.2 案例复核

- 复核对象：[v5.2 讨论稿](Dev-TL全生命周期标准人天基准表_v5.2_讨论稿.md)
- 样本批次：B
- 日期：2026-09-02
- 样本要求：不复用 v5.0 和 v5.1 的既有案例；优先检验行业、终端和交付形态变化

本批次用七个新场景回放 v5.2 的 70 个工作类型。Task 使用稳定工作类型 ID 关联基础表。

## 案例 B1：单租户产品升级为多租户 SaaS

场景：既有企业应用改造成多租户服务，要求租户识别、请求上下文、数据隔离、租户级配置和独立审计。

| Task 实例 | v5.2 类型 ID | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 分析租户边界对身份、数据、缓存、任务和审计的影响 | AN-IMPACT | 新增 | 1.0 | 可准确映射。 |
| 设计租户上下文传播、隔离和迁移方案 | AN-DESIGN | 新增 | 2.0 | 可准确映射。 |
| 建立应用级租户识别、上下文传播和资源隔离基础能力 | **缺口：多租户基础能力** | 新增 | 2.5 | 数据权限只能表达用户能访问哪些数据，不能覆盖租户上下文、资源命名空间和后台任务隔离。 |
| 建立租户管理员功能权限 | GOV-FUNCTION-ACCESS | 新增 | 2.0 | 可准确映射。 |
| 建立租户数据范围控制 | GOV-DATA-ACCESS | 新增 | 2.5 | 可准确映射。 |
| 建立租户级配置和功能开关 | CO-CONFIG | 新增 | 1.5 | 可准确映射。 |
| 调整共享数据模型增加租户契约 | DATA-CONTRACT | 修改 | 1.5 | 模型可独立版本化并被多个能力消费时计量。 |
| 建立租户隔离安全验证 | TEST-SECURITY | 新增 | 2.0 | 可准确映射。 |
| 建立租户并发与资源隔离性能验证 | TEST-PERF | 新增 | 2.0 | 可准确映射。 |

结论：多租户是跨接口、任务、缓存和资源的应用基础能力，不能只用数据权限替代；建议新增一个应用共性类型。

## 案例 B2：移动巡检应用支持离线工作并发布到应用商店

场景：巡检人员离线填写表单、拍照，联网后同步并解决冲突；iOS 和 Android 客户端完成签名、商店提交和灰度发布。

| Task 实例 | v5.2 类型 ID | 模式 | PD | 复核判断 |
|---|---|---|---:|---|
| 建立离线巡检编辑流程 | FE-FLOW | 新增 | 3.0 | 多步骤离线业务流程可准确映射。 |
| 建立照片上传能力 | FE-FILE-TRANSFER | 新增 | 1.5 | 文件传输边界清楚。 |
| 建立巡检数据双向同步 | DATA-SYNC | 新增 | 2.5 | 可准确映射。 |
| 建立同步冲突解决与补偿流程 | FE-COMPENSATION | 新增 | 2.0 | 具有独立触发和结果时计量。 |
| 建立可复用离线队列组件 | FE-COMPONENT | 新增 | 1.5 | 仅在形成跨流程复用资产时计量。 |
| 建立移动端构建、签名和制品流水线 | ENG-PIPELINE | 新增 | 2.5 | 可准确映射。 |
| 完成设备和操作系统兼容验证 | TEST-COMPAT-A11Y | 新增 | 1.5 | 可准确映射。 |
| 编制商店提交、灰度和回退方案 | REL-PLAN | 新增 | 2.0 | 类型内容可覆盖，但“生产”措辞容易让客户端发布被误判为不适用。 |

结论：不需要单独增加移动应用发布类型；现有发布类型只需去除服务器上线偏向的名称。

## 复核发现与审核决定

| Finding | 改进建议 | 审核决定 | 决定理由 |
|---|---|---|---|
| B-F01 | 新增“多租户基础能力” | **吸收** | 租户上下文、后台任务和资源隔离超出普通数据权限，且可形成独立应用能力。 |
| B-F02 | 将发布类型去除“生产上线”限定 | **吸收** | 同一交付物也适用于移动商店、桌面客户端和其他发布渠道；稳定 ID 不变。 |
| B-F03 | 明确共享数据契约不等于单接口 Schema | **吸收** | 防止 DATA-CONTRACT 与 IN-INTEGRATION、FE-QUERY-API、FE-COMMAND-API 重复计量。 |
| B-F04 | 新增“移动应用发布” | **不吸收** | 扩展后的通用发布方案与发布执行已经覆盖，不需要按终端类型拆分。 |
| B-F05 | 新增“搜索引擎与索引” | **不吸收** | 搜索是实现技术；数据同步、查询 API、调度和性能验证已经覆盖独立结果。 |
| B-F06 | 新增“通知发送能力” | **不吸收** | 消息流程、供应商集成、模板和补偿是更稳定且互斥的交付对象。 |
| B-F07 | 新增“IoT、MQTT、时序数据” | **不吸收** | 它们分别是业务领域、协议和存储技术，不应成为 StandardPD Key。 |
| B-F08 | 调整现有 70 类的基准 PD | **不吸收** | 本批次未发现新的相对失衡；所有标准复杂度实例均能在现有基准附近成立。 |

## v5.3 变更输入

1. 新增 CO-MULTITENANCY“多租户基础能力”，建议 2.5 / 1.5 / 1.0 PD。
2. 保持 REL-PLAN、REL-REHEARSAL、REL-EXECUTION 和 REL-REVIEW 的稳定 ID，名称分别改为
   “发布与切换方案”“发布与切换演练”“发布技术执行”“发布后技术复盘”。
3. 收紧 DATA-CONTRACT 的说明：单个接口或集成的 Schema 默认包含在主 Task 中。
4. 其余类型和参数保持不变。

本批次仍产生一个有效新增类型和两项边界改进，因此 v5.2 尚未稳定，进入 v5.3。
