# 研发全生命周期标准人天基准表 v6.0：复杂度标准设计基线

- 状态：业务审视设计基线；不作为当前模板计算权威
- 日期：2026-09-03
- 批准日期：2026-09-02
- 基础版本：[v5.4 模式校准稿](Dev-TL全生命周期标准人天基准表_v5.4_讨论稿.md)
- 适用对象：后续 v6.0 复杂度标准、案例复核和参数校准
- 计量方式：基础表不使用 `quantity`；真实任务清单每个基础工作单元实例一行

> 本文定义 v6.0 替代目录的复杂度判断结构和验收边界。v6.0 不以兼容或映射回旧 37 单元为目标；正式采用时应一次性替换现行目录，新旧目录不得在同一估算中混用。当前仅修订审视标准，尚不修改插件模板，也还不是计算权威。

## 1. 目标

v6.0 在 v5.4 的基础上补齐以下能力：

1. 为 88 个工作类型分别提供可复核的 `S / M / L / X` 判断标准；
2. 同时使用定量锚点和定性约束，不用单一主观描述或总分代替专业判断；
3. 明确“新建 / 调整 / 接入复用”三种模式下复杂度所衡量的范围；无交付对象变化、无项目侧适配工作的重复执行不计；
4. 覆盖每个实际适用的“工作类型 × 工作模式”组合，不为 `-` 模式虚构复杂度标准；
5. 复用真实案例进行多轮拆分、判档和反向校正规则，直到结论稳定、边界明确、用语统一；
6. 区分行业标准可以支持的原则与必须由组织历史数据校准的内部参数。

## 2. 不变边界

v6.0 以 v5.4 为证据基线，但独立复核证明边界存在缺陷时允许建立新的替代 ID、模式或参数：

- 语义未变化的工作类型沿用原 ID；语义实质变化时建立新 ID，不用旧 ID 指代新对象；
- 每个工作类型只保留能够形成独立交付结果的工作模式；
- “新建 / 调整 / 复用”的 M 档基础人天以旧标准和同边界样本为起点，独立复核可显式修正；
- 标准交付对象、模式化完成标准和说明；
- 一行 Task 对应一个独立基础工作单元实例，不设置数量字段；
- `X` 不直接套用复杂度系数：可拆对象先拆分，事实不足先澄清，单一对象确实无法再拆且超出标准范围时单独估算。

独立复核退役了混合 UI 与通用程序库的 `FE-COMPONENT` 以及只描述工具的 `TEST-TOOL`，以 `FE-UI-COMPONENT`、`CO-TECH-COMPONENT`、`TEST-SUPPORT-ASSET` 替代，并新增或明确应用存储模型、数据目录与血缘、人工测试、用户培训与参考、业务规则流程、技术参考、项目侧 AI4SE 工具扩展/Skill/知识上下文/研发流程、现有系统智能化能力/知识检索/业务流程/评测和软件安全性保障等类型。模型训练、微调和模型制品管理暂不纳入，形成 88 类。它们共同构成新的替代目录；旧 37 单元不再是兼容边界。进入模板前仍需单独批准。

v6.0 不把复杂度用作修补目录边界或合并多个独立交付对象的手段。若交付对象可以独立验收、发布或结算，应拆成多行 Task，而不是提高到 L。

## 4. 复杂度模型

采用“工作类型专属标准 + 工作模式范围覆盖 + 统一决策算法”的混合模型。

### 4.1 工作类型专属标准

每个工作类型必须单独列出：

| 字段 | 要求 |
|---|---|
| 工作类型 ID | 与 v6 替代目录一致；语义不变沿用旧 ID，语义变化使用新 ID |
| 主要计量维度 | 2～5 个与该类型直接相关的可观察维度，不罗列无关通用因素 |
| S（简单） | 给出本类型内部的定量上限，并同时说明允许的定性约束 |
| M（标准） | 给出常见范围的定量区间和典型约束；作为默认档 |
| L（复杂） | 给出仍属于一个独立实例的进入阈值或强约束；超过常规 L 范围时服从统一超界门禁 |
| X / 拆分条件 | 多个独立交付对象、边界不明、关键前提缺失，或超出该基础单元承载范围时的处理 |
| 模式适用说明 | 说明本类型在调整或复用时是否需要覆盖规则之外的专门口径 |

定量锚点优先选择实例内部的状态、规则、数据组、映射、场景、角色、环境、资源、依赖或验证矩阵。不得用“代码行数”“文件数量”“开发人数”作为跨类型通用尺度。

每行 Task 只对应一个可以独立说明范围、交付成果和验收结论的对象。能够分别发布或验收的对象必须拆行；共同形成一个完整结果、不能独立验收的内容才可合并。跨工作类型共用的测试路径、数据、证据、技术参考、Runbook 或培训材料只计算一次，其他 Task 引用时不得重复增加工作量。

容易重叠的成果按最终交付结果选择工作类型：交互式看板使用 `FE-DASHBOARD`，受治理的指标数据集使用 `DATA-METRIC`，正式报表使用 `DATA-REPORT`，交易文档模板使用 `DATA-DOCUMENT`。同一结果只选择一个主类型；只有不同结果能够分别版本化和验收时才可叠加。

灾备/发布演练按主验收对象唯一选型：恢复能力、RTO/RPO 或数据恢复结论使用 `TEST-DR`；某次 Release 的上线就绪、部署/切换/回滚路径使用 `REL-REHEARSAL`。一份报告只有一个主结论时不得拆两行，事实不足判 X。

定性约束描述定量数量无法表达的成本驱动因素，例如：

- 一致性、幂等、补偿、状态恢复和零停机；
- 高敏感数据、强监管、职责分离和防篡改审计；
- 严格性能、可用性、恢复目标或业务连续性；
- 跨团队、外部方、联合窗口和受限测试环境；
- 多语言、从右向左书写、无障碍、遗留兼容或多终端矩阵；
- 高风险迁移、复杂回滚和大规模数据核对。

这些内容只有在对应工作类型的 L 档明确列出，并能说明具体机制、限制条件或验收要求时，才能作为升级依据。“复杂”“严格”“重大”等形容词本身不能升级档位。

接入复用只看项目侧实际发生的配置、映射、封装、认证、权限、环境接入和专项验证，共享能力内部规模不参与判档。多维验证按实际执行的组合和抽样范围判断，不能把各维度上限相乘成一个并不存在的范围。身份与授权按结果区分：外部 Claim 或属性到本地主体、用户组的映射使用 `IN-IDENTITY`；本地角色或主体到操作、资源的授权使用 `GOV-FUNCTION-ACCESS`。

智能化应用按交付结果区分：单一生成、总结、分类、提取、推荐或判断结果使用 `AI-CAPABILITY`；可独立维护的业务知识检索和依据引用使用 `AI-KNOWLEDGE`；多步骤智能业务流程使用 `AI-WORKFLOW`；独立的质量与行为安全评测使用 `AI-EVALUATION`；应用攻击面和信息安全控制验证使用 `TEST-SECURITY`；软件安全性论证使用 `GOV-SAFETY-ASSURANCE`。模型训练、微调、训练数据和模型制品管理暂不纳入本版。公司 AI 平台部门提供的模型网关、SSO、密钥托管、审计、运行平台和 Harness 也不属于本表项目研发范围。

项目侧 AI4SE 按可独立验收的资产区分：Plugin、MCP/工具适配器、Hook 或命令扩展使用 `ENG-AI4SE-EXTENSION`；具有明确触发、输入输出、执行规则和验证结果的 Skill 或 Agent 研发职责使用 `ENG-AI4SE-SKILL`；面向研发 Agent 的项目知识、代码索引和上下文规则使用 `ENG-AI4SE-CONTEXT`；需求分析、代码审查、测试生成、缺陷修复等多步骤自动化使用 `ENG-AI4SE-WORKFLOW`。普通使用 Agent、直接打开代码库、临时提示、标准安装或调用现成 Plugin/Skill/知识库/流程均不创建 Task。

### 4.2 工作模式范围覆盖

复杂度始终衡量“当前 Task 这一行实际负责的交付范围”，不能跟随目标系统的总体复杂程度。

模式相对于当前工作类型的标准交付对象判断，而不是相对于底层工具、框架、SaaS 或平台判断。对象不存在且本次形成它用新建；同一对象被改变用调整；共享能力保持不变但项目形成可独立验收的配置、映射、封装、认证、注册、环境接入或专项验证时用接入复用。共享能力被修改且项目接入可独立验收时，可拆为“共享能力调整 + 项目接入复用”；无法分别验收时只保留主交付 Task。测试、演练或评测资产及范围未变化时的重复执行、复测和签署不计。底层引擎或公司 AI 平台既有但本次新形成的业务规则集、智能业务结果、知识域或智能流程仍是新建。

| 工作模式 | 复杂度计量范围 | 不计入当前 Task 的范围 |
|---|---|---|
| 新建 | 新交付对象从无到有形成标准结果 | 与该对象无独立交付关系的存量系统复杂度 |
| 调整 | 已有对象中本次新增、修改、删除的内容，受影响路径，以及完成本次调整必须执行的回归范围 | 未发生变化且无需因耦合重新验证的整个存量对象 |
| 接入复用 | 本项目侧的注册、配置、封装、映射、适配、认证、租户设置、权限设置和专项验证 | 保持不变的共享平台、外部能力或公共组件内部实现 |

每个 v6 标记为适用的模式都必须可以判定 `S / M / L`。标记为 `-` 的模式不生成 Task，也没有复杂度档位。v6.0 修订后共有 88 个工作类型和 191 个适用的“工作类型 × 工作模式”组合；旧目录只用于来源追溯和参数校准，不构成新目录的兼容约束。

接入复用只适用于正文列出的 26 个类型，并只计算项目侧实际交付物；共享能力内部规模不计。同一配置或映射在多个文件中重复出现只计一次。`TEST-SUPPORT-ASSET` 和 `ENG-IAC` 只有形成可独立版本化和验收的项目适配包或 Root Module 时才单列，主 Task 内部的普通配置不计。四类 AI4SE 资产也只有形成可独立验收的项目参数、绑定、权限、适配或专项验证结果时才可使用接入复用；标准安装、启用或普通调用不计。

若共享能力本身要调整，同时本项目还要完成接入，必须拆为两行：

```text
共享能力调整 Task：复杂度只看共享能力的实际变更和必要回归
项目复用 Task：复杂度只看本项目侧接入、配置、映射和专项验证
```

### 4.3 统一决策算法

所有工作类型按同一顺序判定：

```text
1. 先检查与模式无关的结构性 X：是否含多个独立实例、边界不清或关键前提缺失。
2. 按工作模式确定本 Task 的实际计量范围；调整只保留变化和必要回归，接入复用只保留项目侧实际工作。
3. 只对第 2 步得到的当前计量范围执行专属数值上界和全局数值超界门禁；任一维度超界即判 X，禁止用存量对象总体规模判调整/复用 Task。
4. 使用该工作类型在当前范围内的专属定量锚点和定性约束判断。
5. 命中任一明确 L 强约束时判 L，不允许其他简单因素把它平均为 M。
6. 仅当主要定量指标全部落入 S，且没有 M/L 定性约束时判 S。
7. 未命中 X、S 或 L 时判 M。
```

不采用跨维度加权总分。原因是高敏感数据、零停机、强监管、严格恢复目标等单项约束不能被“页面少”“字段少”等低分项抵消。

### 4.4 定量与定性冲突

定量锚点表示常见规模，定性约束表示交付风险和验证强度。两者冲突时按以下规则处理：

- 数量落入 S，但命中 M 或 L 定性条件：按较高档；
- 数量落入 L，但工作内容实际由成熟机制自动完成：除非专属标准明确允许降档，否则仍按 L；成熟机制应优先体现为“复用”或较小调整范围；
- 数值维度分为四类：离散可拆计数的 L 上界为 `2 × M 上限`，连续规模为 `10 × M 上限`，连续执行时长为 `6 × M 上限`，RTO/RPO 等反向目标使用专属闭合区间；专属行有更严格边界时以专属行为准；
- 反向目标只有在直接参与分档时才必须给出闭合 S/M/L/X 区间；项目专属的时延、吞吐、错误率、可用性等服务目标若不采用统一分档，必须移出主要数值区间并使用 量化服务目标，保存基线、目标值、测量窗口和验收方法；
- 任一主要数值维度命中 X 即停止套档；可拆时按独立对象拆分，不可拆时进入专题分析或批准的定制估算；
- 定性 L 条件不按数值倍数机械扩张，但仍必须是一个不可再拆的交付对象；
- 历史样本只能支持超界对象的单独估算和未来阈值校准，不能把应拆分或事实不清的 X 直接改判为 L；
- 事实不足以判断：判 X，补充证据，不默认 M。

## 5. S、M、L、X 的统一语义

| 档位 | 统一语义 | 使用要求 |
|---|---|---|
| S | 同类工作中明显低于标准实例，范围小、依赖少、规则直接、验证矩阵有限 | 必须写出低于 M 的具体事实；不能只写“简单” |
| M | 本类型最常见、边界清楚、约束常规的标准实例 | 记录工作模式、主要维度的实际范围和判断依据 |
| L | 仍为一个独立实例，但规模接近单元上限，或存在明显增加设计、实现、协调、验证工作的强约束 | 必须写出高于 M 的具体事实及对应标准 |
| X | 表示应拆分、应澄清，或单一不可拆对象超出标准范围 | 可拆项先拆分，事实不足先补充信息；确实不可拆且超出标准时单独估算 |

复杂度理由只记录实例事实，不复制标准原文。例如：

```text
复杂度=L：该业务操作包含 6 个相互转换的状态，并要求失败后幂等重试和人工补偿；
相较 M 档的常规多规则事务，状态恢复和补偿验证显著扩大。
```

## 6. 倍率状态与历史校准

v6.0 初稿暂时沿用：

| 档位 | 当前倍率 | 参数状态 |
|---|---:|---|
| S | 0.6 | 内部经验参数，待历史实绩校准 |
| M | 1.0 | 基准参数 |
| L | 1.5 | 内部经验参数，待历史实绩校准 |

正式使用时，倍率仍由项目模板管理；基础文档只说明口径和状态，不成为第二计算权威。

历史校准数据放在独立任务实绩或分析数据中，不增加到基础表，也不引入 `quantity`。每个样本至少保留：

- 工作类型 ID、工作模式、复杂度和复杂度理由；
- 估算时使用的 M 档基础人天和倍率；
- 实际研发有效投入人天；
- 返工、等待、需求变化、外部阻塞等不可归因于复杂度标准的偏差原因；
- 是否按相同基础单元边界完成，是否中途发生拆分或合并。

校准时先剔除范围变化和不可比样本，再按工作类型族、工作模式和复杂度观察实际人天相对 M 档基础人天的分布。样本不足时保留“待校准”状态，不因少数极端案例直接修改全局倍率。任何倍率调整都应单独评审，并同步模板、参数状态和回归案例。

## 8. 案例迭代设计

使用同一组案例反复验证规则，避免每轮更换案例导致结论不可比。至少覆盖：

1. 系统多语言支持：国际化机制、页面/模板适配、资源处理、兼容验证；
2. SSO 或统一身份接入：身份系统、业务权限、用户映射、专项验证；
3. 订单或交易功能：页面、组件、查询 API、业务操作 API、数据模型和发布；
4. 跨系统数据同步与数据权限：集成、同步、对账、安全和监控；
5. 自动化测试与测试工具：测试框架、用例、数据和环境；
6. CI/CD、IaC 与基础设施：流水线、运行环境、资源栈、治理和发布；
7. 数据迁移、切换与回滚：迁移、核对、发布切换和下线；
8. 生产问题诊断、同一根因整改和运维交接。
9. 现有系统智能化升级：智能业务能力、业务知识检索、智能业务流程、独立质量与行为安全评测、工程接入和发布。
10. 项目侧 AI4SE：Plugin/工具扩展、Skill、研发知识与项目上下文、智能研发流程及独立评测；同时验证公司 AI 平台、Harness 和普通 Agent 使用不会被误计。

每轮按以下顺序执行：

```text
按真实交付对象拆成一行一个 Task
→ 选择工作类型和工作模式
→ 检查 X
→ 根据定量与定性标准判 S/M/L
→ 复核是否重复计量或遗漏工作类型
→ 记录规则无法解释、不同人可能得出不同结论的点
→ 只吸收可泛化且不破坏既有边界的建议
→ 用同一案例集重新回归
```

建议至少完成三轮：

- 第一轮检查完整性：是否缺工作类型、缺模式口径或缺关键计量维度；
- 第二轮检查一致性：相近工作类型、三种模式和 S/M/L 档位是否使用同一语义；
- 第三轮检查稳定性：同一事实在不查看上轮答案时能否得到相同拆分和判档。

三轮案例之后还要进行一次 fresh-context 独立复核，至少分别覆盖目录完整性、参数一致性和真实案例可执行性。独立复核可以推翻“三轮无变化即稳定”的结论；共同确认的目录缺口、逻辑矛盾和不可重复判定项修正后，必须对受影响类型补充回归，不能沿用旧的稳定声明。

达到以下全部条件才可标记为“稳定候选”：

- 88 个工作类型均有专属 S/M/L/X 标准；
- 191 个适用模式组合全部有明确计量范围；
- 所有案例均可拆成独立 Task，且没有用 L 代替应拆分的 X；
- 连续两轮没有新增工作类型或改变核心档位定义；
- 同类定量术语、区间边界和定性升级条件不存在相互矛盾；
- fresh-context 独立复核没有未关闭的高优先级逻辑 finding，新增类型已经完成案例回归；
- 仍需历史数据验证的倍率明确标记为“待校准”，没有伪装成外部标准结论。

## 10. 评审决策

本设计选择混合模型，不选择以下两种方案：

- 仅使用全局评分卡：难以表达工作类型差异，强约束可能被其他低分项抵消；
- 为 191 个模式组合分别复制完整 S/M/L/X 表：重复内容过多，后续容易发生同义规则漂移。

混合模型把“不同工作类型测什么”放在 88 行专属标准中，把“不同模式测哪一部分”放在统一覆盖规则中；只有确有差异的工作类型再写模式例外。这样既能逐组合覆盖，又能保持标准统一和可维护。
