# 现状证据问卷

只有在直接调查后仍有一个或多个 Topic 缺少可验证证据时，才使用本问卷。仅选择其回答会影响这些 Topic 稳定合同的问题，并将回复写入 `.ai-sow/work/analyze-as-is/questionnaire.md`；默认不发送完整问题目录。

每个选中的问题都必须准确保留以下回复结构和五个固定字段名：

```text
Question ID:
Answer: <已知值 | UNKNOWN | NOT_APPLICABLE>
Owner:
Evidence reference:
Effective date:
```

## 生成问卷和评审关卡

写评审前先生成问卷。对于每个选中的问题，包含其确切问题文本，后接一条符合上述结构的完整回复记录。分别展开每个问题；ID 列表或范围不是回复记录。

到评审截止时间，将未回答的 `Answer` 规范化为 `UNKNOWN`。`Owner` 填写负责的人员、团队或所需角色；只有完全无法识别时才使用 `UNKNOWN`。缺失的 `Evidence reference` 和 `Effective date` 填写 `UNKNOWN`。已确认回答的生效日期使用 ISO `YYYY-MM-DD`。在 `Answer` 值中保留冲突陈述及其来源和生效日期差异，同时保持五个字段全部存在。

在评审第 7 节添加 **选中的问卷记录** 小节，链接 `.ai-sow/work/analyze-as-is/questionnaire.md`，并为每个选中的问题复现五个字段。批准前必须具备这个固定字段小节，包括每个选中的平台、环境、拓扑、基础设施责任、网络、机密、容量、备份/灾难恢复、CI/CD、发布和支持问题。

`Owner` 是负责的人员或团队。`Evidence reference` 指向提供佐证的政策、系统、工单、仪表板、操作手册、合同或其他可访问来源；其中不得包含凭据或复制的源内容。

## `SYSTEM_CONTEXT`

- `sys-01`：范围内包含哪些系统、业务流程和组织边界？
- `sys-02`：哪些用户组、操作人员、管理员和外部参与者与其交互？
- `sys-03`：哪些上游、下游或共享系统位于边界内，哪些位于边界外？
- `sys-04`：哪个团队负责产品、服务和每个跨系统边界？
- `sys-05`：哪些现有企业服务或人工流程必须保留在当前基线中？

## `CAPABILITY`

- `cap-01`：当前运行哪些业务和技术能力，面向哪些用户？
- `cap-02`：哪些端到端工作流是自动、人工或混合模式？
- `cap-03`：哪些当前能力成果、服务水平或验收指标具有权威性？
- `cap-04`：哪些团队负责并执行每个当前工作流或运营决策？
- `cap-05`：哪些能力不可用、部分实现、已弃用或计划退役？

## `APPLICATION`

- `app-01`：当前部署了哪些应用、服务、模块、作业和运行时组件？
- `app-02`：这些组件适用哪些版本、运行时技术栈和生命周期状态？
- `app-03`：哪些用户入口、API、事件入口、批处理入口或管理入口处于活动状态？
- `app-04`：哪些调度器、工作进程、后台作业或生成组件参与运行时行为？
- `app-05`：哪个团队负责每个组件的代码、配置、运营和退役？

## `INTEGRATION`

- `int-01`：存在哪些入站和出站集成？分别说明来源、目标、目的、协议和负责人。
- `int-02`：什么会触发每个 API、事件、消息或文件交换，频率是多少？

## 确定性编译

每个选中的 Question ID 只处理一次，并在工作证据中保留原始回复。

1. 对回复分类：
   - **已确认：** `Answer` 包含明确的已知值或 `NOT_APPLICABLE`；`Owner` 和 `Effective date` 均存在；并且没有可访问证据与其冲突。
   - **未知：** `Answer` 为空或为 `UNKNOWN`，或者评审截止时问题仍无回复。
   - **冲突：** 两个回答不一致、回答与直接证据冲突，或所述生效日期描述了不兼容的当前状态。
2. 对于已确认回复，创建一条 `kind: QUESTIONNAIRE` 的 Evidence 记录，`reference: questionnaire:<Question ID>`，在 `summary` 中包含简明回答和生效日期，并将每个受支持的 Item、Commitment、Effective Start、Coverage 或 Uncertainty ID 写入 `supportsIds`。只有在回答能够确定这些实体的合同字段时，才创建或更新受支持实体。`NOT_APPLICABLE` 回答只有在其负责人和证据依据使排除结论可验证时，才支持排除。
3. 对每个未知回复，不创建 `QUESTIONNAIRE` Evidence、现状 Item 或 Effective Start。创建一个 Uncertainty；已知时将回复的 `Owner` 设为 Uncertainty 负责人，否则指出必须回答的角色。
4. 对于冲突回复，不根据有争议的事实创建 `QUESTIONNAIRE` Evidence、确定性现状 Item 或 Effective Start。创建一个 Uncertainty，指出相互竞争的陈述、各自的证据引用和生效日期、决策影响、负责人以及建议的解决方式。
5. 将暴露同一影响决策缺口的问题去重为一个 Uncertainty，并将其关联到每个受影响的 BUSINESS Feature。不能影响下游工作的运营琐事只保留在工作证据中。
6. 当任何未解决的问卷缺口阻碍形成可用的 Topic 结论时，将 Topic 设为 `INSUFFICIENT_EVIDENCE` 并关联其 Uncertainty ID。只有证据支持的排除才能使用 `NOT_APPLICABLE`；空白、`UNKNOWN` 或未回答的回复绝不证明不适用。
