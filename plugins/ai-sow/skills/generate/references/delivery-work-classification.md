# 交付工作分类

交付工作不是天然的技术需求。只有本次范围内存在明确交付物、验收结果、责任边界和可结束工作量时，才按正确层级承载；项目外组织、客户或第三方承担的动作不进入 SOW 的 Epic、Feature、Story、AC、Task 或人天。

| 工作 | 何时承载 | 不应承载的情形 |
| --- | --- | --- |
| 自动化测试 | 只验证一个业务结果时作为该 Story 的测试 Task；公共测试能力有独立成果、AC、来源和范围时才是 Technical Story。 | 不能把每个 AC 机械变成测试 Task，也不能把常规质量门禁重复计价。 |
| 数据迁移 | 有明确对象、来源目标、校验结果、责任与切换边界时建立相应交付项。 | 只有“清理数据”“协助迁移”而无对象和结束条件时。 |
| 发布准备 | 有明确环境、配置、发布物、验收或责任边界时由相关 Story 或独立技术结果承载。 | 不能用“支持上线”概括未知工作。 |
| 发布切换 | 有来源支持的切换对象、触发、回退责任和完成条件时承载。 | 不能把持续运行保障或外部运维承诺包装为切换。 |
| 运维交接 | 有明确交接材料、受方、演练或验收结果时承载。 | 不能写成“上线后保障期”“持续支持上线”“保障平稳运行”等开放式工作。 |

## 判断顺序

1. 确认动作是否由本项目供应商承担；若不是，记录责任边界并停止拆解。
2. 确认是否有可观察交付物和完成条件；若没有，归入责任说明、NFR、DoD 或澄清问题。
3. 判断它只服务某个业务 Story，还是形成独立技术结果；分别放入 Story Task 或 Technical Story/Feature。
4. 为迁移、发布、切换和交接保留准确来源、对象、依赖、边界和验收；不能用未知未来问题填充范围。

常规 SIT / UAT 按模板与既有合同处理；只有来源明确、边界固定且不重复计费的专项保障才能单列。
