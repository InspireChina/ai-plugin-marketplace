# Epic 编写

## 是什么

Epic 是一段完整价值流、稳定业务域或跨业务的长期技术能力域，应容纳多个共享同一投入理由和价值边界的 Feature。

## 不是什么

它不是 PRD 标题、一个业务中心、页面、接口、单一步骤、技术组件，也不是只包一个 Feature 的空壳或收纳异质能力的抽象主题桶。

## 来源

从 PRD 与本轮选入 Demo 的需求并集识别业务价值流；长期技术或交付能力必须同时有本期需求依据和已批准设计/交付政策依据。HLD/ADR 不能扩张 PRD/Demo 未提出的业务范围，往期 SOW 和模板目录也不能创造 Epic。每个候选 Epic 必须回到本轮精确 SourceRef 或政策实例；参考示例不构成来源。

## 粒度

它回答“为什么要投入这一整段变化”，应跨多个能力结果。同一 Epic 的 Feature 必须能由一个稳定领域能力解释；迁移、业务集成、安全、可靠性、发布或移交等仅因都属于技术工作，不能自动归入同一 Epic。只有一个 Feature 是回看边界的信号，不是自动补造 Feature 的理由。

## 名称

使用领域中的名词或名词短语，表达可理解的价值流或长期能力，写清对象和边界。`闭环`、`保障`、`赋能`、`一体化`、`全链路` 等抽象词只有在来源把它定义为明确领域术语时才使用；名称用“与”连接多个主题时，必须复核它们是否共享同一价值边界，不能用口号掩盖拼盘。

## 与相邻层关系

Epic 向下组织多个 Feature；它不直接承载 Story、AC 或 Task。若内容只是一个可归责能力，应下调为 Feature；若多个 Epic 没有独立价值闭环，应合并或重新划分。SIT/UAT/GO_LIVE 等阶段名称本身不能成为 Epic，除非来源证明存在多个可独立关闭且共享长期能力边界的 Feature。

## 正例

`客户退换货管理` 可容纳申请、审核、退款、逆向物流等多个能力 Feature。

## 反例

`备件单创建` 只是一次可交付结果，不是完整价值流。

## 错误原因

反例把操作结果抬升为战略层，导致下层只能按岗位或步骤凑层级，无法表达价值边界。

## 纠正方式

回到来源寻找与该操作共同形成闭环的目标；若找不到，保留为 Story 或 Feature，不强行创建 Epic。

## 机械门禁

Epic ID、名称唯一性及其 Feature 引用必须通过结构校验；每个被纳入范围的 Feature 必须归属一个 Epic。

## Reviewer 判断

Reviewer 结合来源判断该 Epic 是否确有完整价值流或长期能力、多个 Feature 是否共享同一投入理由，以及名词化名称是否仍掩盖了异质能力或抽象主题桶；这些语义不能由数量门禁替代。
