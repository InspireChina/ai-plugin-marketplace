# Epic 编写

## 是什么

Epic 是一段完整价值流、重大业务目标或跨业务的长期技术能力域，应容纳多个互相关联的 Feature。

## 不是什么

它不是 PRD 标题、一个业务中心、页面、接口、单一步骤、技术组件，也不是只包一个 Feature 的空壳。

## 来源

从 PRD 的业务目标、范围边界和责任信息，或 HLD 中有明确业务影响的长期技术目标提取。每个候选 Epic 必须能回到当前项目来源；参考示例不构成来源。

## 粒度

它回答“为什么要投入这一整段变化”，应跨多个能力结果。只有一个 Feature 是回看边界的信号，不是自动补造 Feature 的理由。

## 名称

使用可理解的价值流或长期能力名称，写清对象和边界，不以“完成”“实现”“赋能”一类口号命名。

## 与相邻层关系

Epic 向下组织多个 Feature；它不直接承载 Story、AC 或 Task。若内容只是一个可归责能力，应下调为 Feature；若多个 Epic 没有独立价值闭环，应合并或重新划分。

## 正例

`客户退换货与退款闭环` 可容纳申请、审核、退款、逆向物流等多个能力 Feature。

## 反例

`备件单创建` 只是一次可交付结果，不是完整价值流。

## 错误原因

反例把操作结果抬升为战略层，导致下层只能按岗位或步骤凑层级，无法表达价值边界。

## 纠正方式

回到来源寻找与该操作共同形成闭环的目标；若找不到，保留为 Story 或 Feature，不强行创建 Epic。

## 机械门禁

Epic ID、名称唯一性及其 Feature 引用必须通过结构校验；每个被纳入范围的 Feature 必须归属一个 Epic。

## Reviewer 判断

Reviewer 结合来源判断该 Epic 是否确有完整价值闭环、多个 Feature 是否共享边界，以及名称是否掩盖了无关主题；这些语义不能由数量门禁替代。
