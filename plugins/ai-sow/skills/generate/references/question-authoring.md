# 问题与确认材料编写

每个待确认问题必须是一个可回答、可决定、可停止的问题，并固定为同一版本的四个部分：

1. **问题**：需要用户确认的具体事实、边界或选择。
2. **为什么要问**：当前来源、证据缺口或冲突为什么不足以支撑该判断。
3. **答案决定什么**：答案会改变的精确 Scope、责任、Story、Task、工作方式、复杂度、估算、风险或发布决定。
4. **未回答后果**：是形成有边界的假设、改为设计/调研，还是因不能建立可信范围而阻断。

## 编写规则

- 一个问题只处理一个实质决定；不要用“为了保证准确性”或“影响后续结果”等空泛原因替代来源和影响。
- 问题应说明对象、当前已知事实和需要确认的边界，避免“请补充更多信息”。
- 可读确认材料按问题逐项展示四部分、相关来源摘要、候选边界和用户答案；不要求用户阅读内部 ID、hash 或机器 token。
- 答案只能解决其绑定的问题；若答案引出新的独立决定，创建新问题，不偷换原问题版本。

## 答案绑定与来源

只有通过 `questionSha256` 精确绑定当前完整问题包的答案才能形成 `QUESTION_ANSWER` 语义锚点；未回答的
问题没有证据锚点，未知问题、重复答案或问题 hash 不匹配时不写入 pending。锚点的
`normalizedText` 逐项保留四部分问题内容和答案，`locator` 使用 `question:<questionId>`。
同一请求中的 `questionId` 必须唯一，即使两个问题包文本完全相同也不能复用；文档 `sourceId` 与由有效
答案生成的 `QUESTION_ANSWER` sourceId 冲突时同样在 pending 写入前阻断，不能让问答证据关联到文件快照。

机器身份只依赖稳定 `questionId`：`sourceId` 为
`question-answer-<SHA-256(canonical {"questionId": questionId})>`，`anchorId` 为
`question-answer-anchor-<同一完整 SHA-256>`。内容 `sha256` 绑定 canonical 完整问题包和精确答案。
因此只改变答案时 source/anchor ID 保持不变、内容 hash 改变并形成 `MODIFIED`；不同问题即使文本和答案
相同也不会共享锚点。Scope、Effective Start、假设、AC 或其他对象使用该答案时，必须引用这一锚点的
精确 `(sourceId, anchorId, sha256)`，不能引用聊天轮次、摘要或只有答案文本的记录。

## 示例

**问题：** 项目开始时，订单系统是否已提供可供本项目调用的取消订单契约？

**为什么要问：** 往期材料只说明计划对接，当前来源没有证明该契约已可用。

**答案决定什么：** 决定本次是否需要修改既有对象或在项目侧完成适配，并影响对应 Task 的边界。

**未回答后果：** 不能把计划能力当作起点；需固定为新建边界或提出限定设计/调研工作。
