# 技术工作分类

先判断技术项的交付语义，再决定承载层级。不要把实现机制自动升级为 Technical Feature，也不要把持续规范拆成可计价 Story。

| 候选项 | 承载方式 | 判断要点 |
| --- | --- | --- |
| 对所有交付持续适用、没有 Story 特定行为 | NFR、DoD 或质量门禁 | 约束实施或验收，不建立目标、指标、质量属性、政策类别或控制 Story。 |
| 只服务一个业务结果 | 该业务 Story 下的 Task | 与该 Story 一起交付、验证和关闭。 |
| 有一个独立移交、验收和关闭的技术结果 | Technical Story | 必须由来源或已批准设计明确支持一个可独立运行或消费的机制、配置、证据包或运营能力，并共同证明自己的交付、责任或消费者、验收、关闭或发布边界。 |
| 多个 Technical Story 共同形成消费者可感知能力 | Technical Feature | 不是单个组件或方案名称。 |
| 多个 Technical Feature 组成长期跨业务能力域 | Technical Epic | 应有完整价值与来源边界。 |

## NFR 与 DoD

NFR 是来源明确的性能、安全、审计、可用性等结果约束；DoD 是持续适用的工程完成标准。测量、报告阈值或符合一项陈述本身不是独立购买和关闭成果；目标、指标、质量属性、政策类别或异质控制集合也不因可以测试或验收而成为 Story。它们应先作为来源可追溯的 AC 落到每个适用 Story；项目级且没有 Story 特定行为时，作为 NFR、DoD 或质量门禁，不重复建立或计价 Story。

## Task 与技术层级

一个机制若只实现某业务 Story 的结果，就是该 Story 的 Task；只有其本身由来源或已批准设计明确支持为可独立运行或消费的具体技术结果，且同时具备交付、责任或消费者、验收、关闭或发布边界，才从 Technical Story 起步。控制归组、验收活动、证据收集或指定验收人不能代替这个结果；Story 标题必须说明被交付的行为或能力。自动化、性能、安全或合规测试可作为受影响 Story 下的 Task，但不能反向证明已有目标或控制应当成为 Story。若授权、状态或政策控制只在提交、审批、查询等业务触发执行，先写入所有受影响业务 Story 的 AC；跨切面不是创建共享控制 Story 的理由。不要因为使用认证、缓存、消息或监控技术，就自动创建 Feature 或 Epic。

## 设计与探索

未知问题只有具备明确问题、时间盒、交付物和评审 AC 时，才成为有边界的 Spike 或 Design 工作；常规实现分析不自动计价。实现机制、阈值和产品选择必须由当前来源或已批准设计支持。
