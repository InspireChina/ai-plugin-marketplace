# 技术工作分类

先判断技术项的交付语义，再决定承载层级。不要把实现机制自动升级为 Technical Feature，也不要把持续规范拆成可计价 Story。

| 候选项 | 承载方式 | 判断要点 |
| --- | --- | --- |
| 对所有交付持续适用、没有独立可关闭成果 | NFR、DoD 或质量门禁 | 约束实施或验收，不重复建立 Story。 |
| 只服务一个业务结果 | 该业务 Story 下的 Task | 与该 Story 一起交付、验证和关闭。 |
| 有独立可验证、可关闭的技术结果 | Technical Story | 需要自己的 AC、来源和估算边界。 |
| 多个 Technical Story 共同形成消费者可感知能力 | Technical Feature | 不是单个组件或方案名称。 |
| 多个 Technical Feature 组成长期跨业务能力域 | Technical Epic | 应有完整价值与来源边界。 |

## NFR 与 DoD

NFR 是来源明确的性能、安全、审计、可用性等结果约束；DoD 是持续适用的工程完成标准。两者没有独立购买和关闭成果时，作为约束与门禁，不在每个 Story 重复计价。

## Task 与技术层级

一个机制若只实现某业务 Story 的结果，就是该 Story 的 Task；只有其本身形成独立、可验收、可关闭的技术结果，才从 Technical Story 起步。不要因为使用认证、缓存、消息或监控技术，就自动创建 Feature 或 Epic。

## 设计与探索

未知问题只有具备明确问题、时间盒、交付物和评审 AC 时，才成为有边界的 Spike 或 Design 工作；常规实现分析不自动计价。实现机制、阈值和产品选择必须由当前来源或已批准设计支持。
