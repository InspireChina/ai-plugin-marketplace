# Task 编写

## 是什么

Task 是实现一个 Story 及其全部 AC 所需、可独立执行、估算和验收的工作单元。每条 Task 由运行时从权威模板选择一个基础单元，并结合 Effective Start 与证据完成工作方式和复杂度判断。

## 不是什么

它不是 Story 名称加“开发”、不是多接口或多交付物的打包项、不是每条 AC 的一对一副本、不是跨 Story 的共享工作包，也不是岗位占位。

## 来源

Task 依据同一 Story 的全部 AC、已批准 Design / Integration / NFR、Effective Start 证据及运行时读取的权威模板生成。名称或理由不得凭示例、惯例或猜测引入未经来源支持的技术方案。

Task 拆分只能在当前受影响 Story 与 AC 已完整编写并通过来源闭包自检后开始。Task 可以落实 AC，但不能为了迁就模板项、工作量或实现习惯反向扩大、合并或改写 Story/AC；发现上游语义不成立时必须先返回 Story/AC 修正，再重新开始 Task 拆分。

## 粒度

一条 Task 只承载一个可独立估算的工作单元；多个可独立接口、对象或交付物必须拆开。Task 超出 Story 容量时先回退检查 Story 是否包含多个独立结果，不能通过模糊合并逃避边界。

## 名称

名称使用“动作＋业务或技术对象＋单一交付物”，让评审者无需读取理由也能识别计数对象。接口项只表达一个可独立开发、测试和估算的契约；接口内部的校验、事务、权限和异常属于其实现与 AC，除非该校验本身形成独立调用契约。

## 与相邻层关系

Task 只属于一个 Story，可覆盖该 Story 的多条 AC；依赖只表达已计价 Task 之间的顺序，不复制其他 Story 的 AC。它向下由模板目录确定计数与判断边界，不在静态文档中复制该目录。

## 正例

`新增退货申请提交接口` 清楚说明一个对象、动作和单一交付物。

## 反例

`实现退货工单创建、校验与提交接口` 把多个可能独立的接口和业务责任合并在一行。

## 错误原因

反例无法判断唯一计数对象，也无法分别验收、覆盖 AC 或追踪已有能力的修改/复用证据。

## 纠正方式

按独立契约或业务结果拆分；重新读取当前运行的模板目录与[Effective Start 匹配](effective-start-matching.md)。不能确定模板项、工作方式或复杂度时提出澄清，不猜测进入稳定 Delivery。

## 机械门禁

Task 的 Story 引用、基础单元、工作方式、复杂度、覆盖关系、依赖和适用的 Effective Start 证据必须通过运行时合同校验；无效或不匹配的目录项、开放式工作和跨 Story 覆盖不得发布。

## Reviewer 判断

Reviewer 结合当前模板和项目证据判断名称是否隐藏多个交付物、目录匹配是否真实、工作方式是否被粗粒度现状证据误导，以及拆分是否仍可独立验收。

## 模板权威

具体目录、计数口径、允许工作方式、复杂度标准与计算规则只由运行时读取当前权威模板。静态指导不复制目录条目、目录规模、人员工作量或复杂度规则。

若当前目录为空、缺少可用项，或候选工作不能匹配当前目录中的唯一基础单元，不得沿用记忆中的旧模板项、复杂度措辞或工作量。应先恢复有效目录、拆分/澄清候选工作，或形成有边界的问题；未确认前不能发布稳定 Delivery。
