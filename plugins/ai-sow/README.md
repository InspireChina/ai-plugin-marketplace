# AI SOW

AI SOW 是一个 Codex 插件，用于把需求材料和系统现状整理成可评审、可追溯的
工作说明书（SOW）。它不会一次性自动生成结果，而是按阶段推进：插件先整理草稿，
对应角色与 AI 协作调整并确认，通过后再进入下一阶段。

插件负责阅读材料、整理结论、记录依据、检查前后是否一致，并生成最终工作簿；
BA 先处理业务需求，TL 再完成系统分析、设计、交付拆分和最终生成，PM 在后段补充
人员与迭代计划。最终 Excel 由 TL、BA 和 PM 分别复核。插件不能代替任何角色作出决定。

## 前置条件

- 支持本地 marketplace 的 Codex
- 首次运行环境自举时可访问 Astral 官方下载源

Codex 会为插件创建独立的安装副本。第一次运行 `setup` 时，插件会自动准备
[uv](https://docs.astral.sh/uv/) 0.11.7、managed Python 3.12 和锁定依赖，并创建插件自己的
`.venv`；BA、PM 或其他用户不需要打开终端，也不需要管理员权限。若企业网络需要授权，Codex
只会请求完成官方下载安装所需的一次联网权限，然后自动重试。
setup 在 macOS/Linux 实际调用 `bootstrap.sh`，在 Windows 调用 `bootstrap.ps1`。macOS 已实机
验证；Windows 11 当前仍是 `Provisional`，完整限制见
[插件运行时环境合同](references/runtime-environment.md)。
插件升级不会改动用户项目中已有的 SOW 数据。

## 怎么使用

在需要编制 SOW 的项目根目录中打开 Codex，然后直接用自然语言调用 AI SOW。正常使用
不需要手工寻找或运行插件中的 Python 脚本。

第一次开始时可以说：

```text
请使用 AI SOW 初始化项目。项目 ID 是 crm-modernization，项目名称是 CRM 现代化。
初始化后告诉我下一步需要提供什么。
```

随后按阶段提供材料、评审和批准：

```text
请进入需求分析。需求简报和会议纪要位于 docs/requirements/。
请先整理评审稿，有不清楚的地方就列出问题，不要自行假设。

请告诉我当前要评审什么、还有哪些问题没解决、满足什么条件才能进入下一步。

我已经评审并批准本阶段结果，请保存正式结果、完成检查并进入下一阶段。
```

每次只推进一个阶段。插件会先把便于阅读的评审稿放在 `.ai-sow/reviews/`，经相关角色
明确批准后，再保存供下一阶段使用的正式结果。下游发现问题时，应回到负责该结论的阶段
修改，不能直接改最终工作簿来掩盖问题。

### 开始前要准备什么

最少需要稳定的项目 ID、项目名称和业务需求材料。对于既有系统改造，建议同时准备：

- 业务简报、招标文件、合同范围、会议纪要或利益相关方说明；
- 可以调查的本地代码库，以及允许查看的版本或提交号；
- 往期 SOW、现有功能清单和已经承诺但尚未交付的范围；
- 配置、部署、集成、数据、安全、运维和质量相关材料；
- 已知的上线窗口、责任边界、外部依赖和验收约束。

没有代码库或往期 SOW 也可以开始。TL 需要说明哪些方面缺少依据，以及这些未知情况
会不会影响范围或估算。输入可能包含客户或内部机密，使用前请先阅读
[生成数据与敏感数据](#生成数据与敏感数据)。

## 角色与职责

| 角色 | 主要职责 | 必须由本人确认的事项 |
| --- | --- | --- |
| BA | 使用 `analyze-requirement` 生成并处理需求，回答 AI 整理的需求问卷；复核 `generate-story` 生成的 Story 和验收条件（AC）；复核 `generate-sow` 生成的 Excel | 业务需求是否准确、问题是否处理完整、Story 和 AC 是否符合需求、最终 Excel 是否准确反映业务与交付内容 |
| TL | 使用 `setup` 初始化项目；使用 `analyze-as-is`、`generate-design`、`generate-story` 和 `generate-task` 完成系统分析、总体设计、Story、AC 和 Task，并与 AI 协作调整确认；使用 `generate-sow` 生成 Excel，并组织最终复核 | 项目设置、系统现状、总体设计、Story、AC、Task 和最终 Excel 是否正确，技术内容和估算是否有依据 |
| PM | 在 `generate-task` 完成后补充人员和迭代计划；复核 `generate-sow` 生成的 Excel | 人员和迭代计划是否完整，最终 Excel 是否满足项目管理和交付要求 |

“主责”表示该角色对阶段结论负责，不表示所有材料都要由他手工整理。AI SOW 插件是
三个角色使用的辅助工具，负责阅读获授权的材料、整理评审稿、记录依据、检查阶段结果
和生成工作簿，但不承担流程责任。除项目初始化和指定的复核节点外，主线按
BA 处理需求、TL 完成交付编制、PM 完成后段工作的顺序推进。

每个阶段都要经过相关角色评审，插件不会自动一路运行到底。图中的 Skill 是责任人在该阶段
使用的辅助工具，不是独立的流程角色。图只画正常通过的主线；任何环节发现问题，都要由
该内容的负责人回到对应阶段，与 AI 调整并重新确认，再继续后面的工作。最终复核发现问题

SOW package 复读和完整 packet，再由一个 Reviewer 审查并一次批准；每份稳定数据仍由原 Owner
规则和确定性脚本负责，批准后只执行 hash 检查与可恢复发布。

## 七个阶段

项目按以下顺序推进，每个阶段由相应责任人使用对应的 Skill：

1. `setup`
2. `analyze-requirement`
3. `analyze-as-is`
4. `generate-design`
5. `generate-story`
6. `generate-task`
7. `generate-sow`

这些名称用于让 Codex 选择正确的插件能力。实际使用时可以直接说“初始化项目”“分析需求”
或“继续下一阶段”，不需要记住英文名称。`generate-task` 与 `generate-sow` 之间还需要由
PM 补充人员和迭代计划；支持这项工作的 Skill 尚在规划中，不属于当前七个 Skill。

`reconcile` 不属于上述七个阶段。它只用于完整链已经存在后的修正，按固定后缀协调
`CHANGED/NO_CHANGE`、批准前分 Owner 校验与 SOW 再生成、整体 packet Review 和可恢复发布；普通
首次交付仍按七阶段推进。技术实现调整默认保持已批准 Story/AC 原字节，Task 只能满足业务合同，
不能反向改写。

### 1. 初始化项目

- **主责：** TL。
- **输入：** 项目 ID 和项目名称；插件运行环境由 `setup` 自动准备。
- **输出：** 项目基本信息、SOW 模板和后续阶段所需的项目目录。
- **必须评审：** 项目名称和 ID 是否正确，插件版本和 SOW 标准是否符合本次项目。
- **需要澄清或阻塞：** 已有项目和本次输入的身份不一致、模板内容冲突、目录不安全或
  环境检查失败。
- **完成标志：** TL 确认项目设置，初始化检查通过。

### 2. 分析业务需求

- **主责：** BA 使用 `analyze-requirement` 生成并处理需求，回答 AI 整理的需求问卷。
- **输入：** 业务简报、招标文件、合同范围、研讨会记录、会议纪要和利益相关方说明。
- **输出：** 业务需求评审稿（含完整来源处置清单）；必要时附一份需求问卷；批准后保存正式业务需求。
- **必须评审：** 每项需求来自哪里，业务目标是什么，最小范围如何划分，哪些内容属于
  本次项目，业务规则、优先级和验收意图是否清楚；来源中的明确技术输入是否完整留给设计阶段，
  “沿用/不替换/仅集成”等边界是否覆盖全部受影响的业务范围。
- **需要澄清或阻塞：** AI 要把材料不足、内容冲突或可能改变范围和验收结果的问题整理成
  明确的问题清单，交给 BA 回答。BA 与 AI 反复调整，直到关键问题全部处理完成；非关键
  问题只有在 BA 明确给出处理方式后，才能作为暂定条件带到后续阶段。
- **完成标志：** BA 批准业务结论和范围，插件检查通过。

### 3. 调查系统现状

- **主责：** TL 在需求处理完成后使用 `analyze-as-is`，与 AI 协作分析、调整并确认系统现状。
- **输入：** 已批准的业务需求，以及获授权的代码库、往期 SOW、配置、部署材料和其他
  现状依据。
- **输出：** 系统边界、能力、应用、集成、数据、平台、安全、运维质量和交付约束等
  九方面的调查结论；同时整理往期承诺、项目起点、需求覆盖、依据和未知情况。
- **必须评审：** 这是全新项目还是既有系统改造；往期承诺哪些已经实现、哪些仍待交付；
  项目开始时真正可以复用什么；每项业务需求有哪些现有能力和缺口；未知情况是否影响估算。
- **需要澄清或阻塞：** 插件先调查已有静态材料，再询问仍无法确定的问题。默认不启动应用、
  数据库或容器；只有重要问题无法从现有材料判断时，说明原因后才做最小范围的运行验证。
  没有答案时必须记录为未知，不能把推测写成现状。
- **完成标志：** TL 确认系统现状和需求覆盖情况，插件检查通过。

### 4. 形成目标方案和技术需求

- **主责：** TL 使用 `generate-design` 形成总体设计和技术需求，与 AI 协作调整并确认。
- **输入：** 原始需求材料、已批准的业务需求和系统现状。
- **输出：** 目标方案、架构变化、范围结论和完整的技术需求。
- **必须评审：** 每项业务和技术需求是本次交付、现状已完整覆盖，还是明确排除；每项技术
  需求来自原始材料还是方案决定；未知情况如何处理；总体方案是否完整；生产环境、配置、
  发布与回滚、数据迁移、生产验证、监控、运维移交、上线后支持、用户培训和旧系统退役
  是否都有明确结论。
- **需要澄清或阻塞：** 影响估算的未知情况没有解决、范围内需求没有方案覆盖、声称现状
  已覆盖却没有依据、上线责任不明确时都不能通过。专职驻场、固定班次、待命容量或
  全天候支持需要单独的容量估算或单独 SOW，不能按普通开发任务猜估。
- **完成标志：** TL 确认总体设计和上线技术边界，插件检查通过。

### 5. 生成 Story 和验收条件

- **主责：** TL 使用 `generate-story` 生成 Story 和验收条件（AC），并先完成技术复核；BA 再从
  业务和交付角度单独复核。
- **输入：** 业务需求、技术需求、系统现状、目标方案，以及前面阶段批准的问题处理结果。
- **输出：** 需求与现状之间的交付缺口、可独立交付的 Story、验收条件、集成点、假设和风险。
- **必须评审：** 每项交付范围是否都有对应的工作项；每个工作项是否能独立交付、验收和
  结算；验收条件是否能明确判断通过或不通过；上线准备、发布切换、生产验证和运维移交
  是否完整；数据迁移是否单独说明；集成责任、测试范围、支持边界、假设和风险是否清楚。
- **需要澄清或阻塞：** 前面阶段尚未确认时不能继续。TL 或 BA 复核发现问题后，由 TL
  与 AI 调整 Story 和验收条件；如果根因在需求、系统现状或总体设计，则先退回对应阶段
  修改并重新确认，不能在本阶段临时改写前面的结论。
- **完成标志：** TL 和 BA 分别完成复核并确认 Story、AC 和交付边界，插件检查通过。

### 6. 拆分任务并准备估算

- **主责：** TL 使用 `generate-task` 完成技术拆分和估算，与 AI 协作调整并确认 Task。
- **输入：** 已批准的交付项、系统现状、目标方案和项目 SOW 模板。
- **输出：** 可单独估算的任务清单。每项任务说明具体对象、工作方式、复杂度、理由、
  现状依据和必要的集成关系。
- **必须评审：** 每个交付项是否都有任务覆盖；每项任务是否只对应一个可估算对象；“新建”、
  “调整”或“接入复用”是否选择正确并有依据；复杂度是否合理；集成、发布、迁移、问题
  诊断和整改是否遗漏或重复计算。
- **需要澄清或阻塞：** 任务过大或边界不清时，要继续拆分、补充问题或先安排专题调研；
  缺少集成记录时退回交付或方案阶段；没有现状依据时，不能把任务判断为“调整”或
  “接入复用”。
- **完成标志：** TL 确认 Task、估算和技术责任，插件检查通过。人天由 SOW 模板根据
  基础工作、工作方式和复杂度统一计算。

### 生成最终 SOW 前：补充人员和迭代计划

- **主责：** PM。
- **开始条件：** `generate-task` 已经完成，TL 已确认 Task 和估算。
- **工作内容：** PM 补充项目人员和迭代计划，并确认这些安排可以支持已批准的交付范围。
- **当前限制：** 支持这一步的 Skill 尚在规划中。当前版本不会自动生成或检查人员和
  迭代计划，需要由 PM 在插件流程之外完成；PM 确认完成后，TL 再调用 `generate-sow`。

### 7. 生成最终 SOW

- **主责：** TL 使用 `generate-sow` 生成 Excel，并与 AI 协作处理生成或内容问题；生成后
  由 TL、BA 和 PM 分别复核。
- **输入：** 五位 Owner 的有效 0.3 收据、六份正式结果、五份批准评审，以及项目 SOW 模板。
- **输出：** 确定性的 `.ai-sow/outputs/sow-sha256-<generationFingerprint>/` 目录，其中包含
  `sow.xlsx`、`manifest.json`、六份阶段结果、五份批准评审、五份收据和模板副本。相同输入
  复用相同包；同一 package ID 下的不同内容会被拒绝，不会覆盖。
- **必须评审：** TL 核对系统现状、技术需求、集成、Task、技术责任和估算；BA 核对需求、
  Story 和 AC；PM 核对最终 Excel，并确认它与另行完成的人员和迭代计划没有冲突。
  三个人分别完成复核。
  插件只填充模板，不执行 Excel 公式；计算结果要在能够计算该模板公式的表格软件中复核。
- **需要澄清或阻塞：** `generate-sow` 只汇编已经确认的结果，不在这个阶段重新决定需求、
  设计、Story、AC、Task 或估算。前置结果没有确认或文件检查失败时停止生成；Excel 复核
  发现内容问题时，回到对应阶段调整并重新生成。
- **完成标志：** 插件完成文件和前后关系检查，TL、BA 和 PM 分别完成 Excel 复核。

每个可独立引用的结构化实体同时保存必填 ID 和非空名称。最终工作簿只使用唯一名称作为业务
展示与引用主键，稳定 ID 继续保存在结构化 JSON 中。普通白色单元格可填写或选择；浅灰色
单元格由公式或结构化关系派生并锁定。`90-系统现状` 只保留一张项目起点明细表，展示主题、
现状条目名称、现状描述和起点可用性；主题与起点可用性提供浅黄色下拉，名称与描述可自由填写，
整页不启用保护。`05-任务明细` 的“关联现状条目”直接引用该可见名称列，不使用隐藏名单。
工作簿修改不会回写稳定 JSON、评审或 manifest。每个 Task 最多选择一个足以证明工作模式的现状条目，
每个 Story 最多选择一个足以说明不确定性的假设/风险，同一被引用条目可以服务多个 Task 或
Story。任务明细不展示集成点，集成页只在故事名称后带出关联集成 Task 的任务名称；验收条件
不展示结构化顺序，系统现状也不展示仅供审计的证据引用。生成器只接受当前模板合同，不迁移
尚未发布的旧项目模板。

## 评审、澄清和批准

### 一个阶段怎么完成

```text
提供材料
  → 插件整理评审稿
  → 主责角色检查结论、依据、范围、责任和未知情况
  → 有问题：回答、补材料、明确排除，或退回前面的责任阶段
  → 更新评审稿，直到没有阻塞问题
  → 相关角色明确批准
  → 插件保存正式结果并检查前后一致性
  → 检查通过后进入下一阶段
```

评审不是形式确认。批准前，主责角色至少要确认：材料是否齐全、结论是否有依据、范围和
责任是否明确、未知情况是否妥善处理、下一阶段是否能直接使用本阶段结果。

### 问题怎么澄清

1. 插件要说明问题会影响哪个业务结论、技术决定、交付边界或估算，不能只问宽泛问题。
2. BA 回答需求阶段由 AI 整理的需求问卷；TL 与 AI 处理系统现状、总体设计、Story、验收条件、
   Task 和 Excel 生成问题；PM 负责人员与迭代计划。Excel 复核中发现的问题要交回真正
   负责该内容的阶段处理。
3. 回答要写进对应的评审稿或问题清单，并保留决定日期、依据或明确的责任边界。聊天中的
   临时结论只有写入评审结果并获批准后，才能交给下一阶段使用。
4. 无法获得答案时，插件不能自行猜测。项目组可以明确排除该项，把它记录为有处理方案的
   假设或风险，或者保留为未知情况。只要它可能改变范围、责任、工作量或人天，就必须
   阻止最终生成，直到项目组作出决定。
5. 后面阶段发现问题时，要修改真正负责该结论的前面阶段，并重新生成受影响的结果。
   不要直接修改最终工作簿来掩盖问题。

### 谁批准什么

| 评审节点 | 负责确认的角色 | 通过条件 |
| --- | --- | --- |
| 项目设置 | TL 负责确认 | 项目身份、版本、模板和目录检查通过 |
| 业务需求 | BA 负责批准 | 关键问题已经解决，暂定条件明确，需求可以追溯到来源 |
| 系统现状 | TL 负责确认 | 调查范围、往期承诺、项目起点、需求覆盖、依据和未知情况都已说明 |
| 总体设计与上线范围 | TL 负责确认 | 方案完整，十项上线事项都有明确结论 |
| Story 和验收条件（AC） | TL、BA 分别复核 | 范围内需求都有可交付、可验收的安排，集成、假设和风险完整 |
| Task 和估算 | TL 负责确认 | Task 边界清楚、没有重复，工作方式和复杂度有依据 |
| 人员和迭代计划 | PM 负责补充和确认 | 当前由 PM 在插件流程外完成；配套 Skill 实现后再纳入自动检查 |
| 最终 Excel | TL、BA、PM 分别复核 | 前面各阶段均已确认，最终 Excel 与已确认内容一致 |

## 版本与估算规则

当前文档对应插件版本 0.1.0 和 SOW 标准 1.3。BA 处理需求，并复核 Story、AC
和最终 Excel；TL 负责项目设置、系统现状、总体设计、Story、AC、Task 和最终生成；
PM 补充人员和迭代计划，并复核最终 Excel。每项正式结论只有一个责任阶段，后面的阶段
只能引用，不能悄悄改写。

SOW 模板包含 13 个任务类别和 37 个基础工作项，并为“新建”“调整”“接入复用”三种
工作方式维护统一的人天规则。复杂度、集成测试、用户验收测试、风险和取整由模板公式
统一计算。总体方案和上线范围没有完成评审时，插件不会生成最终 SOW。

更详细的规则请参阅[设计文档](docs/AI_SOW_PLUGIN_DESIGN.md)和
[领域说明](docs/CONTEXT.md)。

## 生成数据与敏感数据

插件会在用户项目的 `.ai-sow/` 下保存项目基本信息、复制的往期 SOW、各阶段正式结果、
评审稿、临时文件和生成的工作簿。这些文件可能包含客户需求、代码库事实、估算和机密材料。

本仓库只对自己的测试项目忽略 `.ai-sow/runtime/`。在其他项目中使用本插件前，必须
先决定哪些路径不进入版本控制，或者只提交经过批准且适合公开的正式结果。未经评审，
不要发布 `.ai-sow/inputs/`、临时文件或客户交付物。

## 开发

在 marketplace 根目录运行：

```text
uv sync --project plugins/ai-sow --locked
uv run --project plugins/ai-sow --locked pytest -c plugins/ai-sow/pyproject.toml plugins/ai-sow/skills -q
```

AI SOW 在首次 `setup` 或安装副本缺少环境时自动准备插件私有 uv、managed Python、锁定依赖与
`.venv`；后续 Skill 直接使用该 `.venv` 的跨平台 Python 路径，不要求 uv 位于 PATH。插件不会操作
Git，不会执行 Excel 公式，不提供事务恢复，也不会把用户在工作簿中的修改反向写回阶段结果。
